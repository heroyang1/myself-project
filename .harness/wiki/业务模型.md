# 业务模型

> **装载时机**：写/改业务流程、状态机、库存/限购逻辑，或排查"订单为什么进不了某状态"时读。
> 本文是知识库第 1 层（五层见 `.harness/ROUTING.md` 表 1）。详情以代码与 `docs/design/` 为准，
> 本文只登记"是什么、在哪、别踩什么"。

## 1. 角色与能力边界

- **两套身份，永不混用**：`OshUser`（C 端用户，链路里用 `userId`，接口走 `/pc/**`）
  与 `SysUser`（B 端管理员，接口走 `/pc/admin/**` + `@PreAuthorize`）。
- C 端订单生命周期全由买家驱动；B 端只做审核与配置，不代客下单、不代客改状态（红线）。
- 权限注解不互用：C 端接口混挂 B 端 `@PreAuthorize` = 403 事故（案例集·案例5）。

## 2. 核心业务流程（三条主链路）

1. **课程购买**：下单（order=PENDING）→ 汇付/微信支付 → 回调三重校验（签名/金额/提供方）
   → 双 CAS 推进（payment 0→1、order 0→1 同事务）→ 权益发放（失败入 entitlementTask 重试）。
2. **拼团**：开团 → 参团（名额条件 CAS 递增）→ 成团履约 / 流团退款。
3. **秒杀**：Redis Lua 原子预检（扣库存+记已购，写 PENDING 占位）→ Kafka 异步落库
   → 前端轮询结果 → Quartz 扫过期未付单、Lua 带上限回滚。

## 3. 订单状态机 ⚠️ 双枚举撞号

- `OrderStatusEnum`：**PENDING 0 待支付 / PAID 1 已支付 / CANCELED 2 已取消 / CLOSED 3 已关闭**。
- `PaymentStatusEnum`：**PENDING 0 / SUCCESS 1 / FAILED 2 / CLOSED 3**。
- **同号不同义**：值 1 = 订单"已支付" vs 流水"成功"；值 2 = 订单"**已取消**" vs 流水"**失败**"。
  两枚举禁止互传值、禁止共用魔法数字，状态判断只许引枚举。
- 唯一入口：`handlePayNotify` 双 CAS 闸门 + 幂等短路（payment 已 SUCCESS 时直接分发
  handler，不再推进状态）。改状态必须走闸门，不许旁路 UPDATE。

## 4. 库存与限购三段式（秒杀）

- 预检：Lua 原子扣 `stock` + 记已购（**String 计数 Key**，支持多件限购——曾选错结构只支持单件）。
- 落库：消费者扣 DB 库存、写订单、占位 Key 换真实订单号；失败 Lua 回滚三件套。
- 归还：Lua `math.min` 封顶防超还（幽灵库存事故），DB 侧 `LEAST/GREATEST` 对称防护。
- TTL：禁写死，按活动结束时间 + 缓冲动态计算（`SeckillCacheConstants.calcExpireSeconds`）。

## 5. 金额规则

- 支付校验必须比对**实付总额**，禁止取单价（历史事故：金额字段取单价而非实付总额）。
- ⚠️ **存量债（实扫登记）**：实体层金额类型混用——`String price`（OshFlashsaleList / OshLearn /
  WxPay / OshOrderList）与 `BigDecimal price/amount`（OshGroupOrder / Coupon / OshOrderSave /
  OshPayment）并存。**新代码一律 BigDecimal + decimal 列，禁 float/double**；单位以 `sql/` DDL 为准。

## 6. 快照规则

- 订单价格/商品信息**固化存储**（快照溯源），展示订单禁止 JOIN 商品表现价。
- 无物理外键；关联完整性走业务层 + 索引。

## 7. 事务边界

- 原则：**核心同步（强一致）、非核心异步（Kafka/Outbox）**；事务范围尽量小，事务内禁远程调用。
- 非核心远程用 `@Transactional(REQUIRES_NEW)` 隔离；AOP 自调用失效走 `@Lazy` 自注入代理。
- "写 DB + 发 MQ"一律 Outbox：同事务登记事件 → **提交后**发布（TransactionSynchronization）
  → Quartz 兜底扫描；事件表带完整重试字段（retry_count / max / next_retry_time / last_error）。
- 消费端必须幂等。
