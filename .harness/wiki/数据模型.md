# 数据模型

> **装载时机**：建表、加字段、写复杂查询/JOIN、排查 DDL↔实体不一致时读。
> 本文是知识库第 3 层。表约定的**正文事实源**是 `docs/ai/conventions/database.md`
> 与 `sql/` 脚本（无 Flyway，DDL 走脚本+人审）——本文做装载式摘要+关系登记。

## 1. 表公约

- 前缀：`osh_`（业务）/ `sys_`（系统）；snake_case、禁复数、禁 MySQL 保留字。
- 关联表：`osh_<子域>_rel`；每张业务表必备六字段：
  `id / create_time / create_by / update_time / update_by / delete_flag`。
- 新行 `delete_flag` 默认值**必须为 0**，否则被全局拦截器过滤（存了等于没存）。

## 2. 逻辑删除双保障

1. **注解级**：`OSHBaseEntity` 的 `@TableLogic(value="0", delval="1") deleteFlag`，MP 自动追加条件。
2. **拦截器级**：`GlobalLogicDeleteInterceptor` 在 SQL 层注入 `delete_flag=0`（兜底原生 XML SQL）。

- 删除操作一律 `UPDATE SET delete_flag=1`，**禁 `DELETE FROM`**。
- LEFT JOIN 的 ON 条件须**显式** `AND b.delete_flag = 0`（拦截器可能不覆盖 JOIN 条件）。
- 唯一索引必须包含 `delete_flag`（否则逻辑删除后无法建同名记录）。
- ⚠️ 陷阱：拦截器对**无 delete_flag 列的表**会误注入、正则曾误匹配 SELECT 字段名——
  新建无该列的表前先查拦截器白名单机制。

## 3. 核心表关系（骨架）

```
osh_order ──1:1── osh_payment（流水，双枚举撞号警告见 业务模型#3）
    │
    ├── 权益发放失败 → entitlementTask（重试表，定时兜底）
    │
osh_outbox_event（本地事件表：event_id/aggregate_type/aggregate_id/event_type/
    topic/message_key/payload/status/retry_count/max_retry_count/
    next_retry_time/last_error/sent_time —— 与业务数据同事务登记）
    │
秒杀：osh_seckill_goods ⇄ Redis 三 Key（stock / boughtCnt / orderKey）+ DB 库存列
```

## 4. 字段语义纪律

- **状态列注释必须写全枚举**（`0待支付 1已支付 2已取消 3已关闭`）——order/payment 双枚举
  撞号史无前例地危险，裸数字注释 = 埋雷。
- 金额用 `decimal`，禁 `float/double`；⚠️ 存量债：实体层 `String price` 与 `BigDecimal`
  混用（清单见 业务模型#5），新代码一律 BigDecimal。
- 布尔用 `tinyint`；Java 字段禁 `is` 前缀（序列化丢值）。
- 小数比较、金额运算禁 double；`in` 集合 <1000；`like` 禁前置 `%`（大表走 ES）。

## 5. 索引与查询纪律

- WHERE 条件字段必建索引；联合索引按区分度从高到低；JOIN ≤3 张且连接字段类型一致并建索引。
- 正文细则：`docs/ai/conventions/database.md`（本文不复制）。

## 6. DDL 流程与一致性守卫

- 无 Flyway：DDL 落 `sql/<日期>/` 脚本 → 人审后执行；触碰 `sql/` = R2 保护域，必带 openspec change。
- **R6 四层一致**：改表必须同步 初始 DDL / ALTER / Entity / VO——`scripts/code-quality-guard.sh`
  机器强制（列类型匹配、必填四层齐、索引无幽灵列）。
- 新表优先继承 `OSHBaseEntity`（LocalDateTime + Long 审计字段）；`BaseEntity`（RuoYi 原版）
  只服务老表，两基类不许混用字段类型。
