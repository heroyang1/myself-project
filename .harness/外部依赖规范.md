# 外部依赖规范（线程池 · 超时 · 熔断降级）

> 源起：Harness 工程课程第 29~31 讲三段定稿细则收口（change: add-external-dependency-spec）。
> 本文是"规范层"全文；红线以 `CLAUDE.md` 第 2 层为准，本文与红线冲突时红线赢。
> 公理：外部依赖的失败必然发生，唯一变量是传染范围——三节各上一道笼：空间、时间、行为。

## 第 1 节 · 线程池

> **什么时候读这份规范**：新建/修改任何对外部服务的调用线程池，
> 或 review 到 `Executors.new*` / 缺参数的 `ThreadPoolExecutor` 构造时。

### 1.1 四参数必须显式声明并写注释

核心线程数 / 最大线程数 / 队列容量 / 拒绝策略——**每项都是人工签字的显式决策**，
注释即签字现场。默认值 = 没人对"愿意等多久、能排多深"负过责。

### 1.2 线程必须命名，格式 `<域>-call-%d`

如 `payment-call-1`。线程名是 thread dump 里唯一的"这是谁"信息：
慢失败不抛异常、不打错误日志，**线程状态 + 名字是仅存的现场证据**。
不命名：`pool-3-thread-7` 要 30 分钟反查调用点；命名：30 秒判定"支付池 10 线程全卡 socketRead"。

### 1.3 禁止 Executors 工厂方法（推导链）

```
newFixedThreadPool(n) → LinkedBlockingQueue 默认容量 Integer.MAX_VALUE（无界）
→ 队列永远不会满 → maximumPoolSize 永远不会生效 → 拒绝策略永远不会触发
→ 积压不报错只变慢，每个排队任务持有请求上下文 → 积压转化为堆内存占用
→ 最终 OOM 全站死，或健康检查超时杀进程
```

拒绝是**可控失败**（早死早超生、有日志有语义）；无界队列把可控失败转化为**不可控死亡**。
`newCachedThreadPool` 同理反向：无界线程数，线程本身撑死 JVM。

### 1.4 标准构造片段（Java 8）

```java
private static final ExecutorService PAYMENT_CALL_POOL = new ThreadPoolExecutor(
        10,                                        // ① 核心线程数：按下游容量人工定值
        10,                                        // ② 最大线程数：与核心相等 = 不隐式扩容
        100,                                       // ③ 队列容量：有界，100 ≈ 峰值 10s 缓冲，
                                                   //    超过该拒绝而不是该排队
        new ArrayBlockingQueue<Runnable>(100),     //    无参 LinkedBlockingQueue = 无界，禁用
        new ThreadFactory() {                      // ④ 命名：软失败探测器（见 1.2）
            private final AtomicInteger seq = new AtomicInteger(1);
            @Override
            public Thread newThread(Runnable r) {
                return new Thread(r, "payment-call-" + seq.getAndIncrement());
            }
        },
        new ThreadPoolExecutor.CallerRunsPolicy()  // ⑤ 拒绝策略：饱和时调用者自跑 = 天然背压，
);                                                 //    不丢任务、不抛异常、自动给上游限速
```

## 第 2 节 · 超时

> **什么时候读这份规范**：new 任何 HTTP 客户端/厂商 SDK、改超时配置、
> 或排查"上游超时、下游成功"类状态分叉时。

### 2.1 三层金字塔：下游必须小于上游

```
网关/前端 10s  >  订单服务 8s  >  支付调用（连接 2s + 读取 5s = 7s）
```

- 每层从上游预算倒推，**给本层自身处理留 1~2s 余量**（2+5=7<8 的算术）；
- 填完沿链求和检查一次，"下游<上游"是**验收断言**；
- 倒挂 = 产生**幽灵窗口**：上游已放弃、下游还在执行（见 2.4）。

### 2.2 连接 vs 读取：两段独立计时，各管一条失败通道

| 超时 | 管什么 | 取值原则 |
|---|---|---|
| 连接超时 | "进不进得了门"（宕机/拒连/断网） | 固定档 **1-3s**，连通性问题与业务无关 |
| 读取超时 | "进门后等多久上菜"（对方收下但慢） | **按业务定**，从上游预算倒推 |

**两个都要设，只设一个等于没设**：只设读取 → 握手阶段 OS 层 SYN 重试可挂几十秒，
读取计时根本还没开始；只设连接 → 对方秒接单但迟迟不响应，多数客户端读取方向默认不超时。

### 2.3 「默认值」不算填过

1. 默认值 = 无人签字的决策（与 1.1 同理）；
2. 默认值跨客户端不一致（RestTemplate/OkHttp/HttpClient/厂商 SDK 是四个不同数字，
   很多**默认不超时**——不设超时等于把线程无限期抵押给对方）；
3. "未设置"是显式暴露（钉在纸上的雷，下次排期就拆），"默认"是伪装合规（人人跳过）。

**填值两处、账实一致**：实际生效值进配置文件（`application*.yml`/Nacos，禁硬编码；
注意触碰 `application*` 属 R2 保护域须带 change）；登记值进本文附录清单第 3/4 列。

### 2.4 倒挂时间轴（反例：支付 10s > 网关 8s）

| 时刻 | 网关 | 订单服务 | 支付调用 | 用户 |
|---|---|---|---|---|
| 0~8s | 等 | 等 | 等渠道 | 转圈 |
| 8s | **超时返回，释放线程** | 还在等 | 还在等 | "失败了？" |
| 8~10s | 已下班 | 线程白占 | **扣款成功落库** | 以为没扣钱 |
| 10s | — | — | 超时或收到成功 | **再点一次 → 重复支付** |

后果按痛感排序：重复支付资损 > 日志对不上对账失能 > 线程连接白占放大故障 > 客诉信任损耗。

## 第 3 节 · 熔断降级

> **什么时候读这份规范**：给外部调用配熔断参数、写降级分支返回值、
> 或给支付类状态/常量命名时。

### 3.1 三态参数标准（每个值都是代价不对称称出来的）

| 参数 | 标准值 | 为什么 |
|---|---|---|
| 滑动窗口 | 20 次调用 | 太小误伤（一次抖动=20%），太大迟钝（被历史成功稀释）；按次数不按时间，低峰期时间窗攒不够样本 |
| 失败率阈值 | 50% | "一半都不信了才翻脸"：太低天天误熔断（会被绕过=没有），太高=对方躺下你还在压 |
| OPEN 持续 | 30 秒 | 按**对方典型恢复耗时**（重启/连接池重建量级）定，不按你的耐心；太短熔断震荡，太长伤业务 |
| HALF_OPEN 探针 | 3 次 | 小样本下注：误开亏 3 个请求，误关全量踩死对方——恢复判断从严 |

参数必须配置化（Nacos/yml），禁写死。三态完整剧本：观察 20 次 → 坏一半 → 休战 30s
（期间一律降级，连线程都不占用）→ 3 探针 → 成则 CLOSED，败则再休 30s。

### 3.2 支付类降级四条（第四条是前三条的生效前提）

1. **禁止返回「失败」**；2. **必须返回「处理中」**；3. **订单置「待确认」**；
4. **登记一条待对账记录，交支付回调 + 定时对账收敛到终态**。

前三条对用户挂起承诺（"还没完，我会给结果"），第四条保证必兑现——
没有兜底通道的 PENDING 会烂成**黑洞单**（不敢再付/查无实据/未决款），比失败更难收场。

### 3.3 命名立法：降级返回值常量禁叫 `PAY_FAILED`

超时那一刻对"钱扣没扣"掌握的信息 = **不知道**。`PAY_FAILED` 把"未知"偷换成
"确定没发生"，名字是代码里最粘的注释——下一个读者（尤其 AI）会信它，
然后基于"没扣钱"写出释放库存/允许重试 → 直接制造重复支付。
只许 `PAY_PENDING` / `PAY_PROCESSING`：**名字必须与认知状态同构；超时不是失败，是一次未决。**

### 3.4 收口红线句（候选，待 P6 决定是否晋升 CLAUDE.md 第 2 层）

> 支付类外部调用超时/失败时，一律返回「处理中」（枚举/常量命名只许 PENDING/PROCESSING，
> 禁 FAILED 语义）、订单置「待确认」、并登记待对账记录交回调与定时对账收敛到终态。

违例形态可判定：① grep 降级分支返回 FAILED/失败语义；② 支付出口查对账登记（无兜底 PENDING 同违）；
③ 状态枚举缺"处理中"值。
