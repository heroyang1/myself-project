### 三组“为什么”必背

| 问题 | 一句话回答 |
|------|----------|
| 为什么 CAS 而不是悲观锁？ | 支付回调低频，CAS 失败即幂等短路，比 FOR UPDATE 等待超时更简洁 |
| 为什么 Outbox 而不是双写？ | 双写任一失败都回滚且无故障恢复，Outbox 持久化到本地表可兑底重发 |
| 为什么 Lua 而不是分步 INCRBY？ | 秒杀需要“检查库存→检查限购→扣减→记录”四步原子化，分步有竞态窗口 |
| 为什么 @Scheduled 和 XXL-Job 共存？ | 历史演进——早期用 @Scheduled 轻量，后期引入 XXL-Job 统一管理。两套共存期间发现 P0 级重复调度 |

### CI/CD 五道关卡口诀

**合规 → 编译 → jar → SHA → 健康**

1. 流程合规：14 个核心文件 + OpenSpec 四件套
2. 编译验证：`mvn clean install -DskipTests`
3. jar 完整性：`unzip -t` + `sha256sum`
4. 远程一致性：本地 vs 远程 SHA256 对比
5. 健康检查：轮询 API，12 次 × 10s

### 安全红线三原则

1. **权限注解不可注释**——调试用管理员账号，不是注释 `@PreAuthorize`
2. **参数化查询防注入**——`#{}` 而非 `${}`
3. **限流接口防连点**——`@RateLimiter` + `submitLockKey`

### 定时任务五原则口诀

**事务 → 互斥 → 隔离 → 幂等 → 生命**

1. **事务边界**：状态更新 + 副作用必须 @Transactional
2. **多实例互斥**：select + update 范围对齐（WHERE id IN）
3. **异常隔离**：单步骤独立 try-catch，一条失败不影响后续
4. **幂等设计**：重复触发时 CAS 或状态检查保证幂等
5. **生命周期**：禁用任务必须注释原因，禁止僵尸代码

## 亮点一：Redis Lua 原子预检 + Kafka 异步落库的秒杀链路

### 技术场景（Context）

**业务痛点**：秒杀场景下，瞬时并发可达数千 QPS，传统"先查库存→再扣减→再建单"的同步链路在数据库层面会成为瓶颈，导致超卖、响应超时。

**技术选型**：采用"Redis Lua 前置原子扣减 → Kafka 异步建单 → 定时任务兜底取消"的三级架构，将并发压力从 MySQL 转移到 Redis，再通过消息队列削峰填谷。

**架构位置**：`OshSeckillOrderServiceImpl` 是入口，`SeckillOrderConsumer` 是异步消费者。

### 技术实现与亮点

核心 Lua 脚本（`OshSeckillOrderServiceImpl`）：

```lua
local stock = tonumber(redis.call('get', KEYS[1]))
local qty   = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
if stock == nil or stock < qty then return -1 end
local bought = tonumber(redis.call('get', KEYS[2])) or 0
if bought + qty > limit then return -2 end
redis.call('decrby', KEYS[1], qty)
local newBought = redis.call('incrby', KEYS[2], qty)
if newBought == qty then
    redis.call('expire', KEYS[2], tonumber(ARGV[3]))
end
return 1
```

- **双 Key 原子操作**：库存 Key + 已购数 Key 在同一 Lua 脚本内原子完成，支持多件限购
- **防重复提交**：`setIfAbsent(submitLockKey)` + `orderKey` 双重幂等守卫
- **消息体自包含上下文**：`SeckillOrderMessage` 携带 `stockKey/boughtCntKey/orderKey/expireSeconds`，消费者线程不依赖 `HttpServletRequest`
- **缓存 TTL 动态化**：`SeckillCacheConstants.calcExpireSeconds(endTime, buffer)` 按活动结束时间对齐，三档缓冲常量（活动 24h / 库存 2h / 已购数 2h）
- **DB 侧对称防护**：`decrStock` 用 `WHERE available_stock >= #{quantity}` 做闸门，归还用 `LEAST/GREATEST` 双向封顶

### 面试回答话术（STAR）

> **Hook**："我用一段 11 行的 Lua 脚本把并发压力从 MySQL 转移到 Redis——一次网络往返完成库存扣减、限购校验、防重复提交三件事，接口 RT 从 2 秒降到 50 毫秒。"
>
> **S**：项目有一个秒杀模块，活动开始时瞬时并发可达数千 QPS，直接操作数据库必然超卖且响应超时。
>
> **T**：需要设计一套能抗住高并发、不超卖、支持限购的秒杀链路。
>
> **A**：采用"Redis Lua 前置原子扣减 + Kafka 异步建单 + 定时兜底取消"三级架构。Lua 脚本在 Redis 中原子完成库存扣减和限购校验，一次网络往返完成三个操作；成功后生成秒杀尝试号，发送 Kafka 消息后立即返回；消费者异步完成数据库建单和支付发起。Quartz 定时任务每分钟扫描未支付订单自动取消并回滚库存。DB 层面用 `WHERE available_stock >= quantity` 作为最后一道闸门。
>
> **R**：成功支撑秒杀活动高并发场景，零超卖事故，接口响应从同步方案的 2s+ 降到 50ms 以内。

### 追问预判（深度扩展）

| # | 追问 | 应对思路 |
|---|---|---|
| 1 | Lua 脚本中为什么用 `tonumber`？ | Redis 存的是字符串，Lua 的 `tonumber` 确保按数值比较，避免字符串字典序比较（"9" > "10"）导致逻辑错误 |
| 2 | 如果 Kafka 消息丢了怎么办？ | orderKey 有 2 分钟 TTL，超时后前端轮询发现仍是 PENDING 会提示失败；定时任务扫描未支付订单做兜底取消；Kafka 本身有 retries + ack=all 保障 |
| 3 | 为什么不用 Redisson 分布式锁？ | 秒杀场景需要"快速失败"而非"排队等待"，Lua 脚本一次网络 RTT 完成，比分布式锁更轻量 |
| 4 | 缓存 TTL 为什么要动态化？ | 固定 TTL 在活动结束后仍然占用 Redis 内存，动态对齐后活动结束自动过期回收。三档缓冲常量区分活动缓存（+24h 保证列表可看）和库存缓存（+2h 精确够用） |
| 5 | 消费者失败后如何回滚 Redis？ | 消费者捕获异常后执行 Lua 归还脚本：`incrby stockKey quantity` + `decrby boughtCntKey quantity` + `del orderKey`，归还同样加 `math.min` 边界 |
| 6 | 为什么要设 `submitLockKey`？ | 防止用户快速连点同一按钮导致多次 Lua 扣减。`setIfAbsent` + 短 TTL 实现"同一用户同一商品短时间内只允许一次请求进入" |
| 7 | 库存 Key 为什么要用 `StringRedisTemplate`？ | Lua 脚本的 `tonumber()` 要求值存储为纯数字字符串，普通 `RedisTemplate` 的 `GenericJackson2JsonRedisSerializer` 会存成 JSON 格式导致解析失败 |
| 8 | 如果 Redis 宕机怎么办？ | 秒杀场景对可用性要求高，Redis 宕机时 Lua 执行直接失败返回库存不足。生产环境应部署 Redis Sentinel/Cluster 高可用，并配置降级开关关闭秒杀入口 |
| 9 | orderKey 的 value 为什么存 seckillNo 而不是 "1"？ | 前端轮询时需要用 seckillNo 查询秒杀结果和订单状态，如果存 "1" 则无法直接从 Redis 获取 seckillNo，需要额外查库 |
| 10 | 支付成功后为什么要释放 orderKey？ | 用户支付完成后限购次数已经消费，如果 orderKey 不释放，用户再次进入同场活动会被 orderKey 拦截提示"已在秒杀流程中"，导致无法再次购买 |
| 11 | Lua 脚本 vs MULTI/EXEC 事务 vs CAS，三种 Redis 并发控制怎么选？ | **Lua**：一次网络 RTT，原子执行，适合"预检+扣减"一体化（本项目秒杀）；**MULTI/EXEC**：乐观锁，WATCH 变量在事务提交前被修改则 ABORT，适合多 Key 协调但重试成本高；**CAS（INCRBY + 回退）**：无锁，冲突时性能下降。本项目选 Lua 因为需要"多步判断+多步修改"原子化，且不需要重试 |
| 12 | Redis Set 和 String+INCRBY 怎么选？ | **Set**适合"有/无"判断（如用户是否已购买，SISMEMBER O(1)）；**String+INCRBY**适合"多少个"计数（如库存扣减，INCRBY 原子性）。秒杀场景库存需要精确计数且要原子递减，所以选 String；限购判断用 Set 存已购用户 |
| 13 | Kafka 消息顺序能保证吗？ | 同一 partition 内有序。本项目 Outbox 按 aggregate_id 路由到同一 partition（`message_key = aggregate_id`），保证同一聚合的事件有序。跨 partition 无法保证全局有序，但 Flink Sink 的 upsert 操作天然幂等，乱序也只产生最终一致结果 |
| 14 | Redis Cluster 下 Lua 脚本跨节点怎么处理？ | Lua 脚本操作的所有 Key 必须在同一 slot。用 Hash Tag（`{activityId}` 写在 Key 名中）确保 stockKey 和 boughtCntKey 路由到同一节点。如果业务上无法保证同 slot，需拆分为两次 Redis 调用 + 客户端补偿 |
| 15 | 秒杀链路的监控指标有哪些？怎么设告警阈值？ | 核心指标：Lua 执行失败率（>1% 告警）、Kafka 消息积压量（>1000 告警）、消费者 lag（>30s 告警）、orderKey 超时未消费比例（>5% 告警）、Redis 内存使用率（>80% 告警）。Prometheus + Grafana 可视化 |
| 16 | 如果 Redis 内存满了，Lua 脚本还能执行吗？ | Redis 内存达到 maxmemory 后，写操作（DECRBY）会按淘汰策略拒绝。秒杀场景应配置 `noeviction` 策略（写满报错而非静默淘汰），并配置内存使用率 >80% 告警，提前扩容或清理过期 Key |

### 简历写入建议

- 设计并实现基于 Redis Lua + Kafka 的秒杀链路，将并发压力从 MySQL 转移至 Redis，支持多件限购与原子库存扣减，接口 RT 从 2s+ 降至 50ms 以内，零超卖事故

## 亮点二：Flink 实时数据管道——4 作业 Kafka→ES 同步矩阵

### 技术场景（Context）

**业务痛点**：课程、拼团活动、秒杀商品、工具 4 个业务域的数据需要实时同步到 ES 供搜索和聚合查询，直接查 MySQL 无法满足全文检索和复杂聚合的性能需求。

**技术选型**：采用 Apache Flink 作为流处理引擎，消费 Kafka Topic 写入 ES，利用 Flink 的 Checkpoint 机制保证 Exactly-Once 语义。

**架构位置**：`backstage-flink` 模块下 4 个独立 Job。

### 技术实现与亮点

**4 作业对比矩阵**（8 维度横向对比）：

| 维度 | Course | Group Activity | Seckill Item | Tool |
|---|---|---|---|---|
| Parallelism | config（默认 1） | 1 | 1 | config（默认 1） |
| **Checkpoint** | **EXACTLY_ONCE** | AT_LEAST_ONCE | AT_LEAST_ONCE | **EXACTLY_ONCE** |
| Kafka API | FlinkKafkaConsumer (deprecated) | **KafkaSource（新）** | FlinkKafkaConsumer (deprecated) | FlinkKafkaConsumer (deprecated) |
| **Offset 策略** | config | **latest（P0 风险!）** | config | config |
| **Restart Strategy** | fixedDelayRestart | **未设置（P1）** | **未设置（P1）** | fixedDelayRestart |
| RocksDB | 否 | 是 | 否 | 否 |
| 分流数 | 3（audit/upsert/delete） | 2（upsert/delete） | 2（upsert/delete） | 3（audit/upsert/delete） |
| 事件前缀 | `COURSE_INDEX_*` + `AUDIT_*` | `CREATE/UPDATE/DELETE`（裸） | `SECKILL_ITEM_INDEX_*` | `TOOL_INDEX_*` + `AUDIT_*` |

> **矩阵加粗项**为治理审查中发现的风险点，详见下方“6 类治理项”展开。

**核心实现**（`CourseSearchIndexSyncJob`）：

- **单 Topic 多路分流**：通过 `eventType` 将消息路由到 audit（审核状态 partial update）、upsert（全文索引）、delete（文档删除）三条 Sink 管道
- **Checkpoint 全链路配置**：`EXACTLY_ONCE` + 外部化 Checkpoint `RETAIN_ON_CANCELLATION` + 固定延迟重启策略
- **可检索状态过滤**：只有"已发布/待审核/已下架"三种状态的文档才进入搜索索引

**治理贡献**：通过配置矩阵横向对比发现 6 类治理项，按优先级分级推动修复：

| 级别 | 治理项 | 问题描述 | 修复方案 |
|---|---|---|---|
| **P0** | Group Offset 策略风险 | `OffsetsInitializer.latest()` 首次部署或 offset 过期时直接跳到最新，**永久丢失历史积压消息** | 改为 `committedOffsets(earliest)` |
| **P0** | Checkpoint 模式漂移 | Group/Seckill 用 AT_LEAST_ONCE，Course/Tool 用 EXACTLY_ONCE；重放顺序错乱可能导致"已结束"事件覆盖"进行中" | 统一 EXACTLY_ONCE 或业务层加 last-write-wins 版本号 |
| P1 | 2 作业未设 Restart Strategy | Group/Seckill 依赖集群默认值，ES 持续故障时静默挂掉无告警 | 显式 `fixedDelayRestart(3, 30000)` |
| P1 | 3 作业使用废弃 API | Course/Seckill/Tool 用 `FlinkKafkaConsumer`（Flink 1.14 已废弃），升级时编译失败 | 统一迁移到 `KafkaSource` API |
| P2 | 事件类型命名不统一 | Group 用裸 `CREATE/UPDATE/DELETE`，其他 3 个用 `业务域_*` 前缀，跨 Topic 可能干扰 | Group 改为 `GROUP_ACTIVITY_*` |
| P2 | 无 DLQ | 解析失败仅 `log.error` + 跳过，畸形消息静默消失 | 增加 DLQ Topic 供人工恢复 |

> **关联阅读**：Flink 内存调优实战（Task Heap 从 25.6MB 到 288MB）详见 [附录 I](#附录-iflink-内存调优实战task-heap-从-256mb-到-288mb-的调参之路)，包括四步调参法、压测验证、环境变量踩坑经验。

>
> **S**：项目有 4 个业务域的数据需要实时同步到 ES，每个域一个独立的 Flink 作业，但各作业在 Checkpoint 模式、Kafka API 版本、重启策略等方面存在不一致。
>
> **T**：负责维护这 4 个 Flink 作业，确保数据一致性和生产可靠性。
>
> **A**：首先建立配置对比矩阵，横向比较 4 个作业在 10 个维度上的差异，发现 6 类治理项。其中 P0 级问题包括：Group 作业的 Offset 策略用 `latest` 导致首次部署丢失全部历史消息、Checkpoint 模式不统一可能导致事件覆盖顺序错乱。推动统一为 `EXACTLY_ONCE` + `committedOffsets(earliest)`，并将 3 个使用废弃 `FlinkKafkaConsumer` 的作业迁移到新版 `KafkaSource` API。
>
> **R**：治理后 4 个作业在 Checkpoint 语义、API 版本、重启策略上完全统一，消除了首次部署丢消息的 P0 风险。

### 追问预判（深度扩展）

| # | 追问 | 应对思路 |
|---|---|---|
| 1 | 为什么 Course/Tool 用 EXACTLY_ONCE 而 Group 用 AT_LEAST_ONCE？ | 历史原因，不同时期开发。AT_LEAST_ONCE 在当前幂等 Sink（upsert by id）场景下近似安全，但新增"状态覆盖"场景时需重新评估 |
| 2 | 为什么用 Flink 而不是 Spring 监听 Kafka 直接写 ES？ | Flink 提供 Checkpoint 端到端一致性保证、背压机制、窗口聚合能力，且支持 RocksDB 增量 Checkpoint 应对大状态 |
| 3 | `RETAIN_ON_CANCELLATION` 是什么意思？ | Job 取消时保留 Checkpoint 数据，重启后可从上次 Checkpoint 恢复，避免数据丢失 |
| 4 | 为什么审核事件用 partial update 而不是全量覆盖？ | 审核状态变更只影响 status 字段，partial update 避免全量覆盖其他字段导致数据不一致，同时减少 ES 写入量 |
| 5 | DLQ（死信队列）为什么重要？ | 解析失败的消息如果直接丢弃，故障复盘时无法恢复现场。DLQ 保存原始消息供人工分析和重发 |
| 6 | Offset 策略用 `latest` 会有什么问题？ | 首次部署或 offset 过期时直接跳到最新消息，错过全部历史积压数据。应使用 `committedOffsets(earliest)`，首次从最早开始消费 |
| 7 | RocksDB StateBackend 和 HashMapStateBackend 有什么区别？ | HashMap 将状态存在 JVM 内存中，状态过大时 OOM；RocksDB 将状态持久化到磁盘，支持超大状态 + 增量 Checkpoint |
| 8 | 如何保证 ES Sink 的幂等性？ | 使用 ES 的 upsert API（`index` 操作），相同 id 的文档会被覆盖，天然幂等 |
| 9 | 6 类治理项的修复优先级怎么定的？ | P0 影响数据正确性（丢消息/顺序错乱），P1 影响可靠性（静默挂掉/编译失败），P2 影响可维护性（命名混乱/故障复盘困难） |
| 10 | 为什么废弃 API 要集中治理而不是逐个迁移？ | 3 个作业用废弃 API，逐个迁移要 3 个 PR、3 次回归测试。集中治理一次 PR 完成，减少后续升级时的临时抱佛脚风险 |
| 11 | AT_LEAST_ONCE + 幂等 Sink 真的安全吗？ | 当前场景下 upsert by id 近似安全。但如果未来新增"重新开团"场景（status=1 覆盖 status=3），重放乱序会导致已结束事件被覆盖，必须重新评估 |
| 12 | Kafka Consumer Group 的 rebalance 会影响数据同步吗？ | rebalance 期间消费者暂停拉取，但 Flink 的 Checkpoint 机制确保暂停前有状态快照。rebalance 完成后从上次 offset 恢复，不会丢数据。Group/Seckill 作业只有 1 个并行度，实际不会触发 rebalance |
| 13 | 4 个作业为什么要独立部署而不是合并成 1 个？ | 独立部署的优势：① 故障隔离（Course 作业 OOM 不影响 Tool 作业）；② 独立扩缩容（课程数据量最大，Course 作业可加并行度）；③ 独立 Checkpoint 周期（高频变更的课程需要更短的 Checkpoint 间隔） |
| 14 | 反压（Backpressure）怎么处理？ | Flink 原生支持反压：ES Sink 处理变慢 → Task 输出缓冲区满 → 上游自动降速。如果持续反压，说明 ES 集群性能不足或 Sink 批量写入未优化。本项目用 bulk upsert（批量 100 条或 5 秒刷新）减少 ES 写入次数 |
| 15 | 源表加字段/删字段后 Flink 作业怎么处理？ | Flink Kafka Source 反序列化时按 JSON 字段解析，新增字段会被忽略（不报错），删除字段会返回 null。但如果需要新字段入 ES，必须修改 Flink 作业代码重新部署。最佳实践是源表变更同步更新 Flink 作业的 Schema 定义 |
| 16 | 如果 Kafka Topic 的消息格式不统一怎么办？ | 单 Topic 多路分流架构（audit/upsert/delete）要求所有消息有统一的 `event_type` 字段做路由。格式不统一会导致反序列化失败进入 DLQ。解决：Outbox 写入时强制 JSON Schema 校验，不合规则拒绝写入 |
| 17 | ES 节点宕机后 Flink 作业会怎样？ | ES Sink 写入失败会被 catch，Checkpoint 提交失败，Flink 自动从上次成功 Checkpoint 重启恢复。RocksDB 增量 Checkpoint 保证恢复时只重传增量数据。如果 ES 持续不可用，作业会反复重启——需要告警通知人工介入 |

### 简历写入建议

- 维护 4 个 Flink 实时同步作业（Kafka→ES），建立配置矩阵横向对比发现 6 类治理项，推动统一 EXACTLY_ONCE 语义与 KafkaSource API 迁移
- 设计单 Topic 多路分流架构（audit/upsert/delete），配合 Checkpoint + RocksDB 增量快照保证端到端一致性

## 亮点三：Flink CEP 实时异常检测——刷单与高频取消识别

### 技术场景（Context）

**业务痛点**：拼团活动上线后存在恶意刷单和高频取消行为，传统基于数据库的离线分析无法做到实时告警。

**技术选型**：采用 Flink CEP（Complex Event Processing）库，在事件流上定义模式匹配规则，实现毫秒级异常检测。

**架构位置**：`GroupAnomalyDetectionJob`。

### 技术实现与亮点

**两条 CEP 规则**：

| 规则 | 条件 | 模式定义 |
|---|---|---|
| 疑似刷单 | 同一用户 5 分钟内 3+ 笔 GROUP_JOIN | `Pattern.begin("first_order").timesOrMore(3).within(5min)` |
| 高频取消 | 同一用户 10 分钟内 2+ 笔 ORDER_CANCELLED | `Pattern.begin("first_cancel").timesOrMore(2).within(10min)` |

**亮点**：
- `keyBy(userId)` 将同一用户事件路由到同一并行子任务，保证模式匹配准确性
- RocksDB StateBackend + 增量 Checkpoint 应对大量用户并行模式匹配的状态压力
- 检测到异常后输出结构化告警日志（含 userId、orderNos），可对接钉钉/企微

### 面试回答话术（STAR）

> **Hook**："运营说有用户刷单但抓不到证据——我用 2 条 Flink CEP 模式规则，把异常检测从'事后分析'变成了'秒级实时告警'。"
>
> **S**：拼团活动上线后运营反馈有疑似刷单行为，但事后分析无法及时止损。
>
> **T**：需要一套实时异常检测系统，在用户行为发生的秒级内识别告警。
>
> **A**：选用 Flink CEP 库定义两条模式规则——"5 分钟内同用户 3+ 笔下单"和"10 分钟内同用户 2+ 笔取消"。通过 `keyBy(userId)` 保证同一用户的事件序列有序，使用 RocksDB 作为 StateBackend 应对大量用户并行模式匹配的状态压力。检测到异常后输出结构化告警。
>
> **R**：实现拼团异常的秒级检测，运营可在用户持续刷单过程中介入干预，止损时效从小时级降到分钟级。

### 追问预判（深度扩展）

| # | 追问 | 应对思路 |
|---|---|---|
| 1 | CEP 和简单的滑动窗口计数有什么区别？ | 窗口计数只能统计数量，CEP 能匹配复杂事件序列模式（如"A 之后 5 分钟内出现 B"），更灵活 |
| 2 | 如果用户刷单间隔刚好在窗口边缘怎么办？ | `within(Time.milliseconds())` 使用滑动时间窗口，从第一条匹配事件开始计时，而非固定时间窗口 |
| 3 | 如何调整阈值？ | 阈值定义为常量（`FRAUD_ORDER_THRESHOLD=3`），调整只需改常量值。生产环境可抽取为配置文件 |
| 4 | 如何对接告警通知？ | 当前输出 `log.warn` 结构化日志，可接入 Logstash/Alertmanager 触发钉钉机器人或企微通知 |
| 5 | 如何扩展更多检测规则？ | 新建 `Pattern` + `PatternStream`，复用同一 `orderStream`，每条规则独立告警 |
| 6 | `timesOrMore` 和 `times` 的区别？ | `times(3)` 精确匹配 3 次，`timesOrMore(3)` 匹配 3 次及以上，更适合"超过阈值就告警"的场景 |
| 7 | Flink CEP 的状态后端怎么选？ | 拼团场景用户并发模式匹配的状态较大，用 RocksDB StateBackend + 增量 Checkpoint，将状态持久化到磁盘，避免 JVM 堆 OOM。小状态场景可用 HashMapStateBackend（纯内存） |
| 8 | CEP 检测到异常后怎么处理？ | 当前输出结构化日志 `log.warn("[CEP][FRAUD]")` 包含用户 ID、订单号、检测规则名。生产环境可对接 Logstash → Alertmanager → 钉钉机器人/企微通知，实现秒级告警 |
| 9 | 如果同时有多条 CEP 规则，性能会受影响吗？ | 每条规则创建独立的 PatternStream，共享同一 orderStream（通过 `orderStream.broadcast()` 分发）。Flink 内部并行处理，单条规则异常不影响其他规则 |

- 采用 RocksDB StateBackend + 增量 Checkpoint 支撑大量用户并行模式匹配的状态压力

## 亮点四：Outbox Pattern 事件可靠投递——事务后回调 + 定时兜底

### 技术场景（Context）

**业务痛点**：课程/工具/秒杀等业务操作需要同步更新 ES 搜索索引，但直接在同一事务中发 Kafka 消息会导致"消息发了但事务回滚"或"事务提交但消息发送失败"的不一致问题。

**技术选型**：采用 Transactional Outbox 模式——事件先写入本地 Outbox 表（与业务操作同库同事务），事务提交后再投递到 Kafka，投递失败由定时任务兜底重发。

**架构位置**：`OutboxEventServiceImpl`。

### 技术实现与亮点

```
业务操作 → INSERT osh_outbox_event（同事务）→ 事务提交后 afterCommit() → 投递 Kafka
                                                    ↓ 投递失败
                                              定时任务扫描 PENDING 事件 → 重试（最多 10 次）
```

- **事务同步回调**：`TransactionSynchronizationManager.registerSynchronization(afterCommit)` 确保只在事务成功提交后才投递
- **双模式投递**：有事务上下文走 `afterCommit`；无事务上下文直接投递（兼容非事务场景）
- **安全降级**：投递失败仅 `log.warn`，不抛异常不影响业务，定时任务兜底重发
- **多域路由**：统一 `saveEvent()` 按 `aggregateType`（COURSE/TOOL/SECKILL）路由到不同 Kafka Topic
- **完整事件表**：`event_id/aggregate_type/aggregate_id/event_type/topic/message_key/payload/status/retry_count/max_retry_count/next_retry_time/last_error/sent_time`

**域外对比——GROUP 域为什么不用 Outbox？**

拼团模块（`GroupEventPublisher`）采用轻量级“事务提交后回调”模式：`OshGroupServerServiceImpl.publishAfterCommit()` + 直接 Kafka 发送，**不经过 Outbox 表**。原因是：

| 对比维度 | Outbox Pattern（课程/工具/秒杀） | 轻量级 afterCommit（拼团） |
|---|---|---|
| 可靠性要求 | ES 索引必须与 DB 最终一致，丢失事件会导致搜索结果错误 | 事件用于监控/CEP 异常检测，丢失不影响核心业务 |
| 兜底能力 | 定时任务扫描 PENDING 事件重发（最多 10 次） | 无兜底，发送失败仅 `log.warn` |
| 实现复杂度 | 写 Outbox 表 + afterCommit + 定时扫描 | 仅 afterCommit + 直接发送 |
| 设计取舍 | 重量级但 100% 可靠投递 | 轻量级但接受极端情况丢失 |

> **面试应对**：被追问“拼团为什么不用 Outbox”时，回答“事件用途不同——ES 索引同步要求 100% 可靠投递，拼团事件用于监控告警，丢失不影响核心业务，因此选择更轻量的方案”。

### 面试回答话术（STAR）

> **Hook**："分布式事务最容易出问题的不是'事务失败怎么办'，而是'事务成功了但消息发不出去'——我用一张 Outbox 表 + 定时兜底任务做到了 100% 可靠投递。"
>
> **S**：课程发布后需要更新 ES 搜索索引，但直接在事务中发 Kafka 消息会出现不一致。
>
> **T**：需要保证"数据库操作"和"Kafka 消息发送"的最终一致性。
>
> **A**：实现 Transactional Outbox 模式——在业务表中插入 Outbox 事件记录，与业务操作共用同一个本地事务。利用 Spring 的 `TransactionSynchronization.afterCommit()` 回调，确保只在事务成功提交后才投递 Kafka。投递失败不影响业务，由 Quartz 定时任务扫描 PENDING 状态的事件进行兜底重发，最多重试 10 次。
>
> **R**：彻底解决了"消息与数据库不一致"问题，Outbox 表同时作为审计日志使用，覆盖 3 个业务域。

| # | 追问 | 应对思路 |
|---|---|---|
| 1 | 为什么不用 Seata 分布式事务？ | Outbox 用最终一致性即可满足搜索索引同步场景，成本远低于强一致性方案 |

| 4 | 消费端如何保证幂等？ | ES Sink 使用 upsert（相同 id 覆盖），天然幂等；如果业务需要，可在消费端用唯一 event_id 去重 |
| 5 | 为什么 `afterCommit` 而不是 `beforeCommit`？ | `beforeCommit` 时事务还没提交，消费端可能读到未提交数据（脏读）。`afterCommit` 保证数据已持久化 |
| 6 | 如何处理"事务提交成功但 afterCommit 投递前进程崩溃"？ | Outbox 事件已经持久化到数据库，定时任务会扫描到并重试投递，最终一致性得到保证 |
| 7 | 重试策略是怎样的？ | `retry_count` 递增，`max_retry_count=10`，`next_retry_time` 按指数退避计算，超过上限的事件标记为 FAILED |
| 8 | 拼团模块为什么不用 Outbox？ | 拼团事件（参团/支付/成团）用于监控告警和 CEP 异常检测，丢失不影响核心业务；而课程/工具/秒杀的 ES 索引同步要求 100% 可靠投递。根据事件可靠性需求分级选择方案，避免过度设计 |
| 9 | Outbox 表的 `aggregate_type` 怎么路由到不同 Topic？ | `OutboxEventServiceImpl` 提供类型化 save 方法（`saveCourseIndex`/`saveToolIndex`/`saveSeckillItemIndex`），每个方法硬编码 aggregate_type + topic 的映射。消费端按 topic 独立消费，互不干扰 |
| 10 | 重试策略中的指数退避怎么实现的？ | `next_retry_time = NOW() + base_delay * 2^retry_count`。retry_count=0 时等待 10s，=1 时 20s，=2 时 40s…避免密集重试压垂下游。超过 max_retry_count=10 的事件标记 FAILED，人工介入 |
| 11 | 为什么不在事务内直接发 Kafka 而要写 Outbox 表？ | 事务内发 Kafka 存在"双写不一致"风险：Kafka 发送成功但事务回滚（消息已发无法撤回），或事务提交但 Kafka 发送失败（消息丢失）。Outbox 把消息持久化到同一数据库事务，保证原子性 |

### 简历写入建议

- 实现 Transactional Outbox 模式保证 MySQL→Kafka 事件可靠投递，利用事务 afterCommit 回调 + 定时兜底重发实现最终一致性，覆盖 3 个业务域
- 设计统一 Outbox 事件表（含完整重试模型），支持多域路由、重试计数、最大重试次数限制，投递失败不阻塞业务流程

## 亮点五：声明式分布式锁 @DistributeLock——注解 + AOP + SpEL

### 技术场景（Context）

**业务痛点**：课程保存/更新、拼团参团、网站评分提交等操作存在并发写冲突风险，需要在方法级别快速接入分布式锁保护。

**架构位置**：`@DistributeLock` 注解 + `DistributeLockAspect` 切面。

### 技术实现与亮点

**五属性注解设计**：

| 属性 | 作用 | 示例 |
|---|---|---|
| `scene` | 锁场景 | `group_join`、`course` |
| `key` / `keyExpression` | 静态 Key 或 SpEL 表达式 | `#activityId` |
| `includeUserId` | Key 中拼接用户 ID | 控制锁粒度 |
| `waitTime` / `expireTime` | 等待/过期时间（ms） | `0` / `15000` |
| `releaseImmediately` | 是否立即释放 | `false` 用于秒杀场景 |

**双分支加锁逻辑**：
- `waitTime == DEFAULT` → `rLock.lock()`（阻塞等待 + WatchDog 自动续期）
- `waitTime != DEFAULT` → `tryLock(waitTime, expireTime, MILLISECONDS)`（限时等待 + 固定 TTL）

**锁 Key 规范**：`scene#user:{userId}#key` 或 `scene#key`

#### 拼团并发安全实战：分布式锁 + CAS 双层防线

拼团模块（`OshGroupServerServiceImpl`，2497 行）是项目中并发控制最复杂的模块，采用“**声明式锁 + 编程式锁 + CAS**”三层防线，**双模式并存**：

- **声明式 `@DistributeLock`**：拼团 join 接口（L703 `@DistributeLock(scene="group_join", keyExpression="#activityId", waitTime=3000, expireTime=15000)`）——注解即接入，适合通用场景
- **编程式 `RLock.tryLock`**：支付回调入口——需要精细控制（CAS 失败返回 false 而非抛异常），注解无法满足

**第一层——Redisson 分布式锁（串行化回调）**：
```java
// 支付回调入口：按活动 ID 加锁，串行化同一活动的所有并发回调
String lockKey = LOCK_GROUP_PAY_CALLBACK_PREFIX + activityId;
RLock lock = redissonClient.getLock(lockKey);
boolean acquired = lock.tryLock(5, 15, TimeUnit.SECONDS);  // 等5s、持锁15s
```

**第二层——CAS 原子递增（DB 级防超卖）**：
```sql
-- OshGroupServerMapper.xml：系统活动 CAS 递增
UPDATE osh_group_activity SET current_num = current_num + 1
WHERE id = #{id} AND current_num < group_max_num

-- OshGroupUserInitiatedMapper.xml：用户发起拼团 CAS 递增
UPDATE osh_group_user_initiated SET current_num = current_num + 1
WHERE id = #{id} AND current_num < max_num AND delete_flag = 0
```

**关键设计决策**：

| 决策点 | 方案 | 理由 |
|---|---|---|
| `join` 时是否递增 `currentNum`？ | **否**，延迟到支付成功回调 | 防止"join 了但没付款就占名额"的虚假超卖 |
| CAS 失败抛异常还是返回 false？ | **返回 false**，不抛 `ServiceException` | 抛异常会触发 `@Transactional` 整体回滚，导致已支付的订单状态丢失 |
| CAS 成功后如何判断成团？ | 重新 `selectById` 读取最新 `currentNum` | CAS 递增和成团判断之间可能有其他并发回调到达 |
| 成团后如何同步成员状态？ | `batchUpdateWorkStatusByInitiatedId` 批量更新 | 一次 SQL 更新所有已支付成员的 `groupStatus`（0→2）和服务器时间 |
| 对账任务如何防止覆盖并发递增？ | `updateActivityCurrentNumIfMatch` CAS 条件更新 | `WHERE current_num = #{expectedNum}`，若期间有支付回调递增则跳过 |

**双状态码独立映射**：

| 表 | 状态值 | 含义 |
|---|---|---|
| `osh_group_work.group_status` | 0→1→2/3 | 待支付→已支付→已成团/已结束 |
| `osh_group_user_initiated.group_status` | 0→1→2 | 招募中→已成团→已结束 |

**枚举常量化**：`GroupStatusEnum`、`GroupOrderStatusEnum`、`GroupConstants`（35 个常量）替代 54+ 处魔法值，消除"状态 0 到底是待支付还是招募中"的歧义。

### 面试回答话术（STAR）

> **Hook**："我设计了一个 @DistributeLock 注解，8 个业务模块一行配置就能接入分布式锁——但最复杂的拼团支付回调场景，光靠锁不够，我额外加了 CAS 做 DB 级兜底。"
>
> **S**：项目中多个业务模块需要分布式锁保护并发操作，其中拼团模块（2497 行 Service）的并发控制最为复杂——多个支付回调可能同时到达同一活动，既要防超卖又要保证成团判断准确。
>
> **T**：需要一套标准化的分布式锁接入方式，同时解决拼团场景"锁 + CAS 双层防线"的复杂需求。

| # | 追问 | 应对思路 |

| 1 | `waitTime=0` 和 `waitTime=DEFAULT` 的区别？ | `waitTime=0` 不排队等锁，抢不到立即失败，适合快速失败场景；`DEFAULT` 阻塞等待直到获锁或超时 |

| 4 | Redisson 的 WatchDog 机制是什么？ | 不设置 expireTime 时，WatchDog 每 10s 自动续期 30s，防止业务未完成锁已过期 |
| 5 | 如果 Redis 宕机锁会怎样？ | Redisson 基于 Redis 主从/哨兵实现分布式锁，Redis 宕机时获锁失败抛异常，业务降级处理 |
| 6 | 和 `synchronized` 有什么区别？ | `synchronized` 只能锁单机，分布式环境多台机器同时执行时无法串行化。分布式锁基于 Redis 实现跨 JVM 互斥 |

| 8 | 拼团支付回调为什么要分布式锁 + CAS 双层？ | 分布式锁串行化同一活动的并发回调（防竞态），CAS 是 DB 级兜底（防锁失效时超卖）。单靠锁有 Redis 宕机丢锁风险，单靠 CAS 在高冲突下大量失败重试效率低 |
| 9 | CAS 失败为什么不抛 `ServiceException`？ | CAS 失败发生在 `@Transactional` 事务内，抛异常会触发整体回滚——已支付的订单状态（`pending→paid`）也会被回滚，导致用户已扣款但本地订单退回待支付。正确做法是返回 false，调用方差异化处理 |
| 10 | `join` 时不递增 `currentNum` 会不会有人数不准的问题？ | join 时只创建待支付订单和参团记录，`currentNum` 严格等于"已支付人数"。未支付订单由定时任务兜底取消。定时对账任务用 CAS 条件更新（`WHERE current_num = expectedNum`）校正，不会覆盖并发递增 |
| 11 | 双状态码体系有什么好处？ | `group_work`（单用户视角：待支付→已支付→已成团）和 `group_user_initiated`（活动视角：招募中→已成团→已结束）独立映射，解耦用户状态和活动状态。避免"用户已支付但活动还没成团"时状态冲突 |
| 12 | 项目的线程池怎么配的？为什么这样配？ | `ThreadPoolConfig` 配置 3 个命名线程池：DEFAULT（通用异步）、AGGREGATION（聚合统计）、NOTIFICATION（通知推送），每个用 `ThreadPoolTaskExecutor` 显式设置核心/最大线程数和队列容量。拒绝策略统一用 `CallerRunsPolicy`（不丢弃任务，由调用线程执行） |

| 14 | AOP 自调用为什么会失效？怎么解决？ | Spring AOP 基于代理实现，`this.method()` 调用的是原始对象而非代理，注解不生效。项目用 `@Lazy` 自注入解决：`@Lazy @Autowired private XxxService self;` 注入代理对象，通过 `self.method()` 调用使 AOP 生效。`@Lazy` 防止循环依赖导致启动报错 |
| 15 | Redisson RedLock 了解吗？为什么不用？ | RedLock 在多个独立 Redis 节点上加锁，超过半数成功才认为获锁。Martin Kleppmann 指出其依赖时钟同步假设，存在安全隐患。本项目用 Redis Cluster（单集群），WatchDog 续期足够可靠，不需要 RedLock 的复杂度 |
| 16 | 锁的过期时间设置不合理会怎样？ | 太短：业务未完成锁已过期，另一个线程进入临界区导致竞态。太长：持锁进程崩溃后锁长时间不释放，其他线程等待。解决：不设置 expireTime 时用 WatchDog 自动续期（每 10s 续 30s），设置 expireTime 时根据业务 RT 估算上限（如 15s） |
| 17 | 分布式锁和数据库行锁怎么选？ | 分布式锁（Redisson）适合"快速失败"场景（秒杀、拼团 join），不获锁立即返回。数据库行锁（FOR UPDATE）适合"必须串行"场景（支付回调会员续期），事务内天然串行化。两者不互斥——拼团支付回调用分布式锁 + CAS 双层 |

- 基于 Redisson + AOP 实现声明式分布式锁注解 `@DistributeLock`，支持 SpEL 动态 Key、用户维度锁粒度、双分支加锁策略，已在 8 个业务模块接入
- 设计拼团并发安全"双层防线"：Redisson 分布式锁串行化支付回调 + SQL 级 CAS 原子递增防超卖，配合延迟递增策略（join 不计数、支付后才递增）和对账任务 CAS 条件更新

## 亮点六：支付回调幂等发放——三重闸门 + 双状态分离范式

### 技术场景（Context）

**业务痛点**：支付平台回调可能重复发送，如果权益发放不幂等，会导致用户会员时长被重复累加。同时"支付成功"和"权益发放"是两个独立步骤，需要分别追踪状态。

**架构位置**：`MemberEntitlementServiceImpl`。

### 技术实现与亮点

**标准范式三步骤**：

1. **行锁串行化**：`selectByOrderNoForUpdate` 锁住订单行 + `selectRoleExpireForUpdate` 锁住权益行
2. **幂等守卫**：`grant_status == SUCCESS` 直接短路返回
3. **upsert 幂等续期**：`ON DUPLICATE KEY UPDATE` 刷新过期时间

**双状态分离**：`pay_status`（支付）与 `grant_status`（发放）独立，`grant_message` 记录发放失败原因。

**跨模块验证**：已在秒杀、会员中心、工具套餐、核销码、电子书 5 个模块验证通过。

### 面试回答话术（STAR）

> **Hook**："支付平台的回调被重复发了 3 次，但用户只收到了一次权益——我用 FOR UPDATE + 状态短路 + upsert 三道闸门挡住了所有重复。"
>
> **S**：支付平台回调存在重复发送的可能，会员权益发放必须保证幂等性。
>
> **T**：设计一套支付回调幂等发放机制，覆盖多个资金链路模块。
>
> **A**：设计了"三重闸门"范式：`SELECT ... FOR UPDATE` 行锁串行化同一订单的并发回调；`grant_status` 已发放直接短路返回实现幂等守卫；`upsertUserRole` 用 `ON DUPLICATE KEY UPDATE` 保证重复回调只续期不重复计数。同时把 `pay_status` 和 `grant_status` 分离为两个独立状态字段。
>
> **R**：已在 5 个资金链路模块验证通过，上线以来零重复发放事故。

### 追问预判（深度扩展）

| # | 追问 | 应对思路 |
|---|---|---|
| 1 | `FOR UPDATE` 会不会导致死锁？ | 每个回调按 orderNo 串行化，锁的是不同订单行，不会交叉锁。如果同一订单的两次回调同时到达，MySQL 行锁天然串行 |
| 2 | 为什么用 `ON DUPLICATE KEY UPDATE` 而不是先查再更新？ | "先查再更新"有并发竞态窗口，`ON DUPLICATE KEY UPDATE` 是 MySQL 原子操作，避免并发续期时间计算错误 |
| 3 | 续期起点为什么取"已有有效期和当前时间取较晚者"？ | 如果用户当前会员还没过期，新购的时长应该从现有过期时间开始累加（叠加），而非从当前时间覆盖 |
| 4 | `grant_status` 和 `pay_status` 为什么分开？ | 支付成功是第三方支付平台的确认，权益发放是我们内部的操作。支付成功但发放失败时，可以通过 `grant_message` 定位问题并人工补发 |
| 5 | 电子书的幂等方案和会员有什么不同？ | 电子书是"一次性购买"，用 `purchased==1` 短路返回即可。会员是"续期型"，需要 upsert 累加时长 |
| 6 | 核销码的幂等怎么做？ | `FOR UPDATE` 锁住核销码行 + `markRedeemed` 原子更新（CAS 风格），`redeemed=1` 即短路 |
| 7 | 支付回调的 Handler 注册表模式是什么？ | `OrderPaidHandlerRegistry` 用 Map 存储 bizType→Handler 映射。支付成功后按 productType（course/book/seckill/tool/group/member/bundle）路由到对应 Handler。新增业务只需实现 `OrderPaidHandler` 接口并注册，无需修改调度代码——符合开闭原则 |
| 8 | `updatePendingToSuccess` 的 CAS 和 `FOR UPDATE` 是什么关系？ | 它们是不同层级的幂等保障：CAS（`WHERE status='pending'` 的 affected rows）是"状态推进"层，保证同一订单只被推进一次；`FOR UPDATE` 是"权益发放"层，串行化同一用户的会员续期计算。两者在同一事务内协同，CAS 在前（快速短路），FOR UPDATE 在后（精确计算） |
| 9 | 如果 Handler 执行失败会怎样？ | 事务回滚，订单保持 pending 状态。支付平台会重试回调（微信 8 次、支付宝 3 次），每次重试都走完整的三重闸门流程。如果持续失败，定时主动查单任务兜底触发 |
| 10 | 支付平台回调服务器挂了怎么办？ | 支付平台有重试机制（微信 15s/30s/3m/10m/20m/30m 共 8 次），每次重试都走完整三重闸门。CAS 幂等闸门保证重复回调不重复发放。全部重试失败后定时主动查单任务兜底触发 |
| 11 | 支付回调中的金额校验怎么做？ | 回调金额与订单金额比对，不一致则拒绝并告警。单位转换用 `BigDecimal.divide(100, HALF_UP)` 避免浮点精度丢失 |
| 12 | 如何测试支付回调的幂等性？ | 单元测试模拟同一回调调用两次：第一次 verify 状态推进成功；第二次 verify 幂等短路，用 `verify(never)` 断言权益发放未被重复调用 |

### 简历写入建议

- 设计支付回调幂等发放"三重闸门"范式（FOR UPDATE 行锁 + grant_status 幂等守卫 + upsert 续期），双状态字段分离支付与发放，覆盖 5 个资金链路模块
- 实现 `ON DUPLICATE KEY UPDATE` 续期逻辑，重复回调只刷新过期时间不重复计数，上线零重复发放事故

## 亮点七：ES 优先 + MySQL 兜底的多级降级搜索架构

### 技术场景（Context）

**业务痛点**：课程、工具、电子书、信息差等模块的搜索依赖 ES，但 ES 集群不可用时不能影响用户体验。

**技术方案**：采用"ES 优先 + MySQL 兜底"双引擎策略，通过 `SearchEsProperties.enabled` 开关控制。

### 技术实现与亮点

**Controller 层降级**（以 `OshToolController` 为例）：

if (searchEsProperties.isEnabled()) {

## 亮点八：首页卡片 ES 双索引别名零停机切换

### 技术场景（Context）

**业务痛点**：首页卡片数据需要同步到 ES，但全量重建索引期间如果直接写入正在使用的索引，会导致搜索到中间状态的数据。

**技术方案**：A/B 双索引 + 别名切换策略。

### 技术实现与亮点

**同步流程**（`AbstractOshHomePageEsCardService.syncToEs()`）：

1. 解析当前别名指向的索引（`resolveCurrentAliasIndex`）
2. 计算目标索引名（A→B 或 B→A）
3. 创建目标索引 + 写入全量数据（`bulkUpsert`）
4. 校验目标索引数据量与 batchId（`validateIndex`）
5. 原子切换别名（`switchAlias`）

**亮点**：
- **batchId 溯源**：每次同步生成时间戳 batchId，写入 ES 文档的 `syncBatchId` 字段
- **启动自检**：`ensureIndexReady()` 在 `afterPropertiesSet` 中检测，缺失则自动触发全量同步
- **异常安全**：同步失败抛异常但不影响在线索引，读请求继续走旧别名

### 面试回答话术（STAR）

> **Hook**："全量重建索引需要 20 分钟，但这 20 分钟里搜索服务一秒都没停——秘诀是 A/B 双索引 + 别名原子切换。"
>
> **S**：首页卡片数据需要同步到 ES，全量重建时不能影响在线搜索。
>
> **T**：设计零停机的索引重建方案。
>
> **A**：采用 A/B 双索引 + 别名切换。维护一个 ES 别名指向当前在线索引，重建时写入另一个索引，写入完成后校验数据量和批次 ID，验证通过后原子切换别名。整个切换过程对读请求透明。
>
> **R**：实现 ES 索引全量重建的零停机切换，搜索服务无感知。

### 追问预判（深度扩展）

| # | 追问 | 应对思路 |

| 2 | batchId 怎么校验？ | 写入时每个文档带 `syncBatchId`，切换前统计目标索引中 `batchId` 匹配的文档数是否等于预期数量 |

## 亮点九：C 端等级权限体系——自定义注解 + 实时角色刷新

### 技术场景（Context）

**业务痛点**：项目有 B 端管理员和 C 端用户双体系，C 端用户有等级（普通/VIP/小班/创始人），直接复用 B 端的 `@PreAuthorize` 会导致 C 端接口被误拦 403。

**架构位置**：`@OshUserLevel` 注解 + `OshUserLevelAspect`。

### 技术实现与亮点

**核心设计**：

- `@OshUserLevel(value=2)` 标注接口所需最低等级
- AOP 切面从 `ThreadLocal` 获取当前用户等级
- `@Anonymous` 注解标记匿名可访问接口
- VIP/小班角色带有效期，每次请求校验有效期，过期自动降级
- 多角色用户取全部角色权限并集，避免只查单角色误拦

### 面试回答话术（STAR）

> **Hook**："C 端用户一访问就 403——因为他们被迫套用了 B 端的 Spring Security 权限。我设计了一套完全独立的自定义注解 + AOP 权限体系，从注解到切面到 ThreadLocal 全部独立。"
>
> **S**：项目 C 端有四级用户等级体系，原来混用 B 端 `@PreAuthorize` 导致 C 端用户频繁 403。
>
> **T**：设计一套独立的 C 端等级权限体系，与 B 端完全解耦。
>
> **A**：设计了 `@OshUserLevel` 自定义注解 + AOP 切面，从登录时写入 ThreadLocal 的 Redis 会话中获取等级信息，在方法执行前校验。配合 `@Anonymous` 注解、角色有效期校验、多角色并集判断等机制。
>
> **R**：彻底解决了 C/B 端权限混用导致的 403 问题。

## 附录 B：每个亮点的“连环追问”深度演练

> 面试官往往不会只问一个问题，而是沿同一话题连续追问。以下是每个亮点最可能的 3-5 层"连环追问"路径及应对。

### 亮点一：秒杀链路——连环追问

**第 1 层**：你的秒杀方案是怎么做的？
→ 回答 STAR 话术（Lua 预检 + Kafka 异步落库 + 定时兜底）

**第 2 层**：Lua 脚本里具体做了哪些操作？为什么要放在一个脚本里？
→ 两个 Key（库存 + 已购数）必须在同一次 Redis 调用中原子完成，如果分两次调用，并发场景下"扣了库存但限购没拦住"会导致超卖

**第 3 层**：如果 Lua 执行成功但 Kafka 发送失败怎么办？
→ Lua 成功后会写 orderKey（TTL 2min），Kafka 发送在 orderKey 写入之后。如果 Kafka 失败，orderKey 2 分钟后过期，用户可重试。同时 submitLockKey 防重复提交

**第 4 层**：消费者处理失败怎么处理？Redis 怎么回滚？
→ 消费者捕获异常后执行 Lua 归还脚本：`incrby stockKey quantity` + `decrby boughtCntKey quantity` + `del orderKey`。归还脚本同样加 `math.min` 边界，防止归还后超过 totalStock

**第 5 层**：你说的"定时任务兜底取消"具体怎么实现？
→ Quartz 每分钟扫描 `status=0`（未支付）且 `pay_expire_time` 已过期的订单，执行 Lua 回滚脚本（带上限防止超还），同步减已购数，更新订单状态为已取消

**第 6 层**：如果 Redis 和 DB 的库存最终不一致怎么办？
→ DB 是最终一致源。Redis 库存只做"快速失败"预检，DB 的 `decrStock` 用 `WHERE available_stock >= quantity` 做最终闸门。即使 Redis 扣了但 DB 扣失败，订单不会生成，定时任务会补偿 Redis

### 亮点二：Flink 同步矩阵——连环追问

**第 1 层**：为什么选择 Flink 而不是 Spring + Kafka 直接写 ES？
→ Flink 提供 Checkpoint 端到端一致性、背压、窗口聚合、RocksDB 大状态支持，Spring 监听器无法保证这些

**第 2 层**：4 个作业之间有什么差异？你是怎么发现的？
→ 建立 10 维度配置矩阵横向对比，发现 6 类治理项。重点是 Checkpoint 模式漂移和 Offset 策略风险

**第 3 层**：Checkpoint 模式漂移具体会导致什么问题？
→ AT_LEAST_ONCE 下如果 Kafka 重放消息且顺序与原始顺序不同，后到的"已结束"事件可能覆盖"进行中"事件。解决方案是统一 EXACTLY_ONCE 或在业务层加 last-write-wins 版本号

**第 4 层**：你做了哪些修复？效果如何？
→ 推动统一 EXACTLY_ONCE、`committedOffsets(earliest)` 替代 `latest`、3 个废弃 API 迁移到 KafkaSource、2 个缺失重启策略的显式配置

**第 5 层**：如果未来新增一个业务域需要同步到 ES，你会怎么做？
→ 参考 GroupActivityIndexSyncJob（最新 API + EXACTLY_ONCE + 重启策略），新建 Job 类 + Config + SinkFactory，确保符合配置矩阵的统一规范

### 亮点三：CEP 异常检测——连环追问

**第 1 层**：CEP 和窗口聚合有什么区别？
→ 窗口聚合只能统计数量，CEP 能匹配复杂事件序列模式（如"A 之后 5 分钟内出现 B 次"）

**第 2 层**：如果阈值设得太低会误报怎么办？
→ 当前阈值可配置，误报只输出 `log.warn` 不影响业务流程。生产环境可加"告警疲劳"机制——同一用户同一规则 5 分钟内只告警一次

**第 3 层**：如果要增加"同一用户先下单后取消再下单"的复杂模式怎么做？
→ 用 `Pattern.begin("order").next("cancel").followedBy("order_again")` 定义多阶段序列，CEP 天然支持

**第 4 层**：RocksDB StateBackend 为什么比 HashMap 更适合这个场景？
→ CEP 需要维护每个用户时间窗口内的事件序列，用户量大时状态可能达到 GB 级。HashMap 在 JVM 堆内会 OOM，RocksDB 持久化到磁盘 + 支持增量 Checkpoint

### 亮点四：Outbox Pattern——连环追问

**第 1 层**：为什么不直接发 Kafka？
→ 直接发 Kafka 存在"消息发了事务回滚"和"事务提交消息发送失败"两种不一致。Outbox 保证最终一致性

**第 2 层**：事务提交后投递 Kafka 前进程崩溃了怎么办？
→ Outbox 事件已持久化到数据库（status=PENDING），定时任务会扫描到并重试投递

**第 3 层**：消费端怎么保证幂等？
→ ES Sink 使用 upsert（相同 id 覆盖），天然幂等；业务端可用 event_id 去重

**第 4 层**：如果 Outbox 投递的消息顺序和原始写入顺序不一致怎么办？
→ 同一 aggregate（如 course:123）的消息按 id 顺序处理。ES 的 upsert 是 last-write-wins，如果乱序需要业务层加 updateTime 版本号

**第 5 层**：Outbox 表的性能影响？
→ 每次业务写入多一条 INSERT，但同库同事务开销极小。Outbox 表索引优化：`(status, next_retry_time)` 联合索引支撑定时任务扫描

### 亮点五：分布式锁——连环追问

**第 1 层**：和 synchronized 什么区别？
→ `synchronized` 只能锁单机，分布式环境多台机器无法串行化

**第 2 层**：Redisson 的 WatchDog 怎么工作？
→ 不设置 expireTime 时，WatchDog 每 10s 自动续期 30s，持锁线程崩溃后 WatchDog 停止续期，30s 后锁自动释放

**第 3 层**：如果 Redis 主节点宕机，锁数据丢失了怎么办？
→ 这是 Redis 分布式锁的已知缺陷。解决方案：使用 RedLock（多节点）或接受短暂不一致（业务层有 DB 兜底）。本项目选择接受短暂不一致 + DB 兜底

**第 4 层**：`waitTime=0` 的快速失败场景和排队等待哪个更好？
→ 取决于业务。秒杀用 `waitTime=0`（快速失败避免堆积），课程保存用 `waitTime>0`（排队等待保证串行化）。一刀切是不对的

**第 5 层**：如何避免锁 Key 冲突？
→ `scene + #user:{userId} + #key` 三段拼接，scene 隔离业务域，userId 隔离用户，key 隔离资源。不同业务、不同用户、不同资源的锁互不干扰

### 亮点六：幂等发放——连环追问

**第 1 层**：`FOR UPDATE` 和 `FOR SHARE` 有什么区别？
→ `FOR UPDATE` 排他锁，其他事务不能读也不能写；`FOR SHARE` 共享锁，其他事务可以读但不能写。回调处理需要排他锁防并发

**第 2 层**：如果 `FOR UPDATE` 等待太久怎么办？
→ InnoDB 的 `innodb_lock_wait_timeout` 默认 50s，超时抛异常，业务降级处理。支付回调本身是异步的，可以重试

**第 3 层**：`ON DUPLICATE KEY UPDATE` 有什么性能问题？
→ 如果表很大且唯一索引很多，每次 upsert 需要检查所有唯一索引。但在会员角色表场景（数据量小、索引少）性能没有问题

**第 4 层**：双状态分离的好处和代价是什么？
→ 好处：支付成功和权益发放可独立追踪，发放失败不影响支付确认，支持人工补发。代价：多一个状态字段，业务逻辑稍复杂，但换来的运维能力是值得的

**第 5 层**：有没有遇到过"支付成功但发放失败"的真实案例？
→ 遇到过会员角色不存在（roleId 查不到）的情况，`pay_status=SUCCESS` 但 `grant_status=FAILED`，`grant_message` 记录了"会员角色不存在"，开发修复角色映射后人工补发

### 亮点七/八：ES 搜索与索引管理——连环追问

**第 1 层**：ES 和 MySQL 的搜索结果会不一致吗？
→ 会短暂不一致（Flink 同步有延迟），但 ES 故障降级到 MySQL 时返回的是最新数据。这是"一致性 vs 可用性"的权衡

**第 2 层**：A/B 双索引切换的切换瞬间有请求进来怎么办？
→ `switchAlias` 是原子操作，瞬间完成。切换前请求走旧索引，切换后走新索引，不存在空窗期

**第 3 层**：如果目标索引写入只完成了一半怎么办？
→ 写入完成后有 `validateIndex` 校验数据量和 batchId，校验失败不切换别名，在线索引不受影响

**第 4 层**：批量写入 ES 的性能如何？
→ 使用 `bulk` API 批量写入（每批 200 条），比逐条写入快 10-20 倍。首页卡片数据量小（几十条），全量同步 < 1s

**第 5 层**：ES 的 mapping 变更怎么处理？
→ mapping 一旦创建不能修改已有字段类型。变更方案：新建索引（新 mapping）→ 全量写入 → 切换别名 → 删除旧索引。本项目 `recreateIndex` 方法封装了这个流程

### 亮点九：权限体系——连环追问

**第 1 层**：为什么不扩展 Spring Security？
→ Spring Security 基于角色/权限字符串，C 端等级是数值比较，自定义注解更直观。Spring Security 用于 B 端完全没问题

**第 2 层**：如果用户同时有 VIP 和小班角色，等级怎么算？
→ 取所有角色的最高等级（并集判断），避免只查单角色导致误拦。这是一个实际的 Bug，已修复

**第 3 层**：角色过期后降级会不会导致用户正在看的课程中断？
→ 等级校验在 Filter 层完成，当前请求不受影响。下一次请求时会检测到等级变化，返回 403。前端可提示"会员已过期，请续费"

**第 4 层**：`@Anonymous` 的实现原理是什么？
→ Filter 层检测 `@Anonymous` 注解，如果存在则跳过登录校验，`UserContextUtil` 返回 null。Controller 层通过 `UserContextUtil.getCurrentUserIdSafely()` 获取可能为 null 的 userId

### 亮点十：成长故事+文档脱敏——连环追问

**第 1 层**：为什么不直接用 LLM 生成故事？
→ LLM 可能幻觉导致数据错误（如把 5 门课写成 50 门课），模板渲染保证数据准确。未来可用 LLM 润色文案但事实数据仍用模板

**第 2 层**：脱敏规则有遗漏怎么办？
→ 10+ 条正则覆盖手机号、身份证、邮箱、GitHub、姓名、地址、公司、紧急联系人等。采用"宁可过度脱敏不可漏脱"原则。同时提供人工审核入口

**第 3 层**：PDFBox 抽取扫描件 PDF 会怎样？
→ PDFBox 只能抽取文字层，扫描件没有文字层会返回空字符串，抛 `ServiceException("Only text-based PDF or DOCX documents are supported")`

**第 4 层**：文档处理失败后临时文件会泄漏吗？
→ `process()` 方法用 try-catch 包裹，所有异常路径都调用 `cleanup()` 删除临时目录。使用 `Files.walk` 递归清理，确保无残留

**第 5 层**：如何支持更多文档格式（如 DOC、TXT）？
→ `SUPPORTED_EXTENSIONS` 列表控制，新增格式只需：① 在列表中添加扩展名 ② 在 `process()` 中添加对应的文本抽取方法（如 Apache POI 处理 DOCX）

### 全生命周期与定时任务——连环追问

**第 1 层**：为什么项目同时用 @Scheduled 和 XXL-Job 两套调度器？
→ 历史演进——早期用 @Scheduled 轻量快速（如 OutboxEventPublishTask、SeckillOrderTimeoutTask），后期引入 XXL-Job 做统一管理。两套共存期间发现了 P0 级重复调度问题（PayStatusUpdateTask 与 OrderCloseTask 同时跑）

**第 2 层**：发现重复调度问题后怎么修的？
→ 分两步：① 短期——禁用 @Scheduled 版本（注释并标注原因）；② 长期——统一迁移到 XXL-Job。关键是 select + update 范围对齐（WHERE id IN），避免多实例竞争

**第 3 层**：定时任务执行过程中 JVM 被 kill 了怎么办？
→ 依靠幂等设计——事务内 CAS 状态检查保证重复执行无副作用。OutboxEventPublishTask 的 SENDING 状态超时自动恢复，指数退避（1m→5m→15m→1h）避免风暴重试

**第 4 层**：如果定时任务执行时间超过了调度间隔会怎样？
→ 三种应对：① 设置最大执行时间（超时中断）；② 分布式锁防止重叠执行（@DistributeLock 已接入 8 个模块）；③ XXL-Job 的路由策略可配置"丢弃后续调度"

**第 5 层**：CI/CD 五道关卡中，哪一道最容易出问题？
→ 第三道“jar 完整性检查”和第四道“远程一致性校验”。jar 传输过程中可能截断（SHA256 不匹配），这时部署自动中断。修复方式是重新上传，确保网络稳定

| 缓存穿透/击穿/雪崩怎么办？ | 秒杀库存 Key 不存在时 Lua 返回 -1（库存不足），不会穿透到 DB | 缓存空值防穿透、互斥锁防击穿、TTL 随机化防雪崩 |
| `FOR UPDATE` 和乐观锁怎么选？ | 支付回调用 `FOR UPDATE`（串行化），秒杀用 Lua（无锁，更轻量） | 冲突频率高用悲观锁（`FOR UPDATE`），冲突频率低用乐观锁（CAS） |
| 如何防止越权访问？ | 秒杀订单查询校验 userId 归属；成长故事用 `ensurePaidMember` 闸门；电子书不接受外部传参防探测 | 数据归属校验 + 身份闸门 + 返回通用错误码防业务探测 |
| 软删除有什么坑？ | MyBatis 逻辑删除拦截器正则误匹配 SELECT 字段名，对无 delete_flag 的表也注入 | 拦截器需要校验目标表是否有 delete_flag 列，无则跳过 |
| 定时任务重复执行了怎么办？ | 项目中 @Scheduled + XxlJob 两套调度器同时跑同一逻辑，导致每分钟至少两次重复查询 | 统一为一套实现；多实例场景用 select + update 范围对齐（WHERE id IN） |
| AOP 注解不生效怎么办？ | Spring AOP 基于代理，`this.method()` 调用原始对象而非代理，`@Transactional` / `@DistributeLock` 都不生效 | `@Lazy` 自注入代理对象，或通过 `SpringUtils.getAopProxy()` 获取代理 |
| 跨平台部署遇到诡异问题怎么排查？ | Nacos `server-addr` 带 `http://` 前缀在 macOS 上卡死、Windows 正常，无日志无异常 | 中间件地址用环境变量注入，不硬编码；“A 平台正常 B 平台异常”是典型配置陷阱信号 |

#### 案例 1：支付回调与主动查单并发导致权益重复发放

**现象**：用户支付成功后，权益被发放了两次——课程被重复开通，会员时长被叠加了两倍。

**根因分析**：`OrderServiceImpl` 有两条路径都能触发“支付成功”逻辑：
1. **支付平台回调**：`handlePayNotify()` → 更新订单状态 → 发放权益
2. **前端轮询触发的主动查单**：查询支付平台确认支付状态 → 更新订单状态 → 发放权益

两条路径都是无条件执行“更新流水 + 发权益消息”，当它们并发到达时，都会执行完整的发放流程，导致重复发送支付成功 Kafka 消息、权益重复发放。

**排查过程**：
1. 运营反馈“用户只付了一次钱但课程开通了两次”
2. 查看日志发现同一订单号在 200ms 内有两条“支付成功”记录
3. 追踪调用链：一条来自 `PayNotifyController`（回调入口），一条来自 `OrderServiceImpl.queryPayResult`（主动查单）
4. 确认两条路径都无条件执行了 `updatePendingToSuccess` + `paymentSuccessEventPublisher.publish`

**修复方案**：以 `updatePendingToSuccess`（条件 UPDATE：`WHERE status = 'PENDING'`）的 affected rows 作为幂等闸门：

```java
// 修复前：无条件执行
paymentMapper.updatePendingToSuccess(paymentNo, ...);
paymentSuccessEventPublisher.publish(orderNo); // 两条路径都会执行

// 修复后：CAS 结果做幂等闸门
int updated = paymentMapper.updatePendingToSuccess(paymentNo, ...);
if (updated > 0) {
    // 只有本次推进成功者才能触发下游副作用
    paymentSuccessEventPublisher.publish(orderNo);
}
```

同时为 `executeInTransaction` 增加带返回值的 `Supplier<T>` 重载，把事务内 CAS 结果传出到事务外层判断。

**经验教训**：
- 所有“状态推进 + 副作用”场景必须用**条件 UPDATE 的 affected rows** 做幂等判断，不能用 `SELECT` 预判（SELECT 和 UPDATE 之间有竞态窗口）
- 主动查单与支付回调是**天然并发**的两条路径，必须共用同一套幂等闸门
- 提交证据：`ce8abba0`

#### 案例 2：秒杀限购 Redis Set 只支持单件购买

**现象**：秒杀活动设置了限购 3 件（`limitPerUser=3`），但用户购买 1 件后再次购买被拒绝，提示“已达限购上限”。

**根因分析**：Lua 脚本中限购校验使用了 Redis Set（`SISMEMBER`），只能判断用户“是否买过”，无法记录“已购数量”。即使 `limitPerUser=3`，用户买过 1 件后 Set 中已有该用户，再次购买就被拒绝。

```lua
-- 修复前：Set 只判有无
if redis.call('SISMEMBER', boughtKey, userId) == 1 then return -2 end

-- 修复后：String 计数器判数量
local bought = tonumber(redis.call('GET', boughtCntKey)) or 0
if bought + qty > limit then return -2 end
redis.call('INCRBY', boughtCntKey, qty)
```

**排查过程**：
1. 用户反馈“限购 3 件但只能买 1 件”
2. 检查 Lua 脚本发现 `SISMEMBER` 命令——这是集合成员判断，不是计数器
3. Redis CLI 验证：`SMEMBERS seckill:bought:{activityId}` 只有 userId，没有数量信息
4. 确认数据结构选型与业务语义不匹配

**修复方案**：
- 限购存储从 Set 改为 String Key 计数器：`seckill:bought_cnt:{activityId}:{itemId}:{userId}`
- Lua 脚本改为 `GET` 已购数量 → 判断 `bought + qty > limit` → `INCRBY` 增加
- 取消订单/超时取消时同步 `DECRBY` 减少已购数量
- `doSeckill` 接口新增 `quantity` 参数支持多件购买

**经验教训**：
- Redis 数据结构选型必须与业务语义对齐：Set 适合“有/无”判断，String + INCRBY 适合“多少个”计数
- 排查 Redis 相关问题时，直接查看 Lua 脚本或 Redis 命令，不要只看接口文档
- 提交证据：`05e6d5c5`

#### 案例 3：MyBatis 逻辑删除拦截器正则误匹配 SELECT 字段

**现象**：某个查询接口突然返回异常数据——原本应返回 1 条记录却返回了全表数据，或者 SQL 报语法错误。

**根因分析**：`GlobalLogicDeleteInterceptor` 是项目的全局 MyBatis 拦截器，自动为 `osh_*` 表注入 `AND delete_flag = 0` 条件。原始正则 `\b(osh_\w+)(?:\s+(?:AS\s+)?(\w+))?` 过于宽泛，不仅匹配 FROM/JOIN 后的表名，还会匹配 SELECT 字段列表中以 `osh_` 开头的字段名（如 `osh_user` 字段），导致在字段名后注入 `AND delete_flag=0`，破坏 SQL 语法或改变查询语义。

**排查过程**：
1. 发现某查询返回了已删除的数据
2. 开启 MyBatis SQL 日志，发现注入的 WHERE 条件位置异常
3. 对比拦截前后的 SQL，发现 `SELECT osh_user, ...` 中的 `osh_user` 被拦截器误认为是表名
4. 检查正则：`\b(osh_\w+)` 没有上下文限定，SELECT 字段列表中的 `osh_user` 也命中了

**修复方案**：

```java
// 修复前：正则过于宽泛
Pattern.compile("\\b(osh_\\w+)(?:\\s+(?:AS\\s+)?(\\w+))?");

// 修复后：限定只匹配 FROM/JOIN 后面的表名
Pattern.compile("(?:FROM|JOIN)\\s+(osh_\\w+)(?:\\s+(?:AS\\s+)?(\\w+))?");
```

同时增加无 `delete_flag` 表的白名单判断（`TABLES_WITHOUT_DELETE_FLAG`），避免对无该列的表注入导致 `Unknown column 'delete_flag'` 错误（同一拦截器的另一类事故，提交 `95c0c588`）。

**经验教训**：
- MyBatis 拦截器修改 SQL 是高风险操作，正则必须精确限定匹配上下文
- 拦截器必须有充分的单元测试覆盖各种 SQL 写法（SELECT/JOIN/子查询/别名）
- 新模块建表时必须对齐项目通用列约定（`delete_flag`、`create_time` 等），否则会被全局机制误伤
- 提交证据：`dbb8759b`（正则修复）、`95c0c588`（白名单）

#### 案例 4：C 端 /pc 接口混用 B 端 PreAuthorize 导致 403

**现象**：内部会员管理接口（`/pc/internal-member/*`）全部返回 403 Forbidden，即使管理员登录也无法访问。

**根因分析**：项目存在 B 端（Spring Security `@PreAuthorize` + authority 体系）与 C 端（自定义 Filter + 角色体系）双权限体系。`InternalMemberAdminController` 走 `/pc/` C 端链路，却叠加了 B 端 `@PreAuthorize("hasAuthority('internal:member:*')")`。C 端登录态中没有 B 端 authority，接口全部被拦截。

```java
// 修复前：混用 B 端权限注解
@PreAuthorize("hasAuthority('internal:member:*')")
@GetMapping("/pc/internal-member/list")
public R<List<...>> list() { ... }

// 修复后：移除 B 端注解，由 C 端 Filter + 角色脚本控制
@GetMapping("/pc/internal-member/list")
public R<List<...>> list() { ... }
```

**排查过程**：
1. 前端报 403，检查 Spring Security 日志发现“Access Denied”
2. 检查接口注解：发现 `@PreAuthorize("hasAuthority('internal:member:*')")`
3. 检查 C 端登录态：C 端 Filter 只设置了角色信息，没有注入 B 端 authority
4. 确认路径 `/pc/` 属于 C 端链路，不应使用 B 端权限注解

**修复方案**：移除 B 端 `@PreAuthorize` 注解与 `ensureAdmin()` 检查，改由 C 端认证 Filter + 角色权限脚本控制访问。

**经验教训**：
- 双权限体系项目中，新增接口前先确认路径前缀（`/api/` = B 端，`/pc/` = C 端）归属哪个认证链路
- 权限控制只在该链路对应的机制内实现，禁止跨体系混用
- 可以在项目架构层面做路径-认证映射的文档化约定，或在 Code Review Checklist 中加入“权限注解与路径前缀一致性”检查项
- 提交证据：`81dd573a`

#### 案例 5：OSS 临时签名 URL 存库过期导致裂图

**现象**：课程详情中的图片在上传一段时间后全部裂图（无法显示），刷新页面无效。

**根因分析**：课程小节富文本 `textContent` 中存储的图片地址是 OSS 临时签名 URL（含 `X-Amz-Signature`、`X-Amz-Expires` 参数），签名有过期时间。过期后图片无法访问，而前端每次加载页面时没有重新签名。

**排查过程**：
1. 用户反馈课程详情页图片全部裂图
2. 检查 OSS Bucket 权限——正常（私有桶，需签名访问）
3. 查看数据库中存储的图片 URL——发现是带 `X-Amz-Signature` 的完整临时 URL
4. 直接访问 URL 返回 403——签名已过期
5. 追踪上传代码：`uploadImage` 返回临时 URL，`saveContent` 直接存入了数据库

**修复方案**：

```
修复前：上传 → 返回临时 URL → 存入 DB → 展示时 URL 已过期
修复后：上传 → 返回 objectKey → 存入 DB → 展示时动态签名
```

- 数据库改为存储相对路径（objectKey），读取时通过 `ossService.getLimitedUrl(objectKey, 120)` 动态签名
- 新增批量获取临时 URL 接口 `POST /content/image-urls`：前端传入 objectKey 列表，后端返回 `Map<objectKey, signedUrl>` 映射
- 兼容旧数据：如果 DB 中存的是完整临时 URL，通过域名白名单识别本桶资源，提取 objectKey 重新签名

**经验教训**：
- OSS 私有桶标准做法：**DB 只存 objectKey，读取时动态签名**
- 临时 URL 存入 DB = 定时炸弹，修复时需做旧数据兼容（按域名白名单提取 key 重签）
- 预防性设计：在 DO 对象的 `setUrl` 方法中加入断言——如果 URL 包含 `X-Amz-` 参数则抛异常，从代码层面阻止临时 URL 入库
- 提交证据：`9195694b`（裂图修复）、`84fbf75a`（完整 URL 提取重签）

#### 案例 6：分布式锁固定字符串全局锁反模式

**现象**：多个不相关的业务操作互相阻塞——课程保存慢时，工具删除也被卡住；课程审核一次占用 60 秒，期间所有审核请求全部失败。

**根因分析**：多个 Controller 使用了 `@DistributeLock(scene = "resource", key = "operation")` 这样的固定字符串锁键，所有资源共用一把全局锁：

| 接口 | 锁键 | 后果 |
|---|---|---|
| `OshCourseController` save/update | `resource:operation` | 课程保存慢 → 卡住无关的工具删除 |
| `OshToolController` 增删改 | `resource:operation` | 与课程操作共用同一把锁 |
| 课程审核 | `course:audit:api` | `waitTime=0 + expireTime=60000` → 一次审核占锁 60s，期间所有审核秒失败 |

```java
// 反模式：固定字符串全局锁
@DistributeLock(scene = "resource", key = "operation", expireTime = 60000, waitTime = 0)
public R<?> saveCourse(@RequestBody CourseCreateRequest request) { ... }

// 正确实践：锁键包含资源维度
@DistributeLock(scene = "course", keyExpression = "#request.id", expireTime = 60000, waitTime = 3000)
public R<?> saveCourse(@RequestBody CourseCreateRequest request) { ... }
```

**排查过程**：
1. 监控发现工具删除接口 RT 飙高，但工具模块本身没有慢操作
2. 追踪 Redis 锁状态：`resource:operation` 这把锁被课程保存操作持有，工具删除在排队等待
3. 代码审查发现：多个 Controller 共用 `scene="resource", key="operation"` 这把全局锁
4. 进一步发现课程审核 `waitTime=0`（不排队）+ `expireTime=60000`（60s），一次审核失败后所有审核都超时

**修复方案**：
- 锁键必须包含资源维度：`keyExpression = "#request.id"`（有 ID 时用资源 ID，新增时用 `#request.title`）
- 跨模块隔离：不同业务模块的锁键前缀应区分（`course:save:{id}` vs `tool:delete:{id}`）
- 等待策略匹配业务耗时：长耗时操作禁止 `waitTime=0`，应给 3-5s 缓冲；快速失败场景用 `waitTime=0 + expireTime=3000`

**经验教训**：
- `@DistributeLock` 的锁键审查必须关注两个维度：粒度（是否包含资源 ID）和等待策略（waitTime/expireTime 是否匹配业务耗时）
- 全局锁 = 全局瓶颈，任何场景都不应使用固定字符串作为锁键
- 正面范例：网站提交 `@DistributeLock(scene="website_submit", key="website_submit_lock", includeUserId=true, waitTime=0)` —— 按用户维度防重复提交且不阻塞他人
- 来源：2026-08 跨模块代码审查（OshCourseController、OshToolController、OshPracticalWebsiteServiceImpl）

#### 案例 7：Nacos 地址 http:// 前缀导致 macOS 启动卡死

**现象**：Spring Boot 应用在 macOS 上启动卡死，无任何错误日志输出；同一份代码在 Windows 上正常运行。

**根因分析**：`bootstrap.yml` 中 Nacos 的 `server-addr` 配置为 `http://43.242.200.25:8848`，带了 `http://` 前缀。Nacos Client 在 macOS 上无法正确解析带协议前缀的地址，导致连接超时但无异常输出，应用卡在初始化阶段。Windows 上的 Nacos Client 能自动剥离前缀，所以不受影响。

**排查过程**：
1. macOS 上 `java -jar` 启动，卡在 Loading 阶段无日志
2. `jstack` 查看线程栈：主线程卡在 Nacos Client 的 `ServerListManager` 初始化
3. 检查 `bootstrap.yml`：发现 `server-addr: http://43.242.200.25:8848`
4. 去掉 `http://` 后重启正常

**修复方案**：
- `server-addr` 改为纯 `host:port` 格式（`43.242.200.25:8848`）
- 配置注释标注平台差异
- 长期使用环境变量注入地址，避免硬编码

**经验教训**：
- 中间件地址应外部化（环境变量），不硬编码在配置文件中
- Nacos `server-addr` 标准格式是 `host:port`（不带协议前缀）
- 跨平台启动卡死无日志时，优先检查中间件连接配置
- “Windows 正常 macOS 卡死”是典型的跨平台配置陷阱信号
- 提交证据：`7118fa44`

#### 案例 8：多角色用户权限判断只查单角色导致误拦

**现象**：VIP 用户访问高等级课程接口时被 403 拒绝，但运营确认该用户确实有 VIP 角色。

**根因分析**：`OshUserLevelAspect` 通过 `getRoleCodeByUserId(userId)` 只返回用户的一个角色 code。如果 SQL 恰好返回低权限角色（如 `developer`），即使用户还拥有 `vip` 等高权限角色也会被拦截。

**涉及文件**：
- `OshAuthenticationFilter.java`（L151-170）：`getRoleIdsByUserId` 查全部角色 → 遍历取最高等级
- `OshCourseServiceImpl.java`（L216-234）：`hasFullCourseAccessByRole` 遍历 `FULL_ACCESS_ROLE_CODES`
- `SecurityBoundaryTest.java`（L89-109）：`shouldMergePermissionsFromAllRoles` 测试明确引用 `e663560d`

**排查过程**：
1. 用户反馈"我买了 VIP 但看不了 VIP 课程"
2. 查看日志发现该用户有两个角色：`developer`（普通）和 `vip`（高等级）
3. 检查 `getRoleCodeByUserId` 方法，确认只返回第一个角色
4. SQL 返回顺序不确定，可能返回低权限角色

**修复方案**：
- 改为查询用户全部有效角色 ID 列表，批量查角色对象
- 逐一检查是否有任一角色命中全量访问名单（`FULL_ACCESS_ROLE_CODES`）
- 封装为 `hasFullCourseAccessByRole(userId)` 方法，"任一命中即放行"

**经验教训**：
- 多角色系统中权限判断必须遍历用户的全部有效角色，不能假设返回最高权限角色
- 建议封装通用的 `hasAnyRole(userId, roleCodes)` 方法
- 提交证据：`e663560d`

#### 案例 9：INSERT 语句遗漏 user_name 导致通知流程失败

**现象**：信息差内容发布后，审核通过时小铭铛通知发送失败——找不到接收人。

**根因分析**：`createInfoGap()` 方法在 INSERT 时没有写入 `user_name` 字段，Mapper XML 的 INSERT 语句也缺少该列。发布时只传了 userId 没传 userName。审核通过后小铭铛通知需要 `user_name` 查找接收人，字段为空导致通知发送失败。

**涉及文件**：
- `InfoGapServiceImpl.java`（L31-39）：`createInfoGap` 方法 `entity.setUserName(userName)` 修复点
- `InfoGapController.java`（L1-4）：Controller 获取 `currentUsername` 传给 Service
- `OshInfoGap.java`（L19）：`private String userName` 字段定义
- `OshInfoGapMapper.java`（L18）：`insertInfoGap(OshInfoGap entity)` Mapper 入口

**排查过程**：
1. 运营反馈"发布内容审核通过了但作者没收到通知"
2. 查看 `osh_info_gap` 表，发现 `user_name` 字段为 NULL
3. 追踪 INSERT 语句，确认 Mapper XML 中缺少 `user_name` 列
4. 确认下游通知依赖 `user_name` 而非 `user_id`

**修复方案**：
- Controller 层从 `UserContextUtil.getCurrentUser()` 获取 username 传给 Service
- Service 方法签名增加 `userName` 参数
- Mapper XML INSERT 语句补充 `user_name` 列

**经验教训**：
- 涉及通知/消息推送的业务，关联用户信息时不能只存 userId，还需冗余 userName
- INSERT 语句遗漏非空业务字段可能导致下游流程静默失败
- 新增实体字段后务必检查所有 INSERT 语句是否同步
- 提交证据：`5e2f664a`

#### 案例 10：支付金额字段取单价而非实付总额

**现象**：用户购买 3 件秒杀商品，但实际支付金额只有 1 件的价格——少收钱了。

**根因分析**：调用 `payService.createPay()` 时金额参数传入 `order.getSeckillPrice()`（单件价），而非 `order.getTotalAmount()`（数量×单价的实付总额）。

**涉及文件**：
- `OshSeckillOrder.java`（L52-56）：`totalAmount` 字段（注释“实付总金额”）
- `OshSeckillOrderServiceImpl.java`（L154）：`vo.setTotalAmount(item.getSeckillPrice().multiply(BigDecimal.valueOf(quantity)))` 修复点
- `SeckillOrderConsumer.java`（L87）：消费者中同步的 totalAmount 计算
- `osh_seckill_order.sql`（L14）：`total_amount DECIMAL(10,2)` 列定义

**排查过程**：
1. 财务对账发现某笔订单支付金额与商品总价不一致
2. 查看支付接口调用代码，确认金额参数来源
3. 发现 `createPay(amount)` 传入的是 `seckillPrice`（单价）而非 `totalAmount`（总额）
4. 确认 `OshSeckillOrder` 实体缺少 `totalAmount` 字段

**修复方案**：
- `OshSeckillOrder` 实体新增 `totalAmount` 字段
- 支付接口金额字段从 `seckillPrice` 改为 `totalAmount`
- SQL 建表同步添加 `total_amount` 列
- 支付入口处增加 `totalAmount >= unitPrice * quantity` 的断言校验

**经验教训**：
- 支付金额是最高敏感字段，调用支付接口时必须确认传入的是"实付总金额"而非"单价"
- 支付接口参数命名明确区分 `unitPrice` 与 `totalAmount`
- 提交证据：`5135e950`

### 阶段一：需求分析——OpenSpec/SDD 驱动的行为契约

> **Hook**："我们项目用 SDD 工作流——先写规格文档再写代码，仓库里有 30+ 个 OpenSpec 变更目录，每个都包含 proposal、design、tasks、spec 四件套，CI 自动检查，缺一个都不让合并。"

**S（Situation）**：osh-backend 是一个 Spring Boot 多模块单体，承载课程、工具、订单、拼团、秒杀、内部会员、反馈、问答等业务域。当多个 AI Agent 与人类开发者同时协作时，"需求只留在聊天记录/微信群/口头说明"会导致行为契约被随意破坏、变更不可追溯、回滚无依据。

**T（Task）**：建立一套需求驱动的行为契约机制，确保每次中大型变更都有完整的"为什么做→怎么做→分几步→怎么验收"文档链，并且可以被 CI 自动校验。

**A（Action）**：实施了 OpenSpec/SDD 工作流，核心是四件套结构：

```
openspec/changes/<change-id>/
  proposal.md    # 为什么做（背景、目标、非目标、用户影响、风险、验收标准）
  design.md      # 怎么做（方案概览、接口设计、数据设计、业务流程、兼容性、回滚）
  tasks.md       # 分步执行（按优先级分阶段的 checklist）
  specs/
    <capability>/
      spec.md    # 行为契约（GIVEN/WHEN/THEN 格式）
```

以 `fix-group-module-quality`（拼团模块治理）为例，展示需求拆解过程：

| 文档 | 核心内容 | 规模 |
|------|---------|------|
| **proposal.md** | 背景：P0-P3 共 21 项代码漏洞；目标：消除安全/并发风险 + 枚举常量化 + Map→VO；非目标：不拆分 Service、不改表结构、不改前端契约 | 70 行 |
| **design.md** | 四层实施路径：安全加固（P0）→ 权限与规范（P1）→ 业务一致性（P1）→ 枚举常量化（P2-P3）；9 个接口的变化与兼容策略表 | 132 行 |
| **tasks.md** | 按 P0→P3 分 6 个阶段、共 50+ 个 checklist 项；验证阶段含 grep 扫描确认无遗留魔法值 | 75 行 |
| **spec.md** × 2 | `group-code-quality`（97 行）：枚举引用、常量管理、强类型 VO；`group-security`（75 行）：分布式锁、越权防护、权限注解 | 均用 GIVEN/WHEN/THEN |

**R（Result）**：仓库累计沉淀 **30+ 个 OpenSpec 变更目录**，覆盖课程支付、拼团修复、内部会员、文档管理、电子书防盗链等业务域。CI 的 `verify-ai-process.sh` 脚本自动校验 14 个核心文件存在且非空 + OpenSpec 变更完整性，未提供四件套或豁免声明的 PR 直接阻断合并。

**设计思考（为什么这样做）**：
- **为什么不直接写代码？** 多人协作（尤其是 AI Agent 参与）时，"代码即文档"不够——AI Agent 需要明确的 spec 约束行为边界，Reviewer 需要 design.md 评估方案合理性
- **为什么 spec 用 GIVEN/WHEN/THEN？** 这是行为驱动的标准格式，可直接转化为测试用例，避免 spec 和 test 脱节
- **豁免机制如何运作？** 仅文档错别字、注释修正、无行为影响的小调整可豁免，PR 标注 `OpenSpec-Exempt: true` + 原因

### 阶段二：方案设计——方案对比与选型决策

> **Hook**："我做方案设计时习惯做方案对比表——比如支付回调幂等我对比了乐观锁、悲观锁、CAS 条件 UPDATE 三种方案，最终选了 CAS，因为它在并发性能和实现简洁性之间取得了最佳平衡。"

**S（Situation）**：多个业务模块（课程、拼团、秒杀、电子书）共用支付回调，主动查单与支付回调可能并发触发权益发放，不做幂等控制会导致重复发货。同时 Flink 集群默认配置下 Task Heap 只有 25.6MB，4 个同步作业频繁 OOM。

**T（Task）**：针对两个典型场景做方案设计——支付回调幂等控制 + Flink 内存调优。

**A（Action）**：

**案例 1：支付回调幂等三闸门方案选型**

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **悲观锁（FOR UPDATE）** | 行锁串行化 | 绝对安全 | 并发退化为串行，TPS 受限 | ❌ 支付回调不需要这么高的串行度 |
| **乐观锁（version 字段）** | 版本号比对 | 无阻塞 | 需额外加字段，冲突时重试逻辑复杂 | ❌ 过度设计 |
| **CAS 条件 UPDATE** | `WHERE status='pending'` 的 affected rows | 无额外字段、天然幂等、一条 SQL 完成 | 需理解 affected rows 语义 | ✅ 选中 |

最终方案"三重闸门"：
1. **Redis 分布式锁**（防并发入口）：`@DistributeLock(scene = "pay_callback")` 串行化同一订单的回调
2. **CAS 条件 UPDATE**（DB 级兜底）：`updatePendingToSuccess` 的 affected rows = 0 即幂等短路
3. **事务内副作用编排**（一致性保证）：发权益、写事件、更新状态在同一事务内完成

**案例 2：Flink 内存调优方案设计**

设计思路：先理解 Flink 内存模型 6 个区域（Framework Heap / Task Heap / Network / Managed / JVM Metaspace / JVM Overhead），再通过四步调参法逐轮压测验证。

| 轮次 | 调参方向 | Task Heap 结果 | 关键发现 |
|------|---------|---------------|----------|
| 基线 | 默认 1024MB process | 25.6MB | Managed 230MB 过大，挤压 Task Heap |
| 第 1 轮 | Managed 128m + Metaspace 128m + Network 32m | ~288MB | Task Heap 提升 11 倍 |
| 第 2 轮 | 8 job 压测（逐步递减 taskHeap） | 104MB 仍稳定 | 验证极限承载力 |

**R（Result）**：
- 支付幂等方案上线后，主动查单与回调并发场景 100% 幂等正确，零重复发货
- Flink Task Heap 从 25.6MB 提升到 288MB，4 个作业 + 8 个压测 job 并行稳定运行

**设计思考**：
- **为什么 CAS 优于悲观锁？** 支付回调是低频高价值操作（每秒个位数），不需要悲观锁的绝对串行保证，CAS 的"尝试一次，失败即幂等短路"语义恰好匹配
- **为什么 Flink 调参要分轮次？** 内存模型各区域相互耦合（Managed 减少 → Task Heap 增加），一步到位无法定位瓶颈，逐轮验证才能建立因果关系

### 阶段三：开发实现——编码规范与工程治理

> **Hook**："我写的代码不只是实现功能，还要沉淀为可复用的框架能力——比如我把分布式锁封装成 @DistributeLock 注解，8 个业务模块一行配置就能接入；把事件可靠投递封装成 Outbox Pattern，3 个域接入后零消息丢失。"

**S（Situation）**：项目有 10+ 个业务模块，各模块面临共性技术挑战——并发控制、事件可靠投递、幂等保障。如果每个模块各自实现，会出现代码重复、标准不统一、维护成本高的问题。

**T（Task）**：将通用技术能力抽象为框架级组件，以"约定优于配置"的方式让业务模块低成本接入。

**A（Action）**：三个工程治理实践——

**实践 1：CAS 防超卖（`OrderServiceImpl`）**

```sql
-- 核心 SQL：条件 UPDATE 做幂等闸门
UPDATE osh_order_list 
SET status = 'success', update_time = NOW() 
WHERE order_no = #{orderNo} AND status = 'pending'
-- affected rows = 1 → 本次推进成功，触发下游权益发放
-- affected rows = 0 → 已被其他线程处理，幂等短路
```

三个调用点（课程/拼团/秒杀的支付回调）共用同一个 `updatePendingToSuccess` 方法，保证模式统一。

**实践 2：@DistributeLock 声明式分布式锁**

```java
@DistributeLock(scene = "group_join", keyExpression = "#activityId", 
                waitTime = 3000, expireTime = 15000)
public R joinGroup(@RequestBody JoinGroupVO vo) { ... }
```

8 个业务模块（拼团 join/create/pay、秒杀下单、课程收藏、工具点赞等）通过注解一行接入，底层 AOP + SpEL + Redisson 完全透明。同时保留编程式锁用于复杂场景（如支付回调的 `RLock.tryLock(5, 15, SECONDS)`）。

**实践 3：Outbox Pattern 事件可靠投递**

COURSE/TOOL/SECKILL 三个域走 Outbox 表（`osh_outbox_event`），事务内写入 → 定时轮询投递 → 成功后标记已处理，保证 100% 可靠投递到 Kafka。GROUP 域走轻量级 `publishAfterCommit` + 直接 Kafka 发送（事件仅用于监控，接受极端丢失）。

**R（Result）**：
- CAS 幂等闸门在支付回调并发场景下 100% 正确，零重复发货
- @DistributeLock 覆盖 8 个模块，接入成本从"写 10 行锁代码"降低到"加 1 行注解"
- Outbox 三域上线后消息投递成功率 100%，定时兜底任务覆盖进程崩溃场景

### 阶段四：测试验证——双层测试 + 场景化用例

### 阶段五：部署上线——CI/CD 五道关卡 + 灰度 + 回滚

> **Hook**："我们的 CI/CD 流水线有 5 道自动关卡——从代码提 PR 到生产部署，每一步都有机器校验。有一次 jar 包的 SHA256 本地和远程对不上，部署直接中断了，后来发现是传输过程中文件截断。"

**A（Action）**：

**五道关卡详情**：

| 1 | **流程合规** | PR 创建/更新 | `verify-ai-process.sh` 校验 14 个核心文件 + OpenSpec 四件套完整性 + PR body 的 `OpenSpec-Exempt` 声明 | 阻断合并 |
| 2 | **编译验证** | PR 创建/更新 | `mvn clean install -DskipTests -pl '!backstage-flink'` | 阻断合并 |
| 3 | **jar 完整性** | 部署前 | `unzip -t` 验证 jar 包结构 + `sha256sum` 生成摘要 | 中断部署 |
| 4 | **远程一致性** | 部署后 | 对比本地和远程 jar 的 SHA256 摘要 | 报警 + 回滚 |
| 5 | **健康检查** | 部署后 | 轮询 API 端点，最多重试 12 次 × 10 秒间隔（2 分钟窗口） | 报警 + 回滚 |

**分支策略与灰度发布**：

```text
feature/* → qa/* (自动部署测试环境)
          → release/* (手动确认部署预发)
          → main/master (生产部署)
```

- `qa` 分支提交自动触发 `deploy-qa.yml`，部署到测试服务器
- `release` 分支手动确认后触发 `deploy-prod.yml`，SSH 部署使用 `ssh-agent` action 解决私钥换行问题
- 部署配置动态改写：Python 脚本正则重写 `bootstrap.yml` 中的 Nacos 地址、前端构建产物中的测试机 URL

**回滚预案**：
- **代码级**：Git revert + 重新部署，所有 OpenSpec 变更都有 design.md 中的回滚步骤
- **数据级**：拼团分布式锁 TTL 10 秒自动过期，回滚代码后锁自动释放
- **配置级**：Nacos 配置有版本历史，一键回退
- **邮件通知**：部署结果自动发送邮件，失败不阻断部署流程（解耦通知与部署）

**R（Result）**：
- 五道关卡上线后，jar 传输不完整、配置遗漏等问题 100% 被自动拦截
- qa → release → main 三级灰度，确保每次变更经过测试验证后才进生产
- 部署 workflow 按环境命名（`deploy-qa` / `deploy-prod`），参数化配置避免硬编码

### 追问预判

| # | 追问 | 应对思路 |
|---|------|----------|
| 1 | 为什么用 SDD 而不是敏捷 Scrum？ | SDD 和敏捷不矛盾——SDD 是"规格先行"的工程纪律，敏捷是迭代节奏。我们的 proposal 就是 user story 的技术化表达，spec 就是 acceptance criteria 的形式化。区别在于 SDD 的 spec 可以被 CI 自动检查，而 Jira ticket 不行 |
| 2 | 30+ 个 OpenSpec 变更的维护成本高吗？ | 每个变更平均 200-300 行文档，但都是一次性编写、持续受益。相比"需求在微信群里说了一嘴，三个月后谁也记不住为什么这样做"，文档的成本远低于沟通成本。而且模板统一后，新建一个 change 只需 30 分钟 |
| 3 | 如果紧急 Bug 来不及写 OpenSpec 怎么办？ | 允许先修复上线，但事后必须补档。proposal.md 里有"事后补档"标注（如 `fix-group-module-quality` 就是事后补档）。PR 检查也支持 `OpenSpec-Exempt: true` 豁免机制 |
| 4 | CAS 和数据库唯一索引有什么区别？ | 唯一索引防的是"重复插入"，CAS 防的是"重复更新"。支付回调场景是 UPDATE 订单状态 + 触发下游发放权益，唯一索引派不上用场。两者互补——INSERT 用唯一索引，UPDATE 用 CAS |
| 5 | 测试覆盖率具体是多少？ | 关键域（支付回调、权限校验、拼团并发）覆盖率 >80%，整体项目覆盖率约 40-50%。我们不追求 100% 覆盖率，而是把测试资源集中在"出 Bug 代价最高"的地方 |
| 6 | 五道关卡的执行时间是多少？ | 关卡 1（流程合规）约 5 秒，关卡 2（编译）约 3-5 分钟，关卡 3-4（jar 校验 + 一致性）约 30 秒，关卡 5（健康检查）最多 2 分钟。整体 PR 检查约 5 分钟 |
| 7 | 灰度发布具体怎么做流量切分？ | 目前按环境灰度（qa → release → prod），不是按比例流量切分。单体架构下按比例切分需要网关层做路由，改造成本高。未来拆微服务会引入 Nacos 的灰度标签路由 |
| 8 | Flink 作业部署也纳入 CI/CD 了吗？ | Flink 作业独立管理——jar 包通过 `submit_flink_job.sh` 提交到 Flink 集群，不在主 CI/CD 流水线内。因为 Flink 作业的生命周期（cancel → submit）和 Spring Boot 服务（stop → start）不同 |
| 9 | 回滚时数据不一致怎么办？ | 回滚预案分三层：代码级（Git revert）、数据级（分布式锁自动过期 / Outbox 重投）、配置级（Nacos 版本回退）。对于不可逆的数据变更（如已发放权益），design.md 里必须写明补偿方案 |
| 10 | 你们团队的 Code Review 标准是什么？ | 6 条硬性门禁（CODE_REVIEW.md）：① 接口兼容性 ② 权限影响 ③ 数据/缓存影响 ④ 本地构建已运行 ⑤ 无密钥泄露 ⑥ 无临时文件提交。加上 7 维度 20+ 检查点的审核细则（07-review-rubric.md） |

### 亮点一：秒杀链路——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 Kafka Broker 全挂了，秒杀链路会怎样？ | Kafka 发送失败会被 catch，orderKey 2 分钟后过期释放，前端轮询发现 PENDING 超时后提示"活动太火爆请稍后重试"。库存已在 Redis 扣减但 DB 未建单，定时任务每分钟扫描未支付订单做兜底回滚 |
| 故障场景 | 如果消费者处理到一半 JVM OOM 了怎么办？ | Kafka 的 ack=all + 手动 ack 模式确保消息未确认不会推进 offset，消费者重启后从上次 offset 重新消费。seckillNo 幂等判重保证不重复建单，Redis 库存不丢失（TTL 内） |
| 扩展演进 | 如果要做"预约秒杀"（提前锁定库存，到点统一开抢），架构怎么改？ | 新增 `reserved_stock` Key，预约阶段 incrby 预占，开抢时刻 Lua 脚本从 reserved 转 available。预约阶段不扣减只登记，到点后异步批量转正式库存 |
| 扩展演进 | 如果要支持"组合秒杀"（A+B 一起买才算一次），Lua 脚本怎么改？ | 需要原子扣减多个 stockKey，Lua 脚本改为遍历 KEYS 数组，全部校验通过后才统一 decrby，任一失败则全部回滚 |
| 对比分析 | 为什么不用 Redis Stream 替代 Kafka？ | Redis Stream 适合轻量消息，缺乏 Kafka 的持久化、多消费者组、背压、分区并行能力。秒杀订单需要可靠投递+重试，Kafka 更成熟 |
| 对比分析 | 为什么不用数据库乐观锁（version 字段）替代 Lua？ | 乐观锁在高冲突场景下大量重试，RT 不可控。秒杀是典型高冲突场景，Lua 预检将冲突拦截在 Redis 层，只有真正能成功的请求才到达 DB |
| 性能调优 | 如果 Redis 单节点扛不住秒杀 QPS 怎么办？ | 库存 Key 按 activityId 做 slot 分散到 Redis Cluster 不同节点；或使用 Redis 多活（CRDT）方案；极端场景可引入本地缓存预扣+异步对账 |
| 监控告警 | 秒杀链路需要监控哪些指标？ | Lua 脚本执行失败率、Kafka 消息积压量、消费者消费延迟、orderKey 超时未消费比例、DB 库存与 Redis 库存差值。设置告警阈值，如积压>1000 条或延迟>30s |
| 个人反思 | 如果重新设计秒杀链路，你会怎么改？ | ① 引入 DLQ 保存消费失败的消息供人工恢复；② 用 Redis Stream 或 Kafka 事务消息简化"发送+确认"逻辑；③ 加 Prometheus 埋点做全链路可观测 |

### 亮点二：Flink 同步矩阵——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 ES 集群完全不可用，Flink 作业会怎样？ | Checkpoint 会持续失败，触发 fixedDelayRestart 重启策略（3 次，间隔 30s）。超过重启次数后 Job 挂掉，需要告警介入。Kafka offset 已提交但 ES 未写入，恢复后从 Checkpoint 重放 |
| 故障场景 | 如果 Kafka 某个 Partition Leader 切换，Flink 消费会中断吗？ | KafkaSource 会自动 reassign partition 并 reseek 到上次 committed offset，短暂中断后恢复。EXACTLY_ONCE 模式下 Checkpoint 保证不丢不重 |
| 扩展演进 | 如果未来要新增第 5 个业务域（如电子书）同步到 ES，你会怎么做？ | 参考 GroupActivityIndexSyncJob 的最新模板：KafkaSource API + EXACTLY_ONCE + fixedDelayRestart + DLQ side output。新建 Topic + Job 类 + SinkFactory，复用已有配置矩阵规范 |
| 扩展演进 | 如果 ES mapping 需要新增字段（如加一个"推荐指数"），怎么处理？ | ES 允许动态新增字段（dynamic mapping），直接发消息带新字段即可。如果需要改已有字段类型，则需要 reindex：新建索引 → 全量同步 → 别名切换 |
| 对比分析 | 为什么不用 Canal 监听 MySQL Binlog 替代应用层发 Kafka？ | Canal 方案对业务零侵入，但无法携带业务语义（如 eventType 区分 audit/upsert/delete）。应用层发 Kafka 可以精确控制同步内容和时机 |
| 对比分析 | Flink vs Spark Streaming 在这个场景下怎么选？ | Flink 支持真正的流处理（event-by-event），延迟更低；Checkpoint 机制更成熟；RocksDB StateBackend 支持大状态。Spark Streaming 的微批模式延迟较高 |
| 性能调优 | 4 个作业各占一个 Slot，资源浪费怎么办？ | 可以用 Slot Sharing Group 让多个作业共享 Slot；或调整 Parallelism 使多个 subtask 共享 Slot。当前 parallelism=1 场景下 4 个 Slot 已够用 |
| 监控告警 | Flink 作业挂了怎么第一时间知道？ | Flink Web UI 的 Job Status 变为 FAILED；接入 Prometheus 的 Flink Metrics Exporter 监控 checkpoint 失败次数和重启次数；配置钉钉/企微告警 |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 统一 4 个作业为一个通用框架（Template Method），新增业务域只需实现序列化/过滤/Sink 三个接口；② 全量接入 DLQ；③ 用 Flink SQL 替代 DataStream API 降低开发门槛 |

### 亮点三：CEP 异常检测——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 CEP 作业挂了，重启后会漏检吗？ | RocksDB Checkpoint 保存了所有用户的模式匹配状态，重启后从 Checkpoint 恢复，已积累的事件序列不丢失，不会漏检 |
| 故障场景 | 如果某个用户的事件量特别大（如恶意脚本），CEP 会不会 OOM？ | RocksDB 将状态持久化到磁盘，不会 OOM。但单个用户的状态过大会影响 Checkpoint 性能，可以加 per-key state size 监控 |
| 扩展演进 | 如果要加"同一用户在不同活动间快速切换参团"的检测呢？ | keyBy 改为 userId，Pattern 中增加 activityId 变化条件：`begin("join").where(event -> differentActivityId).timesOrMore(3).within(10min)` |
| 扩展演进 | 如果要从"告警"升级为"自动拦截"（如自动冻结账号），架构怎么改？ | 异常检测输出连接到 Redis，将 userId 写入黑名单 Key（TTL 30min），拼团入口 Filter 检查黑名单 Key 是否存在，存在则拒绝参团 |
| 对比分析 | CEP vs 自己写滑动窗口计数器，你怎么选？ | 简单计数用窗口就够了。但 CEP 能表达"A 之后 B 之前不能有 C"这类复杂序列模式，且内置状态管理和超时清理，维护成本更低 |
| 对比分析 | 为什么不用 Drools 规则引擎？ | Drools 是批处理规则引擎，不适合流式事件处理。CEP 天然集成在 Flink 流处理管道中，延迟更低、状态管理更统一 |
| 性能调优 | 如果用户量从千级增长到百万级，CEP 扛得住吗？ | RocksDB 支持 TB 级状态，瓶颈在 Checkpoint 时间。可以通过增量 Checkpoint + 并行度扩展来应对。极端场景可分层：先用窗口过滤可疑用户，再对可疑用户跑 CEP |
| 监控告警 | 告警量暴增（如大量误报）怎么处理？ | 加"告警去重"逻辑：同一 userId + 同一规则在 N 分钟内只告警一次。加"告警收敛"：当告警量超过阈值时自动降级为汇总告警 |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 阈值和规则抽到配置文件/数据库，支持动态调整无需重启作业；② 加 DLQ 保存异常事件的完整上下文供事后分析；③ 输出到 Kafka 而非日志，下游消费做自动拦截 |

### 亮点四：Outbox Pattern——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 Outbox 表所在的 MySQL 实例挂了会怎样？ | Outbox 和业务表同库，MySQL 挂了业务本身也不可用。MySQL 恢复后 Outbox 事件继续投递，定时任务扫描补偿 |
| 故障场景 | 如果定时任务和主服务部署在不同节点，会不会重复投递？ | 定时任务用分布式锁（如 `@DistributeLock`）保证单节点执行。即使多节点同时扫描，`UPDATE ... SET status=COMPLETED WHERE id=? AND status=PENDING` 的 CAS 语义保证只有一个节点能成功标记 |
| 扩展演进 | 如果要从 Outbox 模式迁移到 CDC（如 Debezium），需要改什么？ | CDC 监听 MySQL Binlog 自动捕获数据变更，无需应用层写 Outbox。但 CDC 无法区分"哪些变更需要发事件"，需要额外的过滤逻辑。迁移时需要评估业务语义是否可完全从 Binlog 推断 |
| 扩展演进 | 如果要支持"事件溯源"（Event Sourcing），Outbox 够用吗？ | Outbox 是"副作用记录"，不是完整的领域事件流。Event Sourcing 需要所有状态变更都以事件形式存储，需要独立的 Event Store（如 EventStoreDB），Outbox 不够 |
| 对比分析 | Outbox vs 两阶段提交（2PC），你怎么选？ | 2PC 保证强一致性但性能差、可用性低（协调者单点）。Outbox 是最终一致性，性能好、可用性高，适合"搜索索引同步"这类允许短暂延迟的场景 |
| 对比分析 | 为什么不用 Kafka 事务消息？ | Kafka 事务消息保证 Kafka 内部的原子性（多 Topic 原子发送），但不保证"DB 写入 + Kafka 发送"的跨系统原子性。Outbox 解决的是 DB+MQ 的跨系统一致性问题 |
| 性能调优 | Outbox 表扫描会不会影响业务表性能？ | Outbox 是独立表，有独立索引 `(status, next_retry_time)`。定时任务用 `LIMIT 100` 分批扫描，不会长事务锁表。如果数据量过大，可以按月分表或归档已完成的记录 |
| 监控告警 | 怎么知道 Outbox 投递是否正常？ | 监控 PENDING 事件数量（应趋近于 0）、FAILED 事件数量（应告警）、平均投递延迟（afterCommit 到 Kafka 确认的时间差）。设置 FAILED 数量 > 0 时钉钉告警 |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 加 DLQ 机制保存投递失败的原始 payload；② 提供管理后台手动重投 FAILED 事件；③ 考虑引入 CDC 替代部分场景，减少应用层侵入 |

### 亮点五：分布式锁——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 Redisson 获锁成功但业务执行到一半 Redis 主从切换了怎么办？ | Redisson 的锁数据在主从同步前可能丢失（异步复制），新主节点上没有锁记录，其他线程可能获锁。这是 RedLock 要解决的问题。本项目接受短暂不一致 + DB 层兜底 |
| 故障场景 | 如果 `releaseImmediately=false` 但持锁线程抛异常了，锁会泄漏吗？ | 不会。AOP 切面的 finally 块会检查 `lock.isHeldByCurrentThread()` 并释放。如果 finally 也失败（如 Redis 不可达），锁的 expireTime 保证最终自动过期 |
| 扩展演进 | 如果要支持"可重入锁"（同一线程多次获锁），怎么改？ | Redisson 的 `RLock` 本身就支持可重入（内部维护 hash + counter）。当前 `@DistributeLock` 的切面逻辑已经是可重入的，因为 Redisson 底层处理了计数 |
| 扩展演进 | 如果要支持"读写锁"（多读单写），注解怎么设计？ | 新增 `lockMode` 属性（READ/WRITE），读锁用 `redissonClient.getReadWriteLock(key).readLock()`，写锁用 `writeLock()`。多个读锁可共存，写锁互斥 |
| 对比分析 | Redisson vs Zookeeper 分布式锁，你怎么选？ | Redisson 性能好（内存操作）、TTL 自动续期、API 丰富。ZK 锁强一致（CP 模型）但延迟高、吞吐量低。本项目选 Redisson 因为锁场景允许短暂不一致 |
| 对比分析 | 为什么不用数据库行锁替代分布式锁？ | DB 行锁（FOR UPDATE）适合事务内的串行化，但不适合跨请求/跨服务的并发控制。分布式锁可以跨 JVM 工作，且不依赖 DB 连接 |
| 性能调优 | 如果锁竞争激烈导致大量线程 waitTime 超时怎么办？ | ① 分析竞争原因，考虑拆分锁粒度（如按 activityId 拆分）；② 用 `waitTime=0` 快速失败 + 前端重试；③ 引入排队机制（如 Kafka 削峰）替代锁排队 |
| 监控告警 | 怎么监控分布式锁的健康状态？ | 监控获锁成功率、平均等待时间、超时失败率。Redisson 提供 Metrics 接口，接入 Prometheus 后设置告警：超时失败率 > 5% 或平均等待时间 > 1s |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 加 `@DistributeLock` 的 `fallback` 属性，获锁失败时执行降级方法而非直接抛异常；② 引入 RedLock 提升强一致性场景的可靠性；③ 加锁使用热力图可视化竞争分布 |

### 亮点六：支付回调幂等——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果支付平台重复回调且两次回调间隔极短（< 1ms），FOR UPDATE 能拦住吗？ | 能。MySQL 行锁是排他锁，第二个 `SELECT ... FOR UPDATE` 会阻塞等待第一个事务提交/回滚后才能执行。两次回调不会同时进入发放逻辑 |
| 故障场景 | 如果发放过程中 MySQL 连接池耗尽了怎么办？ | 事务超时后回滚，`grant_status` 保持 FAILED。支付平台下次重试回调时重新处理。连接池监控告警应提前配置 |
| 扩展演进 | 如果要支持"退款"（扣减会员时长），幂等方案怎么改？ | 新增 `refund_status` 字段，退款回调用同样的 FOR UPDATE + grant_status 闸门。退款逻辑用 `GREATEST(expire_time - duration, now)` 扣减时长，防止退成负数 |
| 扩展演进 | 如果要支持"部分退款"（退 3 个月中的 1 个月），怎么处理？ | `upsertUserRole` 改为 `expire_time = expire_time - refund_months`，加 `GREATEST(expire_time, now)` 保底。退款记录独立表，支持多次部分退款 |
| 对比分析 | FOR UPDATE vs 乐观锁（version 字段），在这个场景你怎么选？ | 支付回调并发低（同一订单不会高频回调），FOR UPDATE 的串行化开销可接受。乐观锁适合高并发读+低并发写场景，重试成本高。此处悲观锁更直观 |
| 对比分析 | 为什么不用 Redis 分布式锁替代 FOR UPDATE？ | 支付回调需要和 DB 事务配合（锁住订单行 → 修改状态 → 提交），FOR UPDATE 天然在事务内。Redis 锁需要额外处理"锁释放但事务未提交"的窗口问题 |
| 性能调优 | FOR UPDATE 在高并发下会成为瓶颈吗？ | 同一订单的回调不会高并发（支付平台有重试间隔）。不同订单的 FOR UPDATE 锁不同行，互不影响。真正的瓶颈在 DB 连接池大小 |
| 监控告警 | 怎么发现"支付成功但发放失败"的异常？ | 监控 `grant_status=FAILED` 的记录数，设置 > 0 时告警。定时任务扫描 FAILED 记录自动重试或通知人工处理 |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 引入 Saga 模式，支付和发放作为独立步骤各自幂等 + 补偿；② 加"对账任务"每日比对支付平台的成功订单和本地 grant_status，发现不一致自动补发 |

### 亮点七/八：ES 降级 + 索引切换——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 ES 返回数据但数据是旧的（Flink 同步延迟），用户看到旧数据怎么办？ | 这是最终一致性的固有延迟。可以在搜索结果中标注"数据更新时间"，让用户感知。关键业务（如秒杀库存）不走 ES，直接查 DB |
| 故障场景 | 如果 A/B 切换后新索引数据有问题，怎么快速回滚？ | 旧索引仍然存在且数据完好，只需将别名重新指向旧索引即可（`switchAlias` 再次执行）。回滚操作秒级完成 |
| 扩展演进 | 如果要从双索引升级为三索引（A/B/C），需要改什么？ | 索引命名改为 `index_v1/v2/v3`，别名切换逻辑改为"找到当前别名指向的索引 → 选下一个可用的索引 → 写入 → 切换"。三索引主要用于更大规模的全量重建场景 |
| 扩展演进 | 如果要做增量同步（而非全量），架构怎么改？ | 增量同步通过 Flink Kafka→ES 作业实现（已有 4 个作业），全量同步仅在首次初始化或 mapping 变更时使用。两者互补：增量保证实时性，全量保证一致性 |
| 对比分析 | 降级到 MySQL 后搜索质量下降，怎么缓解？ | MySQL 搜索用 LIKE 或 FULLTEXT INDEX，对中文分词支持差。可以引入 MySQL 的 ngram 全文索引做基本分词，或者在降级期间只支持精确匹配搜索 |
| 对比分析 | 为什么不用 OpenSearch 替代 ES？ | OpenSearch 是 ES 的 fork，API 兼容。如果 ES 许可协议变更（如 Elastic 改为 SSPL），可以无缝切换到 OpenSearch。当前 ES 许可满足需求 |
| 性能调优 | bulk 写入 ES 时 batchSize 怎么选？ | 取决于文档大小和 ES 集群配置。通常 200-500 条/批或 5-15MB/批。本项目首页卡片数据量小（几十条），batchSize 影响不大。大数据量场景建议压测确定最优值 |
| 监控告警 | ES 降级事件怎么发现和统计？ | 降级时 `log.warn` 记录，接入 ELK 后统计降级频率。设置"1 小时内降级次数 > 10"时告警。同时监控 ES 集群的 health status（green/yellow/red） |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 引入 Sentinel 做自动熔断，ES 连续失败 N 次后自动降级而非每次请求都 try-catch；② 加"降级演练"定时任务，定期模拟 ES 故障验证降级链路 |

### 亮点九：权限体系——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 Redis 挂了，等级信息读不到怎么办？ | Filter 层 catch Redis 异常后，降级为最低等级（普通用户），保证接口可用但高级功能不可用。Redis 恢复后自动恢复等级 |
| 故障场景 | 如果用户的等级信息在 Redis 中被误删了怎么办？ | 下次请求时 Filter 检测到等级信息缺失，从 DB 重新加载并回写 Redis。加"等级信息缺失"日志监控，及时发现异常删除 |
| 扩展演进 | 如果要支持"临时体验 VIP"（24 小时试用），怎么改？ | 角色表增加 `expire_time` 字段，临时 VIP 设 24h 后过期。Filter 层每次请求校验 `expire_time > now()`，过期后自动降级。已有 VIP 角色有效期机制可复用 |
| 扩展演进 | 如果要支持"按内容粒度控制权限"（如某课程只对 VIP 开放），怎么改？ | 在资源维度加 `required_level` 字段，查询时 `WHERE required_level <= user_level`。或在 Controller 层用 `@OshUserLevel` 注解标记特定接口 |
| 对比分析 | 为什么不用 RBAC（角色-权限）模型做 C 端权限？ | C 端权限本质是"等级门槛"，是数值比较，RBAC 的"角色→权限"映射增加了不必要的复杂度。B 端用 RBAC（Spring Security），C 端用等级数值，各取所长 |
| 对比分析 | 为什么不用 JWT 存储等级信息？ | JWT 是无状态的，签发后无法修改（除非 refresh token）。等级变更后需要立即生效，JWT 做不到实时刷新。Redis 会话可以随时更新等级信息 |
| 性能调优 | 每次请求都读 Redis 获取等级，会不会成为瓶颈？ | Redis 单次 GET < 1ms，不是瓶颈。如果 QPS 极高（>10K），可以在 Filter 层加本地缓存（Caffeine，TTL 30s）减少 Redis 访问 |
| 监控告警 | 怎么发现权限异常（如大量 403）？ | 监控 403 响应码的比例，设置 > 5% 时告警。分析 403 日志中的 userId 和 requiredLevel，判断是正常拦截还是配置错误 |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 等级信息加版本号（version），防止并发更新导致等级回退；② 引入权限缓存预热（应用启动时批量加载活跃用户等级）；③ 加管理后台可视化展示用户等级分布 |

### 亮点十：成长故事+文档脱敏——延伸追问

| 维度 | 追问 | 应对思路 |
|---|---|---|
| 故障场景 | 如果 6 个维度的某个数据源查询失败了（如面试记录表为空），故事生成会失败吗？ | 不会。`buildGenerationContext` 对每个数据源做了 null 安全处理，`renderStory` 中的 `defaultText/valueText/safeNumber` 方法对空值提供默认值（0/默认文本） |

| 扩展演进 | 如果要支持"多语言"（英文/日文成长故事），怎么改？ | 模板渲染层引入 i18n 资源文件，`buildStoryContent` 根据用户语言偏好选择不同模板。脱敏规则需要根据语言调整（如日本手机号格式不同） |
| 对比分析 | 为什么用模板渲染而不是 LLM 直接生成？ | 模板渲染：① 数据准确性 100%（不会幻觉）；② 延迟低（200ms vs LLM 2-5s）；③ 成本低（无需 GPU/API 费用）；④ 可控性强。LLM 适合润色不适合事实生成 |
| 对比分析 | 脱敏为什么不用现成库（如 Apache ShardingSphere 的数据脱敏）？ | ShardingSphere 脱敏是 SQL 层的透明脱敏，适合 DB 存取场景。此处是文档文本脱敏，需要正则匹配非结构化文本，现有库不直接支持 |
| 性能调优 | 6 次 DB 查询可以优化吗？ | 可以并行查询（CompletableFuture.supplyAsync），将 6 次串行查询改为并行，总耗时从 ~200ms 降到 ~50ms。但需要注意线程池配置和超时控制 |
| 监控告警 | 怎么监控脱敏是否有效？ | 脱敏后做"反向检测"：用同样的正则扫描脱敏后的文本，如果发现匹配（说明脱敏不彻底），记录告警日志 |
| 个人反思 | 如果重新设计，你会怎么改？ | ① 引入异步生成（提交任务 → 后台处理 → WebSocket 通知完成），避免用户等待；② 脱敏规则抽到配置文件，支持动态调整；③ 加"脱敏覆盖率"指标做质量监控 |

| 个人反思 | 如果重新设计定时任务体系，你会怎么改？ | ① 统一到 XXL-Job，消除双调度器重叠；② 每个任务接入统一监控面板；③ 引入任务依赖编排（DAG）替代独立 cron |

## 附录 F：面试官「为什么」链式追问

> 面试官经常用连续的"为什么"层层追问，考察候选人对每个技术决策的深层理解。以下模拟每个亮点最可能遇到的 3-5 层"为什么"链。

### 亮点一：秒杀链路——为什么链

**Q1：为什么要把库存扣减放在 Redis 里而不是数据库里？**
→ 数据库行锁在高并发下成为瓶颈，数千 QPS 的 UPDATE 会导致连接池耗尽和锁等待超时。Redis 单线程模型 + Lua 原子操作可以支撑 10 万+ QPS，将并发压力拦截在内存层。

**Q2：为什么 Lua 脚本可以保证原子性？Redis 不是单线程的吗？**
→ Redis 的 Lua 脚本在执行期间会阻塞其他命令，整个脚本作为一个原子操作执行。这是 Redis 的设计保证——脚本执行期间不会被其他客户端的命令打断。

**Q3：为什么消息体要"自包含上下文"？不能消费者自己去查吗？**
→ 消费者是异步线程，没有 HTTP 请求上下文。如果消费者需要反查 Redis Key 名称，就需要维护一份与生产者相同的 Key 映射逻辑，耦合度高且容易不一致。自包含上下文让消费者完全独立。

**Q4：为什么定时任务要每分钟扫描？频率太高会不会影响 DB？**
→ 分钟级是权衡用户体验（取消延迟）和 DB 压力（扫描频率）的结果。查询条件 `status=0 AND pay_expire_time < now()` 走索引，单次扫描 < 10ms。频率太低（如 10 分钟）会导致用户等待取消时间过长。

**Q5：为什么 DB 侧还要加 `WHERE available_stock >= quantity` 的闸门？Redis 不是已经扣过了吗？**
→ 防御性编程原则——Redis 和 DB 之间不是原子操作，存在 Redis 扣成功但 DB 操作失败的可能（如网络分区、进程崩溃）。DB 闸门是最后一道防线，保证即使 Redis 出问题也不会超卖。

### 亮点二：Flink 同步矩阵——为什么链

**Q1：为什么要用 4 个独立 Job 而不是 1 个大 Job？**
→ 独立 Job 可以单独部署、单独重启、独立扩缩容。一个域出问题不会影响其他域。缺点是资源占用更多，但在当前规模下可接受。

**Q2：为什么有的用 EXACTLY_ONCE 有的用 AT_LEAST_ONCE？**
→ 历史原因，不同时期开发的。AT_LEAST_ONCE 性能稍好（无需两阶段提交），在幂等 Sink（upsert by id）场景下效果等价。但统一为 EXACTLY_ONCE 可以消除"重放消息导致状态覆盖"的隐患。

**Q3：为什么 Group 作业要用 RocksDB StateBackend 而其他不用？**
→ Group 作业有 1 小时滚动窗口聚合，需要维护每个窗口内的状态。如果窗口内数据量大，堆内状态可能 OOM。RocksDB 将状态持久化到磁盘 + 支持增量 Checkpoint，适合大状态场景。

**Q4：为什么用 Kafka 做中间层而不是直接写 ES？**
→ Kafka 提供了"缓冲 + 持久化 + 多消费者"能力。一条业务事件可以被搜索同步、异常检测、统计分析等多个消费者同时消费。直接写 ES 则无法解耦，ES 不可用时数据直接丢失。

### 亮点三：CEP 异常检测——为什么链

**Q1：为什么要用 Flink CEP 而不是在业务代码里直接判断？**
→ 业务代码中的判断是"单事件触发"的（如每次下单检查一次），无法表达"时间窗口内多事件序列"的模式。CEP 天然支持"5 分钟内 3 笔"这样的时序模式匹配。

**Q2：为什么 keyBy(userId) 而不是 keyBy(activityId)？**
→ 刷单检测的主体是"用户"，需要把同一用户在不同活动中的行为聚合判断。如果 keyBy(activityId)，同一用户在不同活动的行为被分散到不同分区，无法检测跨活动刷单。

**Q3：为什么用 `timesOrMore` 而不是 `times`？**
→ `times(3)` 精确匹配恰好 3 次，第 4 次需要重新匹配。`timesOrMore(3)` 匹配 3 次及以上，一旦达到阈值立即触发告警，更符合"超过阈值就报警"的业务语义。

**Q4：为什么输出到日志而不是直接写数据库或发消息？**
→ 当前阶段是"告警"而非"拦截"，日志是最轻量的输出方式。未来可升级为写 Kafka → 下游消费做自动拦截。日志的好处是零外部依赖，不影响 CEP 作业的稳定性。

### 亮点四：Outbox Pattern——为什么链

**Q1：为什么不直接在事务中发 Kafka？**
→ 两种不一致：① Kafka 发送成功但事务回滚——消费端处理了一条从未存在的数据；② 事务提交但 Kafka 发送失败——消费端永远不会收到这条数据。Outbox 通过"先写本地表 + 异步投递"解决这两个问题。

**Q2：为什么 `afterCommit` 而不是 `beforeCompletion`？**
→ `beforeCompletion` 在事务提交前执行，此时数据还未持久化。如果此时投递 Kafka 成功但事务提交失败，消费端会处理一条"幽灵"数据。`afterCommit` 保证数据已落盘。

**Q3：为什么定时任务扫描间隔设为 30 秒？**
→ 30 秒是"投递延迟可接受度"和"DB 扫描压力"的平衡点。`afterCommit` 即时投递是主路径，定时任务只是兜底。绝大多数事件在 `afterCommit` 阶段就已投递成功。

**Q4：为什么重试次数上限是 10 次？**
→ 10 次指数退避（1s/2s/4s/8s/.../512s）覆盖约 17 分钟的重试窗口，足以应对短暂的 Kafka 不可用。超过 10 次说明是持久性故障，需要人工介入。

### 亮点五：分布式锁——为什么链

**Q1：为什么不用 JDK 自带的 `synchronized` 或 `ReentrantLock`？**
→ 它们是 JVM 级别的锁，只在单进程内有效。分布式环境下多实例部署时无法互斥。

**Q2：为什么用 Redisson 而不是自己用 `SETNX` 实现？**
→ `SETNX` 实现分布式锁有很多坑：锁续期（WatchDog）、可重入、主从切换丢锁、释放非自己的锁等。Redisson 已经把这些都处理好了。

**Q3：为什么要区分 `waitTime=0` 和 `waitTime>0` 两种模式？**
→ 不同业务场景对锁竞争的容忍度不同。秒杀需要快速失败（用户点了没抢到就直接告诉他），课程保存需要排队等待（保证保存成功）。一刀切是不合理的。

**Q4：为什么 `releaseImmediately` 不是默认 true？**
→ 有些场景下方法执行完了但业务还没完成（如秒杀下单方法返回了，但消费者还在异步处理）。如果立即释放锁，另一个线程可能进入临界区导致冲突。

### 亮点六：支付回调幂等——为什么链

**Q1：为什么用 `FOR UPDATE` 而不是分布式锁？**
→ 支付回调需要和数据库事务紧密配合——锁住订单行 → 读取状态 → 判断幂等 → 修改状态 → 提交事务。`FOR UPDATE` 天然在事务内，不需要额外的锁协调。

**Q2：为什么 `grant_status` 和 `pay_status` 不能合并成一个状态？**
→ 它们是不同阶段的事件：支付成功来自第三方，权益发放来自内部系统。合并后无法区分"支付成功但发放失败"的中间状态，运维排查困难。

**Q3：为什么用 `ON DUPLICATE KEY UPDATE` 而不是 `INSERT IGNORE`？**
→ `INSERT IGNORE` 忽略重复插入但不更新已有记录。续期场景下需要更新过期时间，`ON DUPLICATE KEY UPDATE` 能做到"有则更新，无则插入"。

### 亮点七/八：ES 降级 + 索引切换——为什么链

**Q1：为什么不直接查 MySQL 而要用 ES？**
→ ES 提供全文检索（倒排索引）、复杂聚合（terms/histogram/nested）、毫秒级查询。MySQL 的 LIKE 查询在大表上性能差且不支持中文分词。

**Q2：为什么降级要 try-catch 而不是提前判断 ES 是否可用？**
→ 提前判断（如 ping ES）有"检查通过但查询时 ES 刚好挂了"的竞态问题。try-catch 是最可靠的降级方式——实际失败了再切换。

**Q3：为什么用 A/B 双索引而不是 delete + recreate？**
→ delete + recreate 期间别名指向不存在的索引，所有查询返回空。A/B 切换是原子的，切换前走旧索引，切换后走新索引，零空窗。

**Q4：为什么 `validateIndex` 要校验 batchId 而不是只校验文档数？**
→ 文档数相同不代表数据正确——可能是上次同步的残留数据。batchId 确保目标索引的数据确实是本次同步写入的。

### 亮点九：权限体系——为什么链

**Q1：为什么不复用 B 端的 Spring Security 权限？**
→ C 端等级是"数值门槛"（等级 >= 2 即可访问），B 端是"角色-权限字符串"模型。强行复用会导致 C 端接口被 B 端权限拦截，产生 403。

**Q2：为什么等级信息存 Redis 而不是 JWT？**
→ JWT 签发后无法修改（除非 refresh token），等级变更后无法实时生效。Redis 可以随时更新，每次请求读到的是最新等级。

**Q3：为什么用 ThreadLocal 传递等级信息？**
→ ThreadLocal 是同一请求链路中传递上下文信息的标准方式，避免方法参数层层传递。Filter 层写入，AOP 层读取，Controller 层使用。

### 亮点十：成长故事+文档脱敏——为什么链

**Q1：为什么要做六维数据聚合而不是简单展示？**
→ 简单展示（如"学了 5 门课"）价值低。六维聚合后形成完整的"成长画像"，对内部成员的就业指导和自我认知更有价值。

**Q2：为什么脱敏要用正则而不是简单的字符串替换？**
→ 敏感信息格式多样（手机号 11 位、身份证 18 位、邮箱有 @），正则能精确匹配各种格式，字符串替换做不到"只替换手机号不替换其他数字"。

**Q3：为什么 PDFBox 处理完要重新渲染 PDF 而不是直接修改原文件？**
→ PDF 是二进制格式，直接修改容易破坏文件结构。重新渲染（抽取文本 → 脱敏 → 生成新 PDF）更安全，且可以统一格式。

## 附录 G：故障注入与混沌工程追问

> 高级面试中，面试官会问"如果 X 组件出问题会怎样"，考察你对系统韧性的理解。以下按故障类型整理。

### 网络分区类

| 故障场景 | 影响范围 | 系统表现 | 恢复策略 |
|---|---|---|---|
| Redis 与 Spring Boot 之间网络分区 | 秒杀预检失败、分布式锁获取失败、等级信息读取失败 | 秒杀返回"系统繁忙"；锁降级为无锁（业务兜底）；等级降级为普通用户 | 网络恢复后自动恢复，无需人工介入 |
| Kafka Broker 与消费者之间网络分区 | 秒杀消息积压、Outbox 投递失败、Flink 消费延迟 | 秒杀 orderKey 2 分钟后过期释放；Outbox 定时任务 30s 后重试；Flink Checkpoint 失败触发重启 | Kafka 自带重连机制，网络恢复后自动追上积压 |
| ES 集群与应用之间网络分区 | 搜索降级、首页卡片降级、Flink 写入失败 | 搜索自动 fallback 到 MySQL；首页走 MySQL 兜底；Flink 重启重试 | ES 恢复后 Flink 从 Checkpoint 追数据，搜索自动恢复 |
| MySQL 主从延迟超过 10 秒 | 支付回调查不到最新订单、秒杀消费者查不到活动 | `FOR UPDATE` 走主库不受影响；秒杀消费者查主库 | 主从延迟恢复后读从库的请求自动一致 |

### 进程崩溃类

| 故障场景 | 影响范围 | 系统表现 | 恢复策略 |
|---|---|---|---|
| Spring Boot 实例 OOM 被 Kill | 正在处理的秒杀请求失败、正在执行的支付回调中断 | Redis 库存已扣但 DB 未建单——定时任务兜底取消；支付平台重试回调 | 新实例启动后自动恢复，定时任务补偿 |
| Flink TaskManager 崩溃 | 对应作业的所有 subtask 停止处理 | ES 搜索数据延迟（但不丢失，Kafka 消息还在） | JobManager 检测失败后在其他 TaskManager 上重启 subtask，从 Checkpoint 恢复 |
| Kafka Broker 宕机（3 节点中的 1 个） | 部分 Partition Leader 切换 | 短暂不可用（毫秒级），Leader 切换后恢复 | Kafka 自动选举新 Leader，ISR 机制保证数据不丢（ack=all 场景） |
| Quartz 调度节点宕机 | 定时任务（未支付订单扫描、Outbox 兜底）不执行 | 短期内无兜底扫描，未支付订单不会被自动取消 | Quartz 集群模式下其他节点接管；单节点需重启 |

### 数据异常类

| 故障场景 | 影响范围 | 系统表现 | 恢复策略 |
|---|---|---|---|
| Redis 库存 Key 被误删 | 秒杀 Lua 脚本 `GET stockKey` 返回 nil | Lua 返回 -1（库存不足），所有秒杀请求失败 | 定时任务或管理后台重新初始化库存 Key |
| Kafka 消息 payload 格式变更（上游改了字段名） | Flink 反序列化失败、消费者解析异常 | Flink 消息进入 DLQ（如果有 side output）；消费者抛异常 | 修复 Flink/消费者的反序列化逻辑，从 DLQ 重放失败消息 |
| ES mapping 与写入文档字段不匹配 | Flink 写入 ES 失败 | ES 返回 mapping 异常，Flink Checkpoint 失败 | 修复 mapping 或文档字段，重启 Flink 作业从 Checkpoint 恢复 |
| Outbox 表事件 payload 超过 Kafka 消息大小限制 | Kafka 发送失败 | Outbox 事件重试 10 次后标记 FAILED | 拆分大 payload 或增大 Kafka `max.message.bytes`，管理后台手动重投 |

### 资源耗尽类

| 故障场景 | 影响范围 | 系统表现 | 恢复策略 |
|---|---|---|---|
| MySQL 连接池耗尽（HikariCP max=20） | 所有需要 DB 操作的请求超时 | 抛 `SQLTransientConnectionException`，HTTP 返回 500 | 排查慢查询/长事务；临时增大连接池；长期优化 SQL |
| Redis 内存超过 maxmemory | 新 Key 写入失败（OOM command not allowed） | 秒杀库存扣减失败、锁获取失败、会话写入失败 | 配置 `maxmemory-policy=allkeys-lru` 自动淘汰冷数据；扩容 Redis |
| Kafka 磁盘写满 | 新消息无法写入 | 生产者发送超时，秒杀消息丢失，Outbox 投递失败 | 缩短日志保留时间（`log.retention.hours`）；扩容磁盘；清理过期 Topic |
| Flink Slot 不够（所有 Slot 被占用） | 新作业无法启动 | 作业状态为 CREATED 但不运行 | 增加 TaskManager 数量；调整 Slot Sharing Group 共享策略 |

### 亮点专属变体追问

| 亮点 | 变体问题 | 应对思路 |
|---|---|---|
| 秒杀 | 如果要支持"预售"（先付定金后付尾款），怎么改？ | 新增 `deposit_stock` Key 做定金预占，尾款支付时用 Lua 将定金库存转为正式库存。两次支付分别走幂等闸门 |

| Outbox | 如果要支持"事件版本化"（同一事件类型有多个版本的 payload），怎么改？ | Outbox 表加 `schema_version` 字段，消费端按版本号选择反序列化策略。Schema Registry 管理版本兼容性 |
| 分布式锁 | 如果要支持"联锁"（同时锁住 A 和 B 两个资源），怎么改？ | Redisson 的 `RedissonMultiLock` 支持同时获取多把锁并按顺序释放。注解可扩展为 `@DistributeLock(keys={"#a","#b"})` |
| 幂等发放 | 如果要支持"批量发放"（一次支付发放多个权益），怎么改？ | 循环执行三重闸门（每个权益独立 FOR UPDATE + 幂等判断 + upsert），外层事务统一提交。失败时回滚全部 |

| 文档脱敏 | 如果要支持“图片 OCR 脱敏”（扫描件中的敏感信息），怎么改？ | 引入 OCR 引擎（如 Tesseract）抽取图片文字 → 正则脱敏 → 在图片上覆盖脱敏区域。性能开销大，需要异步处理 |
| 课程资料 | 如果同一份文档要被多门课程/考试/电子书复用，怎么设计？ | 采用 `ref_type + ref_id` 多态关联表（`osh_doc_ref`），同一文档可关联多个资源。已实现支持 20+ 资源类型（`ResourceTypeEnum`），以及文档片段锚点引用（heading/range/xpath） |

### 课程文档多态关联实战：三层架构 + ref_type/ref_id 多态设计

> 课程模块的文件管理体现了从“简单外键”到“多态关联”的架构演进，是面试中展示数据建模能力的好素材。

**第一层——课程级资料**（`osh_course_material`）：
- 外键 `course_id` 直接关联课程，支持文件类型白名单（zip/rar/7z/pdf/doc/docx/ppt/pptx/xls/xlsx/txt）
- `pay_only=1` 控制仅购买后可下载，`download_count` 跟踪下载次数
- 课程创建时通过 `bindCourseMaterial()` 绑定，编辑时 `materialId` 非空则跳过重建

**第二层——章节级资料**（`CourseManageServiceImpl.saveSectionMaterials`）：
- 章节下支持**双类型附件**：视频（`mediaUrl`，走 `uploadVideo` 专用接口）+ 课件（`materials` 列表）
- 视频作为“特殊资料类型”存入 `osh_course_material`，`fileType` 区分 video/zip/pdf 等
- 章节类型由 `CourseSectionConstants` 定义：`video`（视频课时）、`text`（图文课时）、`course_link`（引入另一门课程——跨课程引用）

**第三层——通用文档多态关联**（`osh_doc` + `osh_doc_ref`）：

```
osh_doc（文档主表）                osh_doc_ref（多态关联表）
┌──────────────────────┐    ┌─────────────────────────────────┐
│ id (snowflake)         │    │ doc_id        → osh_doc.id      │
│ title                  │◄───│ ref_type      (course_section/  │
│ content (html/markdown)│    │               course/exam/book/  │
│ status (0草稿/2审核/    │    │               tool/website/…)   │
│        4已发布/6拒绝) │    │ ref_id        → 资源ID           │
│ visibility (0私有/     │    │ anchor_type   (full/heading/     │
│            1跟随资源) │    │               range/xpath)       │
└──────────────────────┘    │ is_primary    (0否/1是)           │
                               └─────────────────────────────────┘
```

**多态设计亮点**：

| 设计点 | 实现 | 优势 |
|---|---|---|
| `ref_type + ref_id` | 关联表用类型+ID 而非多张外键表 | 一张关联表服务 20+ 资源类型，新增资源无需建表 |
| `ResourceTypeEnum`（20+ 枚举） | COURSE/TOOL/BOOK/EXAM/WEBSITE/OPEN_PROJECT/INFO_GAP/BBS_POST 等 | 类型安全 + 统一路由（`mysqlTableName` + `esIndexName`） |
| `anchor_type` 片段锚点 | `full`（整篇）/`heading`（标题 ID）/`range`（字符偏移）/`xpath`（DOM 路径） | 支持“引用文档片段”而非只能引用整篇文档 |
| `is_primary` 主引用标记 | 同一文档被多个资源引用时标记主引用 | 区分“原始归属”和“复用引用” |
| 唯一键 `uk_doc_ref_active` | `(doc_id, ref_type, ref_id, anchor_type, anchor_start, anchor_end, delete_flag)` | 防止重复关联 + 软删除后可重新关联 |

> **面试应对**：被问“你做过什么数据建模/架构设计”时，可以用这个三层演进作为例子：
> “课程资料从简单外键（`course_id`）开始，随业务复杂化演进到章节级双类型附件，最后抽取为通用文档多态关联表（`ref_type + ref_id`），支持 20+ 资源类型和文档片段锚点引用。”

## 附录 I：Flink 内存调优实战——Task Heap 从 25.6MB 到 288MB 的调参之路

> 基于 `docs/Flink8slot测试.md` 中的真实压测记录，提炼 Flink TaskManager 内存模型调优的完整实战经验。
>
> **关联阅读**：Flink 4 作业 Kafka→ES 同步矩阵的整体架构与 6 类治理项详见 [亮点二](#亮点二flink-实时数据管道4-作业-kafkaes-同步矩阵)。本附录聚焦于 Flink 内存模型的调优实践，与亮点二形成“架构治理 + 资源调优”的完整 Flink 技术故事。

### 技术场景（Context）

**业务痛点**：线上 Flink 集群（1 个 JobManager + 6 个 TaskManager，每 TM 配置 `process.size=1024m`、`slots=2`）运行 `course-search-index-sync-job` 和 `tool-search-index-sync-job` 两个业务作业。当尝试提交更多作业或运行内存压测 Job 时，频繁出现 `NoResourceAvailableException: Could not acquire the minimum required resources`，作业无法调度。

**问题根源**：Flink 的内存模型将 `process.size` 切分为多个区域，默认配置下 `Managed Memory`、`JVM Metaspace`、`Network Memory` 占比过大，导致真正用于任务执行的 **Task Heap 只剩 25.6MB**——连一个 8MB 规格的压测 Job 都无法启动。

**调优目标**：在 `1GB process.size` 不变的前提下，通过压缩非必要内存区域，将 Task Heap 提升到能同时运行多个作业的水平。

### 问题分析：初始配置下的内存画像

调优前单 TaskManager 的资源画像（Flink REST API 返回）：

| 内存区域 | 调优前（默认） | 占 process.size 比例 | 说明 |
|---|---|---|---|
| **Task Heap** | **25.6MB** | **2.5%** | 真正用于任务执行的堆内存，严重不足 |
| Managed Memory | 230MB | 22.5% | 用于 RocksDB StateBackend、排序缓冲等；当前业务作业不使用 RocksDB |
| Network Memory | 64MB | 6.3% | 用于 Shuffle 缓冲；当前作业 shuffle 压力小 |
| JVM Metaspace | 256MB | 25.0% | 用于类元数据；默认值偏保守 |
| Framework Heap | 128MB | 12.5% | Flink 框架自身堆内存 |
| JVM Overhead | 192MB | 18.8% | JVM 原生内存（线程栈、直接内存等） |
| **合计** | **~1024MB** | **100%** | `taskmanager.memory.process.size` |

**核心矛盾**：Managed Memory（230MB）+ Metaspace（256MB）= 486MB，接近 process.size 的一半，但当前业务作业根本不需要这么大的 Managed Memory（未使用 RocksDB），Metaspace 256MB 也远超实际需求。

### 解决方案：四步调参法

```
Step 1: 缩 Managed Memory  → 230MB → 128MB（当前业务不用 RocksDB，保留基础量）
Step 2: 缩 JVM Metaspace   → 256MB → 128MB（实测类加载量远不需要 256MB）
Step 3: 缩 Network Memory   →  64MB →  32MB（当前作业 shuffle 压力小，32MB 够用）
Step 4: Task Heap 自动提升  → 25.6MB → 288MB（Flink 自动将剩余空间分配给 Task Heap）
```

调优后的 `flink-conf.yaml` 配置：

```yaml
taskmanager.numberOfTaskSlots: 4
taskmanager.memory.process.size: 1024m
taskmanager.memory.managed.size: 128m
taskmanager.memory.jvm-metaspace.size: 128m
taskmanager.memory.network.min: 32m
taskmanager.memory.network.max: 32m
```

> **关键理解**：Flink 的内存模型是"切蛋糕"——`process.size` 是固定大小的蛋糕，压缩 Managed/Metaspace/Network 三个区域后，Task Heap 会自动获得释放出来的空间。

### 调优后资源画像对比

| 内存区域 | 调优前 | 调优后 | 变化 |
|---|---|---|---|
| **Task Heap** | **25.6MB** | **288MB** | **+1023%** |
| Managed Memory | 230MB | 128MB | -44% |
| Network Memory | 64MB | 32MB | -50% |
| JVM Metaspace | 256MB | 128MB | -50% |
| Framework Heap | 128MB | 128MB | 不变 |
| JVM Overhead | 192MB | 192MB | 不变 |

### 效果验证：8 个 8MB Job 压测

**压测工具**：项目自研 `MemoryStressJob`（`backstage-flink` 模块），使用 `HeapMemoryHoldJob` 类，每个 Job 持续占用 8MB Task Heap。

**压测过程**：
1. 临时将 Flink 切为单 TM + 4 Slots 测试态
2. 循环提交 8 个 `heap-8m-{N}` 压测 Job（`parallelism=1, heapMb=8`）
3. 观察 JobManager 日志中 `Available ResourceProfile` 逐步下降

**压测结果**：

| 指标 | 结果 |
|---|---|
| 8 个 8MB Job 状态 | 全部 `RUNNING`，无 `RESTARTING` 或 `FAILED` |
| Task Heap 消耗 | 288MB → 96MB 剩余（已用 192MB） |
| Managed Memory 消耗 | 128MB → 128MB 剩余（Heap 压测不消耗 Managed） |
| Network Memory 消耗 | 32MB → 17MB 剩余 |
| `NoResourceAvailableException` | **未出现** |

**JobManager 日志关键证据**：

```text
# 起始可用资源
Available: cpuCores=4, taskHeapMemory=288MB, managedMemory=128MB, networkMemory=32MB

# 随 Job 逐步提交，taskHeap 逐步下降
taskHeapMemory=280MB → 272MB → 264MB → ... → 104MB

# 全程未出现 NoResourceAvailableException
```

### 踩坑经验：环境变量配置问题

**问题现象**：第一次切测试态时，直接用 `osh-target.env` 启动 docker compose，导致容器内 `usrlib` 目录为空，提交 Job 报错：

```text
Could not get job jar and dependencies from JAR file:
JAR file does not exist: /opt/flink/usrlib/memory-stress-test.jar
```

**根本原因**：`osh-target.env` 只提供业务端口和密码变量，但 `docker-compose.osh.yml` 中的卷挂载还依赖 `DATA/APP/CONFIG/LOG` 等路径变量。这些路径变量需要通过 `osh-render-config.sh` 脚本结合 `osh-paths.env` 生成完整的 `osh-stack.env`。

**修正方法**：

```bash
# 正确流程：先用渲染脚本生成完整环境文件
bash /opt/osh/005-scripts/osh/osh-render-config.sh \
  /opt/osh/005-scripts/osh/osh-target.env \
  /opt/osh/001-docker-compose/osh \
  /opt/osh/005-scripts/osh/osh-paths.env

# 生成的 osh-stack.env 包含完整路径变量
APP=/opt/osh/app/osh
DATA=/opt/osh/002-data/osh
CONFIG=/opt/osh/003-config/osh
LOG=/opt/osh/004-log/osh
```

**教训**：测试环境与正式环境切换时，必须确保环境变量文件完整，不能混用不同用途的 `.env` 文件。

### 测试后恢复流程

测试完成后的标准化恢复步骤（5 步）：

1. 取消所有压测 Job（`heap-8m-*`）
2. 用备份文件恢复 `docker-compose.osh.yml`
3. 用 `osh-render-config.sh` 重新生成正式 `osh-stack.env`
4. `docker compose up -d --remove-orphans` 恢复正式集群（6 个 TM）
5. 重新提交业务作业，确认 `RUNNING` 状态

恢复后确认：业务 Job `course-search-index-sync-job` 和 `tool-search-index-sync-job` 均恢复 `RUNNING`，资源画像恢复为原始值。

### 追问预判（深度扩展）

| # | 追问 | 应对思路 |
|---|---|---|
| 1 | Flink 的 Task Heap 用来做什么？为什么它这么重要？ | Task Heap 是用户代码（算子、函数、序列化/反序列化）执行时使用的堆内存。如果 Task Heap 不足，任务会 OOM 或无法调度。它是 Flink 内存模型中"真正干活"的部分 |
| 2 | Managed Memory 缩到 128MB 会不会影响 RocksDB StateBackend？ | 会的。如果作业使用 RocksDB，Managed Memory 是 RocksDB 的写缓冲和 Block Cache。当前业务作业（课程/工具同步）不使用 RocksDB，所以 128MB 足够。如果未来切换到 RocksDB 作业，需要重新调大 |
| 3 | 为什么 Network Memory 选 32MB 而不是 48MB 或 64MB？ | 32MB 是根据当前作业的 shuffle 模式选择的——单 TM 4 slots 的简单作业 shuffle 压力小。压测中 32MB 还剩 17MB 空闲，说明有余量。但如果是复杂 DAG 或有反压的作业，需要回到 64MB |
| 4 | 如何判断调参是否"过度"？ | 监控三个指标：① Task Heap 利用率（如果 > 80% 说明给少了）；② GC 频率和耗时（频繁 Full GC 说明 Heap 不够）；③ Network Buffer 使用率（如果经常 100% 说明 Network Memory 给少了） |
| 5 | JVM Metaspace 缩到 128MB 够用吗？怎么判断？ | Metaspace 存储类元数据，Flink 作业的类加载量取决于用户代码复杂度。可以通过 `-XX:MaxMetaspaceSize` 配合 JMX 监控实际使用量。当前作业 128MB 有足够余量，但如果引入大量反射或动态类加载需要调大 |
| 6 | 生产环境可以直接应用这版参数吗？ | 不能直接照搬。生产环境有 6 个 TM、2 slots/TM，业务作业使用 RocksDB（CEP 检测作业）。需要根据每个 TM 实际运行的作业类型单独调整——不用 RocksDB 的 TM 可以激进压缩，用的则需要保留更多 Managed Memory |
| 7 | 为什么不用增大 `process.size` 的方式解决？ | 服务器资源有限（每台物理机跑多个容器），增大 process.size 意味着减少 TM 实例数或挤占其他服务资源。调参是在固定资源约束下的最优解——"不加钱也能提升性能" |
| 8 | Flink 内存模型的 6 个区域分别是什么？ | ① Framework Heap（框架堆）② Task Heap（任务堆）③ Framework Off-Heap（框架堆外）④ Task Off-Heap（任务堆外）⑤ Managed Memory（托管内存）⑥ Network Memory（网络缓冲）。`process.size` = 以上 + JVM Overhead |
| 9 | 踩坑的 `osh-target.env` 和 `osh-stack.env` 有什么区别？ | `osh-target.env` 只包含业务配置（端口、密码），是"输入模板"；`osh-stack.env` 是通过渲染脚本生成的"完整环境文件"，包含路径、端口、密码等全部变量。docker compose 必须使用完整文件 |
| 10 | 如果要从 8 个 8MB Job 提升到 16 个 8MB Job，还需要调什么？ | 需要：① 增加 slots 到 8 或 16；② 增大 process.size（如 2GB）并按比例调整各区域；③ 或增加 TM 实例数。单 TM 288MB Task Heap 不够 16×8MB=128MB 的持续占用 |
| 11 | 为什么选择自研 `MemoryStressJob` 而不是 Flink 自带的 benchmark？ | 自研工具可以精确控制每个 Job 的内存占用模式（HEAP/MANAGED/COMBINED），更贴合业务场景。Flink 自带的 benchmark 更偏向吞吐量测试，不够灵活 |
| 12 | 调参过程中最大的风险是什么？ | 最大风险是"改了生产配置忘记恢复"。我们的做法是：① 备份配置文件；② 测试和正式用不同的 `.env` 文件隔离；③ 测试结束后执行标准化恢复流程并验证业务 Job 状态 |

### 简历写入建议

- 主导 Flink TaskManager 内存模型调优，在 1GB process.size 约束下通过四步调参法将 Task Heap 从 25.6MB 提升至 288MB（+1023%），单 TM 成功稳定运行 8 个 8MB 压测 Job
- 自研 Flink 内存压测工具（MemoryStressJob），支持 HEAP/MANAGED/COMBINED 三种模式，建立测试态/正式态标准化切换流程，发现并修复环境变量配置缺陷

## 面试模拟对话：秒杀链路完整 STAR 演示

> 以下模拟一场真实面试场景，展示面试官从开场提问到 3 层追问的完整对话链，以及候选人如何组织回答。
> **使用方式**：与朋友模拟练习，或自己对着镜子口述，确保每个环节自然流畅。

### 第一轮：开场提问

**面试官**：“你简历上提到了秒杀链路优化，能详细讲讲吗？”

**候选人**（Hook + STAR）：

> “好的。我用一段 11 行的 Lua 脚本把并发压力从 MySQL 转移到 Redis——一次网络往返完成库存扣减、限购校验、防重复提交三件事，接口 RT 从 2 秒降到 50 毫秒。
>
> 当时秒杀场景下，瞬时并发可达数千 QPS，传统‘先查库存→再扣减→再建单’的同步链路在数据库层成为瓶颈。
>
> 我设计了三级架构：第一级用 Redis Lua 脚本做前置原子预检——检查库存够不够、用户有没有超限购、防重复提交，全部在一次 Redis 调用内原子完成；第二级预检通过发 Kafka 消息异步建单，削峰填谷；第三级定时任务兜底取消未支付订单。
>
> 上线后接口 RT 从 2s+ 降到 50ms，零超卖事故，经历了几次大促活动都很稳定。”

### 第二轮：第一层追问

**面试官**：“为什么用 Lua 脚本而不是分布式锁？比如 Redisson？”

**候选人**（对比分析）：

> “秒杀场景需要‘快速失败’而不是‘排队等待’。Lua 脚本一次网络 RTT 就能完成库存扣减+限购校验+防重复提交三件事，非常轻量。分布式锁（比如 Redisson）需要获取锁→执行业务→释放锁三步，在高并发下锁竞争会很严重。而且 Lua 脚本是 Redis 单线程执行，天然原子性，不需要考虑锁的粒度和超时问题。”

### 第三轮：第二层追问

**面试官**：“如果 Redis 宕机了怎么办？秒杀链路会怎样？”

**候选人**（故障场景）：

> “Redis 宕机时 Lua 脚本执行直接失败，返回库存不足（return -1），秒杀接口快速返回‘系统繁忙’。生产环境我们部署了 Redis Sentinel 高可用，主从自动切换。另外我们在应用层配置了降级开关，如果 Redis 持续不可用，可以一键关闭秒杀入口，避免无效请求堆积。已扣减的 Redis 库存不会丢失，因为 Redis 重启后 RDB/AOF 持久化会恢复数据。”

### 第四轮：第三层追问

**面试官**：“Kafka 消息顺序能保证吗？如果乱序了会怎样？”

**候选人**（深度技术）：

> “同一 partition 内消息是有序的。我们的 Outbox 按 `aggregate_id` 路由到同一 partition，保证同一聚合的事件有序。跨 partition 无法保证全局有序，但 Flink Sink 用的是 ES 的 upsert 操作——相同 id 的文档会被覆盖，天然幂等，乱序也只产生最终一致的结果。另外 Kafka 配置了 `ack=all` 和手动确认，确保消息不丢失。”

### 第五轮：压力追问

**面试官**：“如果让你重新设计，你会怎么改进？”

**候选人**（个人反思）：

> “三个方向：第一，引入 DLQ 保存消费失败的消息，供人工恢复而不是依赖定时任务重发；第二，用 Kafka 事务消息简化‘发送+确认’逻辑，减少 Outbox 表的复杂度；第三，加 Prometheus 埋点做全链路可观测，比如 Lua 执行失败率、Kafka 积压量、消费者延迟等指标，用 Grafana 可视化告警。”

### 对话复盘：关键技巧拆解

## 面试模拟对话：工程治理与全生命周期演示

> 以下模拟一场偏架构师/工程治理方向的面试场景，展示候选人如何把“流程规范”讲得有深度、有数据、有故事。
> **使用方式**：与第一套模拟对话交替练习，覆盖“技术深度”和“工程素养”两个维度。

### 第一轮：开场提问

**面试官**：“你们团队的开发流程是怎样的？有做过什么改进吗？”

**候选人**（Hook + STAR）：

> “我们有一套 SDD（规格驱动开发）流程，从需求到上线经过 proposal → design → tasks → spec 四个阶段，每个 PR 都有 CI 自动校验。仓库里沉淀了 30 多个变更目录，CI 有 5 道自动关卡。
>
> 背景是早期项目没有标准化流程，PR 质量参差不齐，上线后经常返工。我推动了 OpenSpec 工作流：每个变更必须先写四件套（proposal 说为什么、design 说怎么做、tasks 拆分步骤、spec 定义接口），再写代码。
>
> CI 管线自动检查 14 个核心文件是否被修改、编译是否通过、jar 是否完整、SHA256 是否一致、部署后健康检查是否通过。任何一关失败都会阻断合并。
>
> 上线后 PR 返工率下降了 60% 以上，新人入职看 spec 就能快速理解模块设计。”

### 第二轮：第一层追问

**面试官**：“这套流程对小团队来说会不会太重了？”

**候选人**（权衡分析）：

> “确实，这是最常见的质疑。我们的做法是分级处理：中型以上变更必须走完整流程，小修复可以用 `OpenSpec-Exempt: true` 豁免，但必须在 PR 里写明豁免原因。实际上，写 proposal 和 design 的时间大约 15-20 分钟，但能避免开发过程中方向性错误——我们有一次在 design 阶段就发现方案有问题，避免了 2 天的返工。所以整体是赚的。”

### 第三轮：第二层追问

**面试官**：“CI/CD 5 道关卡具体是什么？如果有一关一直失败怎么办？”

**候选人**（细节 + 故障场景）：

> “五道关卡是：① 流程合规（14 个核心文件 + OpenSpec 四件套）；② 编译验证（`mvn clean install -DskipTests`）；③ jar 完整性（`unzip -t` + `sha256sum`）；④ 远程一致性（本地 vs 远程 SHA256 对比）；⑤ 健康检查（轮询 API，12 次 × 10s）。
>
> 如果某一关持续失败，GitHub Actions 会发邮件通知。常见问题是 SHA256 不一致——通常是本地构建后没重新打包就部署，重新 `mvn package` 就能解决。健康检查失败通常是中间件没启动或环境变量配置错误，我们有一份 `local-dev-setup-guide.md` 专门指导环境配置。”

### 第四轮：第三层追问

**面试官**：“Code Review 是怎么做的？有标准化的检查清单吗？”

**候选人**（具体化）：

> “我们有一份 `CODE_REVIEW.md` 定义了 6 条门禁和 7 维度检查表。6 条门禁是硬性底线，比如‘事务内禁止 RPC 调用’、‘状态推进必须用 CAS’。7 维度包括并发安全、幂等性、异常处理、日志规范、SQL 质量、安全性、可维护性。
>
> 举一个实际案例：拼团模块原来用 Map 作为返回值，Code Review 时发现类型不安全——下游代码可能强转报错。我们改为 VO 对象，并在 Review 时顺带做了枚举常量化和分布式锁接入。这次 Review 一次解决了 4 个潜在问题。”

### 第五轮：压力追问

**面试官**：“如果团队成员觉得流程太繁琐，不愿意配合怎么办？”

**候选人**（软技能 + 数据驱动）：

> “三个策略：第一，用数据说话——我统计了引入 OpenSpec 前后的 PR 返工率，改进后返工率下降 60%，把这个数据分享给团队；第二，降低门槛——我写了一份 `AGENTS.md` 和 `CONTRIBUTING.md`，让 AI Agent 也能自动遵守流程，减少人工负担；第三，豁免机制——小修复可以走 `OpenSpec-Exempt`，避免流程成为负担。核心思想是‘流程服务于人，而不是约束人’。”

## 附录 L：方案选型决策对比矩阵

> 面试官问"为什么用 X 而不用 Y"时，用以下矩阵结构化回答：先列出备选方案，再从多个维度对比，最后给出选型决策和理由。

### L.1 并发控制方案对比

| 维度 | CAS（条件 UPDATE） | 悲观锁（FOR UPDATE） | 乐观锁（version 字段） |
|------|-------------------|---------------------|----------------------|
| **原理** | `WHERE status='pending'` 的 affected rows | 行锁串行化，锁住后其他事务等待 | 版本号比对，`WHERE version = #{old}` |
| **并发性能** | 高（无锁，失败即短路） | 低（串行等待） | 中（冲突时重试） |
| **额外字段** | 无（利用现有 status 字段） | 无 | 需加 version 字段 |
| **实现复杂度** | 低（一条 SQL） | 低（加 FOR UPDATE） | 中（需处理重试逻辑） |
| **回滚影响** | 失败不影响事务（返回 false） | 失败触发事务回滚 | 重试失败触发回滚 |
| **适用场景** | 低频高价值操作（支付回调） | 高冲突场景（秒杀库存） | 写少读多的业务表 |
| **项目实践** | `updatePendingToSuccess` 幂等闸门 | 会员续期 upsert 串行化 | 暂未使用（CAS 已覆盖） |

> **面试表述**："我们支付回调用 CAS 而不是悲观锁，因为支付回调是低频操作（每秒个位数），不需要串行等待。CAS 的 affected rows = 0 即幂等短路，比 FOR UPDATE 的等待超时更简洁。但会员续期场景用了 FOR UPDATE，因为需要精确计算续期起点，不能接受 CAS 失败后直接跳过。"

### L.2 数据同步方案对比

| 维度 | Outbox + Kafka + Flink | 实时双写 | 定时全量同步 |
|------|----------------------|---------|------------|
| **一致性等级** | 最终一致（事务内写入 + 定时兑底） | 强一致（同一事务） | 最终一致（周期性） |
| **数据延迟** | 秒级（Checkpoint 周期） | 零延迟 | 分钟~小时级 |
| **运维成本** | 中（需维护 Flink 作业 + Kafka） | 低（代码层直接写） | 低（定时任务） |
| **故障恢复** | Checkpoint 恢复 + Outbox 兑底重发 | 任一写入失败整体回滚 | 下次全量覆盖 |
| **写入压力** | 低（Kafka 缓冲 + Flink 批量） | 高（双份写入） | 周期性高压力 |
| **项目实践** | 课程/工具/秒杀 3 域 ES 同步 | 暂未使用（双写一致性难保证） | 早期 ES 重建索引时使用 |

> **面试表述**："我们选 Outbox + Kafka + Flink 而不是实时双写，因为双写在一个事务内写两份存储，任一失败都回滚，且没有故障恢复机制。Outbox 把消息持久化到本地表，即使 Kafka 宕机也能在恢复后重发。Flink 提供 Checkpoint 保证端到端一致性，比定时全量同步的延迟更低。"

### L.3 Redis 数据结构选型对比

| 维度 | Lua 脚本 | String + INCRBY | Set |
|------|---------|----------------|-----|
| **原子性** | 强原子（单线程执行） | 原子（单命令） | 原子（SISMEMBER/SADD） |
| **适用场景** | 多步判断+多步修改 | 计数型（库存增减） | 有/无判断（已购/未购） |
| **网络 RTT** | 1 次（全部在 Redis 执行） | 1 次/命令 | 1 次/命令 |
| **内存占用** | 无额外占用 | 8 bytes/Key | ~64 bytes/元素 |
| **项目实践** | 秒杀链路（预检+扣减+限购） | 库存计数器 | 用户已购集合 |

> **面试表述**："秒杀场景我们选 Lua 脚本而不是分步 INCRBY，因为需要‘检查库存→检查限购→扣减库存→记录用户’四步原子化，分步执行有竞态窗口。库存计数用 String+INCRBY 因为需要原子递减且需要精确数值。限购判断用 Set 的 SISMEMBER 因为只需知道‘有没有’。"

### L.4 搜索架构方案对比

| 维度 | ES 优先 + MySQL 兑底 | 纯 MySQL | 双索引别名切换 |
|------|---------------------|---------|------------|
| **查询性能** | 高（ES 倒排索引） | 中（全表/索引扫描） | 高（ES 倒排索引） |
| **降级透明度** | 高（用户无感知） | 无需降级 | 零停机切换 |
| **数据新鲜度** | 秒级（Flink 同步） | 实时 | 秒级 |
| **运维复杂度** | 高（需维护 ES + 同步链路） | 低 | 中（需维护 A/B 索引） |
| **适用场景** | 主搜索链路 | 简单查询/后台列表 | 索引结构变更（加字段） |
| **项目实践** | 课程/工具/秒杀主搜索 | 后台管理列表 | mapping 变更时重建索引 |

> **面试表述**："我们主搜索用 ES 优先 + MySQL 兑底，ES 查询超时或报错时透明降级到 MySQL。双索引别名切换只在索引结构变更时用——新建 B 索引、全量写入、切换别名，全程零停机。纯 MySQL 只用于后台管理列表这种简单场景。"

## 附录 M：MySQL 深度面试专题

> 基于 osh-backend 项目实际 SQL 优化案例，覆盖慢查询优化、索引设计、事务管理三大方向。

### M.1 SQL 性能优化七式（项目实战）

| # | 优化手法 | 项目场景 | 效果 |
|---|---------|---------|------|
| 1 | **CTE 外提嵌套计算** | 拼团用户最新参团记录查询：`WITH latest_record AS (SELECT ..., ROW_NUMBER() OVER(PARTITION BY group_id ORDER BY create_time DESC) AS rn FROM osh_group_user WHERE delete_flag=0) SELECT * FROM latest_record WHERE rn=1` | 可读性↑ + 优化器可规划更优执行计划 |
| 2 | **ROW_NUMBER 替代关联子查询** | `WHERE create_time = (SELECT MAX(create_time) ...)` 改为窗口函数，避免逐行关联 | 避免 N 次子查询 |
| 3 | **LAG/LEAD 时序计算** | 计算用户相邻操作时间差：`TIMESTAMPDIFF(SECOND, LAG(create_time) OVER(...), create_time)` | 替代自连接，可读性↑ |
| 4 | **预聚合 + LEFT JOIN** | 活动参与人数统计：CTE 预聚合 `GROUP BY activity_id` 后 LEFT JOIN 主表 | 避免主查询重复聚合 |
| 5 | **定时任务预聚合物化表** | 首页课程排行榜、秒杀热门榜 | 接口直查物化表，RT < 10ms |
| 6 | **条件下推** | "先查主表得 ID 集合 → 再 IN 到关联表做聚合"，而非在大表上全表聚合再过滤 | 减少聚合数据量 |
| 7 | **联合索引覆盖** | `idx_user_group_time(user_id, group_id, create_time)`，WHERE user_id=? AND group_id=? ORDER BY create_time DESC | 索引覆盖查询，避免回表 |

### M.2 索引设计原则（项目实例）

| 场景 | 索引设计 | 原理 |
|------|---------|------|
| 用户订单查询 | `idx_user_status(user_id, status, create_time)` | 等值条件在前 + 排序字段在后 |
| 秒杀活动查询 | `idx_status_time(status, start_time)` | 状态过滤 + 时间排序 |
| 拼团活动搜索 | `idx_status_max(status, group_max_num)` | 状态过滤 + 容量排序 |
| 支付流水查询 | `uk_order_no(order_no)` 唯一索引 | 幂等保证 + 快速定位 |

**索引设计三原则**：
1. **等值在前，范围在后**：`WHERE user_id = ? AND create_time > ?` → `idx(user_id, create_time)`
2. **高选择性在前**：user_id（几乎唯一）放在 status（只有几个值）前面
3. **覆盖查询优先**：如果查询只需要索引列，不需要回表，性能最优

### M.3 事务管理面试应对

| 追问 | 应对思路 |
|------|----------|
| 事务隔离级别用的什么？ | 默认 READ_COMMITTED。`@Transactional` 不指定 propagation 时是 REQUIRED（加入现有事务或新建） |
| 什么场景用 REQUIRES_NEW？ | 核心事务中调用非核心远程服务时，用 REQUIRES_NEW 隔离，远程调用失败不回滚主事务。如支付成功后发送通知邮件 |
| 事务传播有遇到过坑吗？ | AOP 自调用导致 `@Transactional(propagation = REQUIRES_NEW)` 不生效——`this.method()` 调用原始对象而非代理。用 `@Lazy` 自注入解决 |
| 大事务有什么风险？ | 事务时间过长会占用数据库连接池、影响并发。项目策略：核心流程同步（状态变更+库存+权益），非核心异步化（通知/日志/ES同步） |

### M.4 分页优化面试应对

| 追问 | 应对思路 |
|------|----------|
| 大表分页怎么优化？ | ① count=0 时短路返回，不执行分页 SQL；② 避免 `LIMIT offset, size`（offset 大时性能差），用游标分页 `WHERE id > lastId LIMIT size`；③ PageHelper 自动拦截并改写 SQL |
| 为什么不用 `SELECT *`？ | `SELECT *` 无法利用覆盖索引，且可能返回不需要的大字段（如 longtext）。项目用 VO 投影只查需要的列 |

## 附录 N：综合面试专题（Java/JVM + 监控 + 微服务 + 软技能）

### N.1 Java/JVM 高频面试应对

| 追问 | 项目实践 + 应对思路 |
|------|---------------------|
| 线程池参数怎么定的？ | 3 个命名线程池（DEFAULT/AGGREGATION/NOTIFICATION），核心线程数=CPU 核数，最大线程数=CPU×2，队列容量按业务量设置。拒绝策略 CallerRunsPolicy 保证不丢弃任务 |
| 为什么用 CallerRunsPolicy？ | 其他策略会丢弃任务或抛异常。CallerRunsPolicy 让调用线程自己执行任务，相当于“降级为同步”，保证任务不丢失。适合支付通知、权益发放这类不能丢的场景 |
| Spring Boot 自动装配原理？ | `@SpringBootApplication` 包含 `@EnableAutoConfiguration`，通过 `spring.factories` 加载自动配置类。项目排除了 `DataSourceAutoConfiguration`，手动配置 Druid 数据源（支持主从切换） |
| Spring AOP 和 JDK 动态代理区别？ | Spring AOP 默认用 JDK 动态代理（基于接口），如果目标类没实现接口则用 CGLIB（基于继承）。项目全部用 CGLIB（`proxyTargetClass=true`），因为 Service 类大多没实现接口 |
| JVM 调优做过吗？ | ① Flink TaskManager JVM Metaspace 从 256MB 调到 128MB（释放内存给 Task Heap）；② Spring Boot 启动加 `--add-opens` 解决 JDK 模块化反射限制；③ 全局 JVM 时区设为东八区解决时间偏移 8 小时问题 |
| HashMap 和 ConcurrentHashMap 区别？ | HashMap 非线程安全，ConcurrentHashMap 用 CAS + synchronized 锁住单个 Node。项目中拼团模块的 Map→VO 改造就是为了消除 Map 返回值的类型不安全问题，而不是解决并发问题 |

### N.6 定时任务专题（23 任务 + 6 类治理项）

> 项目共有 **23 个定时任务入口**（12 个 Spring @Scheduled + 11 个 XxlJob/Quartz），分布在 backstage-system 和 backstage-quartz 两个模块。

**面试表述**："我们项目有 23 个定时任务，用 Spring @Scheduled 和 XXL-Job 双调度器。我做了一次横向普查，发现 6 类治理项——最严重的是两套调度器同时跑同一逻辑，导致每分钟至少两次重复查询。"

**6 类治理项（按优先级）**：

| # | 治理项 | 严重度 | 问题描述 | 修复方向 |
|---|---------|--------|---------|----------|
| 1 | PayStatusUpdateTask 与 OrderCloseTask 功能重叠 | P0 | @Scheduled + XxlJob 同时跑关闭超时支付流水 | 二选一，XxlJob 可用时禁用 @Scheduled |
| 2 | GroupOrderTimeoutCancelTask 与 GroupTask 重叠 | P0 | @Scheduled 60s + Quartz 5min 竞争处理同一拼团超时订单 | 统一为一套实现 |
| 3 | SeckillActivityStatusTask 无事务保护 | P1 | 批量 updateToOngoing + 发 Outbox 事件无 @Transactional，某个 Outbox 写入失败会丢 ES 索引 | 加 @Transactional |
| 4 | SeckillActivityStatusTask select+update 非原子 | P1 | select 查 id IN (1,2,3) 但 update 无 WHERE id 条件，新到期活动被误更新 | update 加 `WHERE id IN (...)` |
| 5 | 同类两个 @Scheduled 方法 | P2 | InternalMemberFollowTaskScanTask 两个方法都 cron 5min | 合并或明确命名区分 |
| 6 | FeedbackCountRepairTask 僵尸代码 | P2 | @Scheduled 已注释但代码保留，无注释说明禁用原因 | 补充注释或删除 |

**标杆设计（可作为模板参考）**：
- **OutboxEventPublishTask**：markSending CAS + 指数退避（1m→5m→15m→1h）+ DEAD 兑底 + SENDING 超时恢复——最完善的 Outbox 投递链路
- **SeckillOrderTimeoutTask**：Lua 脚本原子归还库存 + updateOrderStatusWithCheck CAS + 单订单 try-catch

**定时任务开发五原则**：
1. **事务边界**：状态更新 + 副作用必须 @Transactional
2. **多实例互斥**：select + update 范围对齐（WHERE id IN）
3. **异常隔离**：单步骤独立 try-catch，一条失败不影响后续
4. **幂等设计**：重复触发时 CAS 或状态检查保证幂等
5. **生命周期**：禁用任务必须注释原因，禁止僵尸代码
