## 一、项目级 AI 协作规则（提取自 AGENTS.md）

### 1.1 强制 SDD / OpenSpec 工作流
本仓库对所有 AI 辅助开发执行 SDD + OpenSpec + harness 纪律。代码变更前每个 agent 必须阅读：
1. `docs/ai/README.md`；2. `docs/ai/02-workflow.md`；3. `openspec/project.md`；4. 当前变更 `openspec/changes/<change-id>/`（除非明确豁免）。

规则要点：
- 中大型代码变更没有 OpenSpec change 不得开工；
- 改 API 契约、权限、数据模型、中间件配置、部署行为、存储行为必须备齐 `proposal.md`、`design.md`、`tasks.md`、`specs/**/spec.md`；
- 保留用户改动，编辑限定当前任务范围；
- 运行相关验证并汇报精确结果；
- 微小变更豁免时，PR 必须带 `OpenSpec-Exempt: true` 及理由。

### 1.2 ZenTao MCP token 守卫（强制）
任何使用 `mcpServers.zentao` 的操作前必须执行：
```powershell
powershell -ExecutionPolicy Bypass -File .\bin\ensure_zentao_mcp_token.ps1 -ConfigPath .\MCP.json
```
规则：token 有效则继续；为空或过期则先请求账号密码刷新；禁止跳过此步骤。

## 三、项目介绍与架构

### 3.1 项目用户与角色双体系架构（project_introduction）
- B 端后台管理：RuoYi 框架的 sys_user、sys_role、sys_user_role 表，控制后台菜单与操作权限；
- C 端前台用户：自定义 osh_user、osh_role、osh_user_role 表，支持角色等级（level 0~5），新用户默认 role_id=1（普通用户）；
- 拼团模块所有业务表（osh_group_work、osh_group_order）的 user_id 均关联 osh_user.id，而非 sys_user.user_id。

### 3.2 C 端用户角色权限体系（project_introduction）
C 端用 osh_user/osh_role/osh_user_role/osh_permission/osh_role_permission 五张表管理用户、角色、权限及关联关系，其中 osh_user_role 支持 expire_time 过期时间控制。

### 3.3 C 端敏感操作权限角色限定规则（project_introduction）
group:work:create（用户发起拼团）和 group:user:add（手动添加用户参与）两个敏感操作权限仅授予 osh_role 表中 id=6（核心开发者）和 id=7（创始人）的角色，其他角色（id=1~5）无权执行。

### 3.4 拼团模块上线必须 SQL 脚本及执行顺序（project_introduction）
上线前必须按顺序执行 5 个脚本：
1. `init_group_base_data.sql`：字典(5类)+系统参数(12个)+活动模板(3套)，第 1 个执行（定时任务依赖其超时参数）；全新上线用精简版(165行)，增量上线用完整版(197行，含 activity_id 历史回填)；
2. `group_permission.sql`：C 端 API 权限(20 端点)注册到 osh_permission 并关联角色 1~7，敏感操作仅给 role_id=6/7；
3. `init_group_menus_and_perms.sql`：管理端菜单树+按钮权限，NOT EXISTS 防重复，依赖脚本 2；
4. `init_group_quartz_jobs.sql`：注册 7 个定时任务（初始暂停，需手动启用）；
5. `optimize_group_indexes.sql`：5 张核心表复合索引+唯一索引（含防重复参团 uk_activity_user），低峰执行。

编译验证：`mvn clean package -DskipTests`（必须带 clean，否则 JDK 21 下 AOP 报 NPE）。

### 3.5 拼团模块字典初始化脚本选型规则（project_introduction）
- `init_group_base_data.sql`（165 行）精简版：删除头部元数据、历史回填语句；
- `拼团模块字典数据脚本.sql`（197 行）完整版：保留历史数据回填逻辑；

### 3.17 安全认证双体系实现方案（expert_experience）
- **双 JWT 体系**（共享 ${token.secret}，HS512）：后台 TokenService（payload 只存 uuid，LoginUser 存 Redis，20 分钟续期，记录浏览器/OS/IP）；前台 JwtUtil（payload 直接存 userId，静态工具）；
- **SecurityConfig 过滤器链**：CSRF 禁用 + 无状态会话 + BCrypt；CorsFilter → OshAuthenticationFilter → UsernamePasswordAuthenticationFilter；@Anonymous 经 PermitAllUrlProperties 收集 URL 白名单动态放行；
- **OshAuthenticationFilter（254 行）流程**：WebSocket 握手直接放行 → 解析 Token → Redis 读登录态 → 设备踢出检测（activeToken 对比）→ 顺延会话 TTL（500 分钟）→ 实时查角色权限（非缓存，过期角色立即失效）→ ThreadLocalUtil 写入上下文（TransmittableThreadLocal）→ 构建 Security 上下文 → finally 清理 ThreadLocal；
- **WebSocket 认证**：TokenHandshakeInterceptor 从 ?token=xxx 解析 userId，失败拒绝连接；
- **认证失败**：AuthenticationEntryPointImpl 返回 JSON 401（Fastjson2）。

## 六、开发规范

### 6.1 阿里巴巴 Java 开发手册（黄山版）核心编码规约（development_code_specification）
osh-backend 所有 Java 代码编写与审查均须遵循（【强制】不可违反，【推荐】尽量遵循）。要点摘录：
- **命名**：类 UpperCamelCase；方法/变量 lowerCamelCase；常量全大写下划线；抽象类 Abstract/Base 开头；异常类 Exception 结尾；测试类 +Test；枚举 +Enum；禁拼音与中英混合；POJO 布尔字段禁 is 前缀；实现类 Impl 结尾；杜绝魔法值；
- **OOP**：覆写必加 @Override；常量放 equals 前面；包装类判等用 equals；BigDecimal 用 compareTo、禁 new BigDecimal(double)；禁 Map<String,Object> 直接输出须定义 DTO/VO；POJO 属性用包装类型；循环内拼接用 StringBuilder；
- **日期**：SimpleDateFormat 线程不安全，优先 DateTimeFormatter；年份用 yyyy 非 YYYY；
- **集合**：Arrays.asList 只读禁改；subList 不可强转；foreach 中禁 remove（用 Iterator）；Map key 必须重写 hashCode/equals；entrySet 遍历；
- **并发**：禁 Executors 建线程池（须 ThreadPoolExecutor 显式参数+有界队列）；线程池必须命名；锁必须 finally 释放；多资源锁固定顺序；ThreadLocal 用后必须 remove；定时任务用 ScheduledExecutorService 非 Timer；
- **异常**：禁 e.printStackTrace()（用 slf4j）；禁空 catch；捕获具体异常；转抛必带 cause；禁 finally 中 return；try-with-resources；@Transactional 必须 rollbackFor=Exception.class；事务内不做 RPC/耗时操作；
- **日志**：SLF4J 占位符 {}；异常日志必带堆栈（log.error("msg, p={}", p, e)）；
- **SQL**：表名字段名小写下划线；布尔 is_xxx；表必备 id/create_time/update_time；小数用 decimal；count(*)；禁 SELECT *；分页 count=0 直接返回；禁外键级联；in 集合 <1000；join ≤3 表；
- **安全**：用户输入必须校验防注入/XSS；密码禁明文；
- **单测**：AIR 原则；命名 should_预期结果_when_条件；覆盖边界与异常分支。

### 6.2 定时任务开发规范与审查要点（development_practice_specification）
1. 事务边界：涉及"状态更新+副作用（如发消息）"必须 @Transactional 保证原子性；
2. 多实例互斥：查询与更新用 WHERE id IN (...) 对齐范围，防多实例重复处理；
3. 异常隔离：每个子步骤独立 try-catch；
4. 幂等设计：重复执行的任务必须通过 CAS 或状态检查保证幂等；
5. 生命周期管理：禁用任务需注释原因或直接删除。

### 6.3 AI 调用事务边界规范（development_practice_specification）
AI 评分调用严禁放在 @Transactional 内部：先收集客观题分数和简答题 Prompt，提交事务后在事务外调 AI，最后小事务更新最终分数；避免长耗时 AI 请求占用数据库连接导致连接池耗尽。

### 6.4 CAS 失败处理规范（含拼团模块具体实现模式）（development_practice_specification）
- 规范：并发场景 CAS 失败应返回 false 而非抛 ServiceException，避免事务整体回滚导致业务状态丢失；
- 三种触发条件：并发超卖、活动已满、活动被删；
- 错误做法：CAS 失败直接 throw → @Transactional 回滚 → 用户已付款但订单显示待支付；
- 正确做法：CAS SQL（`UPDATE SET current_num=current_num+1 WHERE id=? AND current_num<max_num`）返回 0 时记 WARN 日志返回 false，调用方检查返回值差异化处理；
- 适用条件：方法在事务内、CAS 是业务核心步骤、调用方必须检查返回值（否则静默失败）；
- 日志策略：WARN 级别（可预见业务场景），含失败原因与关键标识（脱敏）。

### 6.5 OpenSpec SDD 四件套工作流与 PR 检查清单（development_practice_specification）
- 中大型变更（新功能、影响用户行为的修复、改接口/权限/支付/订单/库结构/中间件/架构边界）必须先建 OpenSpec change；

- 豁免：仅错别字、注释、无行为影响的小调整，PR 标注 `OpenSpec-Exempt: true` + 原因；
- PR 检查清单：接口兼容性、权限影响、数据缓存影响、本地构建/测试已运行、无密钥泄露、无临时文件提交；
- 实证样本：unify-alipay-payment-only、protect-book-comic-assets、add-object-storage-slimmer。

### 6.6 MyBatis-Plus 自动填充协同规范（development_practice_specification）
MetaObjectHandler 必须与实体字段 @TableField(fill=...) 注解配合，二者缺一不可：

### 6.7 考试模块并发与异常测试规范（development_test_specification）
单元测试必须覆盖并发与异常场景：针对收藏计数、交卷幂等、AI 失败处理等逻辑编写并发测试验证原子性；模拟 AI 返回 null 或超时，验证系统降级处理而非静默错误。

### 6.8 单元测试实践规范（双层测试+双路径用例+副作用验证）（development_test_specification）

## 七、业务模块实现方案（按业务域分组）

### 7.1 统一支付与订单权益体系

**7.1.1 统一支付模块架构与业务接入方案**
- 统一支付模块：OrderCheckoutReqVO/RespVO 统一下单出入参、支付流水表 osh_payment、支付配置迁移 Nacos；
- 回调 PayNotifyController 精简为核心分发，支付成功后经 MQ 异步转发各业务 handler，WebSocket 通知前端；业务按《业务模块接入支付模块说明》接入；
- 积分抵扣：updatePointsAtomic 用 SQL WHERE points>=cost 原子扣减防负余额；
- 高频坑：① 金额必须取实付总额 totalAmount 而非单价；② 主动查单与回调并发用 CAS 结果做幂等闸门；③ channel 参数需默认值；④ 资产扣减必须事务+原子 SQL。

**7.1.2 汇付支付网关接入与支付渠道抽象方案**
- 完整网关包：HuifuPayClient（544 行）、HuifuRsa2 RSA2 签名、HuifuHttpTransport、DTO/异常、HuifuPayNotifyService 回调验签；PaymentProviderEnum 抽象渠道；
- 签名核心规则：同步加签 canonicalize() 用 TreeMap 只排第一层，嵌套 JSON 以字符串传递；同步/异步验签分离——异步通知必须用未解析重排的 resp_data 原文，且验签在 JSON 解析之前；
- 私钥格式守卫：检测 PKCS#1（BEGIN RSA PRIVATE KEY）直接抛异常，强制 PKCS#8；
- resp_code 语义陷阱：异步外层 resp_code 是消息投递码，真实交易结果只能取已签名 resp_data 内的 resp_code/trans_stat；
- 回调终态：失败终态也须推进本地失败/关闭并退积分，事务提交后才返回 ACK（`RECV_ORD_ID_`+paymentNo）；
- 教训：第三方接入标准六件套（Client+签名+Transport+DTO+异常+NotifyService）；异步验签三铁律（验原文、验签先于解析、失败终态可靠 ACK）。

**7.1.3 支付成功消息防重复发送方案（消费确认+查单去重）**
- 支付成功消息存在"回调 + 主动查单"双来源，发送前必须查重（已发标记）；
- 消费端确认时机错误会导致重复消费，ACK 必须在业务处理成功后；
- 支付成功消息的幂等是防重复发货的第一道闸门。

**7.1.4 订单权益发放任务表与重试机制方案**
- 新表 osh_order_entitlement_task 记录发放任务与状态；OrderEntitlementTaskService 登记与执行；OrderEntitlementRetryTask 定时重试；
- 7 Handler 矩阵（幂等守卫）：GroupPaid（订单 CAS）、SeckillPaid（status==1 短路+CAS）、MemberPaid（grantStatus 短路）、ToolPaid（grantStatus+FOR UPDATE）、CoursePaid（countPaid 短路）、BookPaid（purchased 短路）、BundlePaid（子项逐项幂等，⚠️部分成功风险）；
- 链路真相：实际运行路径是同步事务（PayNotifyController → handlePayNotify → completePaidNotify 双 CAS → OrderPaidHandlerRegistry.handle）；注释中的 PaymentSuccessConsumer 是历史重构残留；
- 双 CAS 闸门：同一事务内先 payment CAS 再 order CAS，任一失败整事务回滚，避免"钱扣了订单没推进"；
- 教训：权益发放失败不回滚支付，只靠重试补偿；新 Handler 必须提供幂等短路+事务+失败快照。

### 7.3 内容资源管理与组件化架构

**7.3.1 首页通用组件化方案（公告栏+轮播图+卡片ES化）**

## 八、ES 搜索与 Flink 数据同步体系

### 8.1 ES 搜索索引同步标准链路（Outbox→Kafka→ES+降级查库）
- **ES 存储层三件套**：XxxEsDocument 文档实体 + XxxEsMapper（搜索/批量写/清空）+ XxxEsService（关键词+条件搜索、全量同步）；

- **mapping 管理**：独立 JSON 文件，title 用 ik_max_word 中文分词；提供 /esSync/all 全量同步接口；只索引已发布状态资源；状态时间敏感字段查询时动态推导不冗余存储；
- 必踩坑：① mapping 变更后必须全量重建；② 列表 VO 字段回填环节易遗漏新增字段；③ 草稿状态不发索引消息。

### 8.2 ES function_score 相关度算分排序方案（信息差搜索）
- 算分完全下沉 ES（删除 Java 侧自定义 rerank）；四组函数：① 编号精确命中 weight=1000 置顶；② 热度因子 fieldValueFactor（collectCount 0.45、goodCount 0.30、viewCount 0.08）；③ 时效高斯衰减（updateTime，scale 14d、offset 3d、decay 0.5）；④ scoreMode=SUM、boostMode=SUM、maxBoost 2000；
- 分页从内存窗口改为 ES 服务端分页；
- 教训：ES 排序优先 function_score；"全量拉取+内存排序+内存分页"是窗口瓶颈，算分应下沉服务端。
- 适用：实现 ES 相关度排序、热度+时效混合权重设计时。

### 8.3 新增筛选字段全链路贯通方案（实体到 ES 六处同步）

### 8.5 ES 索引 mapping 变更后缺少重建流程（common_pitfalls）

### 8.6 Flink Kafka→ES 同步作业治理清单（4 作业对比+6 类治理项）
- 4 作业：Course/GroupActivity/SeckillItem/Tool，各自消费独立 Topic 写独立索引；

## 九、基础设施与并发安全范式

### 9.1 跨模块并发安全标准范式（库存三重闸门+幂等发放模板）
- **范式一：库存扣减三重闸门（秒杀）**：① Redis Lua 前置原子扣减+边界；② DB 扣减 SQL 即闸门（`SET stock=stock-#{qty} WHERE id=? AND stock>=#{qty}`）；③ 归还双向封顶（LEAST 封顶库存 + GREATEST 防负销量）；
- **范式二：支付回调幂等发放（会员/工具套餐）**：① 行锁串行化（selectByOrderNoForUpdate）；② upsert 幂等续期（ON DUPLICATE KEY UPDATE，重复回调只续期不重复计数）；③ 双状态分离（pay_status 与 grant_status 独立，失败可人工补发）；
- **范式三：权益开通幂等守卫（电子书）**：订单反查 userId/bookId（不接受外部传参防越权）+ purchased==1 短路；购买查重返回通用 "access denied" 防业务探测；
- 已验证通过模块：秒杀、会员中心、工具套餐、核销码、电子书、拼团三级防线；
- 教训：新资金链路直接套用范式一+二；幂等优先用"条件更新影响行数"或 upsert；支付+发放两阶段必须双状态字段分离。
- 适用：新模块实现库存扣减/限量发放/支付回调权益发放/重复回调防护时。

### 9.2 高并发秒杀异步下单链路设计技能（learned_skill）
1. 预检占位：doSeckill 先 Redis Lua 原子扣库存+记已购数（String Key 支持多件限购），写 PENDING 占位，发 Kafka 立即返回；
2. 异步落库：SeckillOrderConsumer 扣 DB 库存、写订单、orderKey 更新为真实订单号；失败 Lua 回滚；
3. 结果查询：识别 PENDING；Redis Key 过期兜底查库；待支付一并返回二维码；
4. 超时取消：Quartz 每分钟扫 status=0 且过期订单，Lua 带上限回滚；
5. 上下文传递：消息体自带 stockKey/boughtCntKey/orderKey/expireSeconds/clientIp（消费者线程无 HTTP 上下文）；
6. 缓存 TTL 动态化：calcExpireSeconds(endTime, buffer) 与活动结束时间对齐，三档缓冲常量（24h/2h/2h）；
- 教训：标准架构 = Redis Lua 预检占位 + MQ 异步落库 + 兜底查库 + 定时取消兜底；Redis 增减必须 Lua 原子且加边界；限购计数用 String Key；TTL 禁止写死；消息体自包含全部上下文。
- 适用：设计高并发抢购链路、库存扣减与限购并发控制、活动类缓存过期策略时。

### 9.3 Outbox 模式实现可靠异步消息发布技能（learned_skill）
1. 本地事件表 osh_outbox_event + 完整重试模型字段（retry_count/max_retry_count/next_retry_time/last_error/sent_time）；
2. OutboxEventServiceImpl 与业务数据在同一数据库事务内登记事件；
3. 提交后即时发布双通道：有事务时注册 TransactionSynchronization 于提交后投递（避免读未提交数据），无事务时立即发布；
4. Quartz 任务 OutboxEventPublishTask 周期扫描兜底（指数退避 1m→5m→15m→1h + DEAD 兜底 + SENDING 超时恢复）；
5. Topic/事件类型常量集中 KafkaConstants；消费端按 eventType 分流；
- 教训：凡"写 DB + 发 MQ"场景统一走 Outbox，禁止内联直接 send；即时发布必须挂事务同步器在提交后触发；事件表带完整重试字段，消费端必须幂等。
- 适用：需要写库同时发 MQ、设计最终一致性异步通知、消息重试与兜底扫描机制时。

### 9.4 基于 Redisson 的声明式分布式锁技能（learned_skill）
- backstage-common 定义 @DistributeLock 注解（scene+key 拼锁键、expireTime、waitTime、releaseImmediately）；
- DistributeLockAspect 基于 Redisson，加锁双分支（waitTime==DEFAULT 与否）；获锁失败抛 DistributeLockException；finally 释放；
- 锁粒度细化到资源维度（如 `courseId:#id`）；配套单测；
- 教训：声明式注解+AOP 是标准姿势；TTL 需评估业务耗时（秒杀锁 30s→2min）；waitTime=0 抢不到立即失败；避免全局大锁。
- 适用：为并发写操作加分布式锁、资源级互斥控制、锁等待与释放策略配置时。

### 9.5 分布式锁键设计与用户上下文 API 使用规范（learned_skill）
**分布式锁反模式：禁止固定字符串全局锁键**：
- 后果：所有资源共用一把锁，无关操作互相阻塞；长耗时操作配 waitTime=0 是自相矛盾；
- 实证：课程/工具共用 `resource:operation` 全局锁；课程审核占锁 60 秒期间所有审核秒失败；拼团锁键缺来源维度；
- 正确实践：① 必须包含资源维度（`#request.id`）；② 跨模块隔离前缀；③ 非关键路径给 waitTime 3-5s 缓冲，长耗时禁 waitTime=0；④ 防重复提交场景按用户维度加锁（includeUserId=true）。
**用户上下文 API 语义纪律**：
- 错误用法：可能匿名场景调 getCurrentUserId()（未登录抛 NPE）后又判 null（死分支）；
- 正确：确认需登录→getCurrentCurrentUser()+判空；匿名可选→getCurrentUserIdSafely()；等级→Optional.ofNullable(getCurrentLevelSafely()).orElse(0)；异步线程池必须用 TtlExecutors 包装（裸 CompletableFuture 静默丢上下文）。
- 适用：为接口加分布式锁注解、设计锁键与等待策略、获取当前登录用户或等级、异步线程需要用户上下文时。

### 9.6 定时任务全量清单与重叠治理（23 任务+6 类治理项）
- 全仓 23 个定时任务入口：12 个 Spring @Scheduled（backstage-system）+ 11 个 XxlJob/Quartz（backstage-quartz）；
- 6 类治理：🔴 PayStatusUpdateTask 与 OrderCloseTask 双调度器重叠（应二选一）；🔴 GroupOrderTimeoutCancelTask 与 GroupTask.cancelExpiredOrders 重叠；🟠 SeckillActivityStatusTask 无事务保护（批量更新+Outbox 发布不原子，丢事件无法自愈）；🟠 select+update 非原子（update 缺 WHERE id IN 范围）；🟡 同类两个 @Scheduled 方法；🟡 已注释僵尸任务无说明；
- 标杆设计：OutboxEventPublishTask（CAS+指数退避+DEAD 兜底）；SeckillOrderTimeoutTask（Lua 带上限归还+单订单 try-catch）；
- 教训：双调度器重叠是最高频治理项；批量状态流转必须加事务；select 与 update 范围必须对齐；僵尸代码必须标注原因。

### 9.7 支付回调注册表模式与同步链路真相（learned_skill）
步骤：入口三重校验（签名/金额/提供方）→ 幂等短路（payment.status==SUCCESS 直接分发）→ 双 CAS 闸门（先 payment 后 order，同事务）→ 注册表路由（OrderPaidHandlerRegistry 按 bizType）→ 权益发放（失败写 entitlementTask 重试）→ 定时任务兜底。

### 9.8 CAS 乐观锁失败处理规范技能（learned_skill）
步骤：执行 CAS 获取影响行数 → 失败记 WARN 日志返回 false → 成功继续返回 true → 调用方检查返回值决定抛异常/重试/人工介入。输出：CAS 失败不触发事务回滚，保留中间状态。注意：CAS 失败属可预见业务场景，用 WARN 不用 ERROR；调用方必须检查返回值，否则静默失败。
- 配套技能：Java 服务层 CAS 失败安全处理与多数据源 ID 语义修复（方法返回 void→boolean；多数据源 ID 混淆时放弃业务字段间接查询，改用订单中精确 ID 直接定位；缓存清除用 Set 去重）；
- 适用：并发场景下的状态推进、库存递增、活动人数原子更新、支付回调等资金/名额相关场景；与 6.4 规范、7.4 拼团缺陷记录形成完整知识链；
- 历史实证：拼团支付回调满员场景——违反此规范曾导致用户已付款但订单状态丢失的事故；这是项目 P1 级强制规范。

## 十一、接口安全、权限与横切机制（common_pitfalls / expert_experience / project_introduction）

### 11.1 双权限体系边界：/pc 前缀接口禁止混用 B 端 @PreAuthorize（提交 81dd573a）
- Bug 类：InternalMemberAdminController 走 /pc/ C 端链路，却叠加 B 端 `@PreAuthorize("hasAuthority('internal:member:*')")` 与 ensureAdmin()，C 端登录态中没有这些 authority，接口全部 403；

- 教训：项目存在 B 端（RuoYi Spring Security authority）与 C 端（自定义 Filter + osh_role 体系）双权限体系；新增接口前先确认路径归属哪个认证链路，权限控制只在该链路对应机制内实现。
- 适用：双权限体系项目新增 /pc 接口做权限控制、排查已配置注解仍 403 时。

### 11.2 公开接口路径不得落入 /pc 认证前缀（提交 e688778b）
- Bug 类：Controller 标注 @Anonymous（免认证），但 @RequestMapping 路径 /pc/public/feedback 含 /pc 前缀，OshAuthenticationFilter 白名单规则中 /pc/ 默认需认证，注解生效但仍被 Filter 层先拦截返回 401；
- 修复：路径改为 /public/feedback，去掉 /pc 前缀；
- 教训：/pc/ 路径前缀约定为需登录认证接口，公开接口用 /public/ 或独立前缀；@Anonymous 注解与 URL 白名单必须配合一致；与 11.1 同源，都是双体系边界不清导致。
- 适用：新增免登录公开接口、排查已标 @Anonymous 仍 401 时。

### 11.3 Redis 会话必须滑动续期（提交 3eb4e258）
- Bug 类：OshAuthenticationFilter 从 Redis 读 `LoginUser:{userId}` 验证登录态，只在登录时设置 TTL（500 分钟），后续请求不续期，用户持续操作超过 TTL 后被踢出；
- 修复：Filter 每次有效请求主动 `redisCache.expire(loginUserKey, LOGIN_EXPIRE_MINUTES, TimeUnit.MINUTES)`；
- 教训：Redis 会话管理不能"只写不管"，必须每次有效请求续期（滑动过期）；建议 Spring Session setMaxInactiveIntervalInSeconds 或 Filter 层统一续期。
- 适用：实现自定义认证 Filter 管理 Redis 会话、排查用户操作中途被踢出时。

### 11.4 C 端敏感操作权限最小化授权（role_id=6/7）
- 规则：`group:work:create`（用户发起拼团）与 `group:user:add`（手动添加用户参与）两个敏感权限仅授予 osh_role 表 id=6（核心开发者）与 id=7（创始人），其他角色（id=1~5）无权执行；
- 实现：在 init_group_menus_and_perms.sql 与 group_permission.sql 中对敏感权限码增加 `AND (p.permission_code NOT IN (...) OR r.role_id IN (6, 7))` 条件，其余 `group:*` 权限对 role_id=1~7 全量开放；
- 适用：设计敏感操作权限、评审权限脚本、讨论越权风险时。

### 12.1 数据库数据一致性校验视图设计技能（learned_skill）
- 步骤：① 分析各表间关系和常见不一致场景（如活动 current_num 与实际参团数差异）；② 为每类问题创建独立 MySQL 视图，用 LEFT JOIN + CASE 聚合校验逻辑；③ 视图含 consistency_status 字段标识问题类型；④ 提供快速诊断查询（如 `SELECT * FROM v_xxx WHERE status != 'OK'`）；
- 注意：视图用 CREATE OR REPLACE 保证可重复执行；JOIN 条件需覆盖所有关联可能性（如活动可能来自系统模板或用户发起）；定期执行视图查询并告警关键问题。
- 适用：多张关联表的人数同步、状态匹配、孤儿记录校验需求。
- 配套：拼团模块已建配套一致性校验视图，与 7.4 拼团缺陷记录配套使用。

### 12.2 Java 服务层 CAS 失败安全处理与多数据源 ID 语义修复（learned_skill，9.8 完整版）
- 输入：服务方法中使用 CAS 更新；存在用户侧与系统侧不同数据源导致 ID 语义不一致（如 groupWorkId 在用户发起场景下实际为 initiatedId）；
- 步骤：① 方法返回类型 void→boolean 表达 CAS 成败；② 失败返回 false 而非抛异常，避免事务强制回滚导致业务状态丢失；③ 调用方根据返回值差异化处理（WARN 日志、保留中间状态）；④ 多数据源 ID 混淆时放弃业务字段间接查询，改用订单中已有精确 ID 直接定位；⑤ 缓存清除用 Set 去重；
- 注意：CAS 失败返回 false 的前提是调用方必须检查返回值；直接用订单内嵌 ID 的前提是该字段在所有场景均被正确赋值且非空。
- 适用：并发状态推进、资金/名额相关 CAS 更新、多数据源 ID 混淆排查。
- 实证：cancelExpiredOrders 中用户发起拼团 group_activity_id 实际存 initiatedId，改用 order.getGroupWorkId() 直接查 osh_group_work 修复（任务经验）。

### 12.3 订单取消处理器注册表模式（多业务取消策略解耦，expert_experience）
- 背景：订单超时关闭/取消时，秒杀、拼团、工具等不同业务需各自执行回滚（退库存、退点数、释放名额），原逻辑散落在定时任务中（release/20260628 df4db273）；
- 方案：OrderCancelHandler 接口（bizType() + handle(orderNo, paymentNo)）+ Registry；各业务实现 SeckillCancelHandler/GroupCancelHandler/ToolCancelHandler；注册表构造器注入 `List<OrderCancelHandler>` 自动收集，按 bizType() 建 Map 逐条 log 注册；handleIfPresent 容错（无匹配静默跳过）；Handler 内注入业务 Service 用 `@Lazy @Resource` 破环；SeckillCancelHandler 提供 syncUnifiedOrder 参数控制是否同步取消统一订单；
- 教训：多业务横切动作（取消/支付成功）统一用"接口 + 注册表 + 构造器注入 List 自动收集"，新业务只加 @Component Handler 不改主流程；与支付成功 PaidHandler 形成对称设计；超时取消定时任务只扫单，回滚全部委托 Handler。
- 适用：新业务模块接入订单取消回滚、设计多业务横切分发机制、解决 Handler 与 Service 循环依赖时；与 9.7 支付回调注册表模式配套。

## 十三、常见陷阱经验库（common_pitfalls_experience，按缺陷域分组）

### 13.1 OSS/R2 签名域（全仓最高频缺陷域，跨 4+ 分支 5+ 提交）
- **临时签名 URL 存库导致裂图**（9195694b）：富文本 textContent 存了含 X-Amz- 参数的临时 URL，过期后裂图；修复：新增批量获取临时 URL 接口 POST /content/image-urls，前端传相对路径列表，后端 getLimitedUrl 动态签名；旧数据提取 fileKey 重签；教训：OSS 临时签名 URL 不应存库，应存相对路径（fileKey）展示时动态签名；
- **完整 OSS URL 需提取 objectKey 按白名单重签**（84fbf75a，qa/20260708）：图书模块历史数据存完整对象 URL，resolveBookAssetUrl 对 http 直接放行导致私有桶 403；修复：resolveManagedObjectKey() 解析 host，仅匹配 publicDomain/endpoint 或 R2 桶域名（*.r2.cloudflarestorage.com 且 path 以 bucket 开头）时剥离 bucket 前缀提取 objectKey，再 getLimitedUrl(objectKey, 120)；外部域名原样返回；教训：禁止无差别签名所有 http 地址；
- **同域其他历史修复**：路径重复 e0ed08ae、递归漏签 991d047b、下载 1ac43347；
- 治理建议：建立统一签名工具方法 + 检查清单（见 14.2 频率排行）。
- 适用：任何涉及私有桶资源展示/下载/存库的场景。

### 13.2 Redis 边界与生命周期域（集中于 master 秒杀模块）
- **库存归还超限需 Lua 加边界**（14a0edb4）：直接 increment 无上限校验，并发回滚出现幽灵库存；修复：RETURN_STOCK_SCRIPT 原子归还 `math.min(cur+qty, total)`（total 先查库）+ DB 侧对称防护 `LEAST/GREATEST`；教训：Redis INCR/DECR 不带边界，关键计数必须 Lua 原子+边界，归还永远加上限，上限以 DB 为准；与 9.1 范式一配套；
- **数据结构选型错误致限购只支持单件**（05e6d5c5）：限购用 Set（SISMEMBER）只能判有无，无法记数量；修复：改 String 计数器 `seckill:bought_cnt:{activityId}:{itemId}:{userId}` + GET 判断 + INCRBY/DECRBY；教训：限购用计数器（String+INCRBY）而非 Set；Set 只适合有/无判断；
- **流程 Key 未在终态释放致误拦截**（dc573b21）：seckill:order:{...} 防重提交 Key 支付成功后未删，用户再购被误判"订单处理中"；修复：SeckillPaidHandler.handlePaid() 主动 delete(orderKey)；教训：Redis Key 设计必须明确生命周期与职责边界，支付成功/取消/超时等终态事件都应检查是否清理关联 Key；
- 适用：Redis 库存/限购/防重/会话等一切计数与状态 Key 设计。

### 13.3 支付金额与订单域（跨 2 分支 4 提交）
- **支付金额取单价而非实付总额**（5135e950）：createPay 传 order.getSeckillPrice()（单件价）而非 totalAmount，多件购买少付款；修复：改传 totalAmount，实体+建表 SQL 同步新增字段；教训：支付金额是最高敏感字段，必须确认传"实付总金额"；建议参数命名区分 unitPrice/totalAmount + 入口断言 totalAmount >= unitPrice*quantity；
- 同域历史修复：订单号枚举调用错误 e38d72ce、二维码回退 9912db31、积分兼容 1ea73698（见 14.2）；
- 适用：调用支付接口、新增多件购买/金额计算功能时。

### 13.4 权限双体系域（跨 2 分支 3 提交）

### 13.5 状态机与字典域
- **审核状态硬编码映射致静默失效**（ff4d2eab）：ResourceAuditServiceImpl 中 `status==1 ? 4 : 6` 与业务表状态码定义不一致，审核写入错误状态；修复：直接透传前端 status；教训：状态流转由状态机/枚举严格定义，禁止裸数字硬编码映射，`status == 1 ? 4 : 6` 是危险信号；
- **组团状态字典与代码状态机不一致**：init_group_base_data.sql 字典只定义 3 态，代码实际用 4 态（0=待支付/1=已支付待成团/2=已成团/3=已取消）；修复模式：对照 ServiceImpl 中 setGroupStatus(N) 逐条反推字典；教训：数据字典脚本必须由代码状态赋值逻辑反推生成，不能凭业务直觉臆测；上线前 SELECT 验证 dict_value 与代码所有状态值一一对应；另注意 osh_group_user_initiated.group_status（0=招募中/1=已成团/2=已结束）与 work 表语义不同需单独字典类型；
- **状态检测定时任务缺异常恢复方向**（47ccf100）：见 10.3。
- 适用：实现审核/审批状态流转、编写字典初始化脚本、状态检测定时任务时。

### 13.7 环境与工具域（跨平台/构建/本地工具）
- **@JsonFormat 缺 timezone 致时间偏移 8 小时**（14a0edb4）：Jackson 默认 UTC 而服务器/数据库均 GMT+8；修复：所有 Date 字段补 `@JsonFormat(pattern=..., timezone="GMT+8")`；建议全局 spring.jackson.time-zone=GMT+8；
- **雪花 ID 写入 INT 列被截断**（a13289a5）：osh_user_exam_record 的 user_id/exam_id 建表为 INT，雪花 bigint 超范围，本地已迁移正常而 QA/生产报 Data truncation；修复：MODIFY COLUMN bigint(20) + 可重复执行脚本（sql/2026/07/fix_user_exam_record_user_id_bigint.sql）低峰执行；教训：凡存雪花 ID 的列一律 BIGINT；"本地正常、线上截断"优先怀疑环境间表结构不一致；
- **Nacos server-addr 带 http:// 前缀致 macOS 启动卡死**（7118fa44）：见 10.5；
- **JDK 21 反射访问 Proxy.h 需 --add-opens**：JDK 17+ 强制模块化，MetaObject.getValue('h') 被 InaccessibleObjectException 拒绝；修复：backstage-admin/pom.xml 的 spring-boot-maven-plugin 配 fork=true + 三条 --add-opens（java.base/java.lang、java.base/java.lang.reflect、java.base/java.util=ALL-UNNAMED）；解包机制：while(hasGetter('h')) 循环读 Proxy.h 获 InvocationHandler → while(hasGetter('target')) 读 Plugin.target 获真实 StatementHandler；预防：JDK 17+ 反射密集型框架必须预配 --add-opens，不可降级 JDK；不适用于 JDK 8/11；
- **PowerShell 调用 java.exe 需 & 操作符加绝对路径**：直接 `java -version` 可能因别名冲突/PATH 解析异常报 NativeCommandError（实际已运行）；稳定方式：`& "绝对路径\java.exe" -version`；
- 适用：新实体 Date 字段、建表定 *_id 列类型、JDK 17+ 升级/反射报错、PowerShell 环境验证时。

### 13.8 防重与校验域（邀请类操作，1f535f56）
- Bug 类：批量邀请只校验邮箱格式正则与"是否已注册"，无域名 MX 校验、无待使用邀请去重索引（Redis 只有 token→data 正向键），同一邮箱可反复生成邀请、虚构域名也能发邀请；
- 修复：新增 `admin:invite:email:{email}` 反向索引，重复创建提示"已有未使用的邀请链接"；新增 DNS MX 查询（InitialDirContext）校验域名邮件服务存在性；
- 教训：Redis 资源需"按业务键查重"时必须同时建业务键→token 反向索引，只存 token→data 无法防重；邮箱类输入除格式正则外应做 MX 校验。
- 适用：邀请/验证码类按业务键防重功能、邮箱有效性校验时。

### 13.9 日志与可观测域（a7366f06）
- Bug 类：SeckillOrderTimeoutTask 日志模板写 "seckillNo={}" 但传入变量实际是 orderNo，拿订单号搜不到日志误导排查；
- 教训：日志占位符名称必须与变量语义一致，尤其定时任务/消费者这类只能靠日志排查的场景；错误的日志比没有日志更有害。
- 适用：编写定时任务/消费者日志时。
