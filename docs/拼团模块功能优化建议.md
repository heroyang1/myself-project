## 一、性能优化 🔧

### 1.1 索引优化【P0 - 已通过 `optimize_group_indexes.sql` 解决】

**问题**：现有索引覆盖不足，关键查询走全表扫描

| SQL | 现有索引 | 问题 | 优化方案 |
|-----|----------|------|----------|
| `selectMyGroupList` | `idx_user_id` | 排序字段 join_time 不在索引中,filesort | 联合索引 `(user_id, group_status, join_time DESC)` |
| `selectGroupWorkList` | `idx_group_activity_id` | 查 group_status + ORDER BY 走全表 | 联合索引 `(group_status, join_time DESC)` |
| `selectTimeoutOrders` | `idx_status` | 范围扫描 `created_time` 不在索引中 | 联合索引 `(status, created_time)` |
| `checkUserJoined` | 单列索引 × 2 | 应用层校验可被绕过 | **唯一索引** `(group_activity_id, user_id)` 防重复 |
| `osh_payment` | 单列 `payment_no` | 子查询 `MAX(id)` 扫描子表 | 联合索引 `(payment_no, delete_flag, id DESC)` |

**关键SQL示例**：
```sql
-- 【优化前】EXPLAIN 结果: type=ref, Extra=Using filesort
SELECT * FROM osh_group_work
WHERE user_id = 100 AND group_status = 0
ORDER BY join_time DESC;

-- 【优化后】type=ref, Extra=Using index condition; Using where
-- 添加联合索引 (user_id, group_status, join_time DESC)
```

### 1.2 SQL 查询优化【P0】

#### 问题 1：`selectMyGroupList` 3 表 UNION ALL JOIN
**位置**：`OshGroupServerMapper.xml` L126-194

**当前SQL结构**：
```sql
SELECT ... FROM osh_group_activity ga
LEFT JOIN osh_group_work gw ON ga.id = gw.group_activity_id
LEFT JOIN osh_group_order go ON gw.order_id = go.id
WHERE gw.user_id = #{userId}
UNION ALL
SELECT ... FROM osh_group_user_initiated gui
LEFT JOIN osh_group_activity ga ON gui.activity_id = ga.id
LEFT JOIN osh_group_order go ON gui.order_id = go.id
WHERE gui.user_id = #{userId} AND gui.delete_flag = 0
ORDER BY join_time DESC
```

**问题**：
- UNION ALL 后再做 ORDER BY，无法利用索引顺序
- 两段 SQL 都需要排序，filesort 开销大

**优化方案**：
```sql
-- 方案A：分别查询后在Java层合并（推荐）
List<MyGroupListVO> joinedList = mapper.selectJoinedGroup(userId, status);
List<MyGroupListVO> initiatedList = mapper.selectInitiatedGroup(userId, status);
List<MyGroupListVO> merged = Stream.concat(joinedList, initiatedList)
    .sorted(Comparator.comparing(MyGroupListVO::getJoinTime).reversed())
    .limit(pageSize)
    .collect(Collectors.toList());

-- 方案B：利用 MySQL 8.0 窗口函数 + 覆盖索引
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY source_type ORDER BY join_time DESC) AS rn
    FROM (...)
) t WHERE rn <= #{pageSize};
```

#### 问题 2：`selectGroupUsers` 子查询性能
**位置**：`OshGroupServerMapper.xml` L211-215
```sql
IF(gw.id = (SELECT MIN(gw2.id) FROM osh_group_work gw2 
             WHERE gw2.group_activity_id = #{groupActivityId}), TRUE, FALSE) AS is_leader
```

**问题**：每个参团记录都要执行子查询，O(N²) 复杂度

**优化方案**：
```sql
-- 改为 LEFT JOIN + GROUP BY
SELECT gw.id, ..., 
       IF(gw.id = MIN(gw.id) OVER (PARTITION BY gw.group_activity_id), TRUE, FALSE) AS is_leader
FROM osh_group_work gw
-- 或在Java层排序后取第一个标记为团长
```

### 2.2 状态机不闭环【P0】

**问题**：支付成功回调 `handlePaymentSuccess` 只处理 `osh_group_user_initiated` 表，但**未处理系统活动模板**（`osh_group_activity` + `osh_group_work`）

**当前代码**（`OshGroupServerServiceImpl.java` L1238-1330）：
```java
public boolean handlePaymentSuccess(String orderNo) {
    // ... 更新订单为 paid ...
    
    Long groupWorkId = order.getGroupWorkId();
    OshGroupUserInitiated initiated = userInitiatedMapper.selectById(groupWorkId);
    if (initiated == null) {
        logger.warn("用户发起拼团记录不存在，groupWorkId={}", groupWorkId);
        return true; // ⚠️ 静默返回，系统活动模板支付后未更新 current_num 和状态
    }
    // ...
}
```

**优化方案**：
```java
public boolean handlePaymentSuccess(String orderNo) {
    // 1. 查询订单
    OshGroupOrder order = mapper.selectGroupOrderByOrderNo(orderNo);
    
    // 2. 幂等检查
    if ("paid".equals(order.getStatus()) || "success".equals(order.getStatus())) {
        return true;
    }
    
    // 3. 更新订单状态
    mapper.updateOrderStatus(order.getId(), "paid", LocalDateTime.now());
    
    // 4.【新增】判断数据源
    Long groupWorkId = order.getGroupWorkId();
    if (groupWorkId != null) {
        OshGroupUserInitiated initiated = userInitiatedMapper.selectById(groupWorkId);
        if (initiated != null) {
            handleUserInitiatedPayment(initiated, order); // 用户发起的拼团
        } else {
            handleSystemActivityPayment(groupWorkId, order); // 系统活动模板
        }
    }
    
    // 5.【新增】发送通知（站内信/微信模板消息）
    notificationService.sendJoinSuccessNotice(order);
    return true;
}

private void handleSystemActivityPayment(Long groupWorkId, OshGroupOrder order) {
    // 更新 osh_group_work
    OshGroupWork work = mapper.selectGroupWorkById(groupWorkId);
    mapper.updateGroupWorkStatus(work.getId(), 1); // 标记为已支付
    
    // 更新 osh_group_activity.current_num + 检查是否成团
    int newNum = work.getGroupActivityId().getCurrentNum() + 1;
    int status = newNum >= work.getGroupActivity().getGroupMinNum() ? 2 : 1;
    mapper.updateGroupActivityWithLock(work.getGroupActivityId(), newNum, status, ...);
    
    // 成团时分配服务器
    if (status == 2) {
        serverAssignService.assignServer(work.getGroupActivityId());
    }
}
```

### 2.3 并发安全问题【P0】

**问题 1：活动人数超卖**
**位置**：`OshGroupServerMapper.xml` L300-310
```sql
UPDATE osh_group_activity
SET current_num = #{currentNum}
WHERE id = #{id} AND current_num = #{currentNum} - 1
```

**风险**：
- 乐观锁条件 `current_num = #{currentNum} - 1` 依赖调用方传入的 currentNum
- 高并发场景下，可能多个请求同时读到 current_num=4，都尝试写入 5，导致 ABA 问题

**优化方案**：
```sql
-- 方案A：使用原子递增 + CAS 模式
UPDATE osh_group_activity
SET current_num = current_num + 1,  -- 原子递增
    status = CASE
        WHEN current_num + 1 >= group_min_num THEN 2  -- 成团
        WHEN current_num + 1 >= group_max_num THEN 3  -- 已结束
        ELSE status
    END,
    update_time = NOW()
WHERE id = #{id}
  AND current_num < group_max_num;  -- 容量限制

-- 检查 affected_rows
-- 若为0，说明已满员或活动已结束，回滚事务
```

**问题 2：成团后服务器分配竞争**
**当前代码**：成功成团后 `userInitiatedMapper.updateServerTime` 仅设置当前团的时间，未限制**同一资源被多次分配**

**优化方案**：
- 增加 `server_assignments` 表，记录服务器ID → 拼团ID 的一对一映射
- 在 Service 层加分布式锁（Redis SETNX 或 Redisson）

## 三、数据一致性保障 🛡️

### 3.1 活动状态与人数一致性【P0】

**当前问题**：
- `osh_group_activity.current_num` 是冗余字段（实际数据在 `osh_group_work`）
- `joinSystemActivity` 增加人数，但 `handlePaymentSuccess` 不增加（事件触发遗漏）
- 无定时任务补偿（已通过 `groupTask.refreshActivityCurrentNum` 解决）

**增加数据校验 SQL**（管理后台菜单使用）：
```sql
-- 数据一致性校验视图
CREATE OR REPLACE VIEW v_group_data_consistency AS
SELECT 
    ga.id AS activity_id,
    ga.title,
    ga.current_num AS stored_num,
    COUNT(gw.id) AS actual_num,
    ga.current_num - COUNT(gw.id) AS diff
FROM osh_group_activity ga
LEFT JOIN osh_group_work gw 
    ON ga.id = gw.group_activity_id AND gw.group_status IN (0,1)
GROUP BY ga.id, ga.title, ga.current_num
HAVING diff != 0;
```

### 3.2 订单与支付状态一致性【P0】

**当前问题**：
- `osh_group_order` 和 `osh_order` 是双写关系（拼团支付链路要求）
- `handlePaymentSuccess` 只更新 `osh_group_order`，未联动 `osh_order`
- 订单状态在两个表间可能出现不一致（已支付、已取消等）

**优化方案**：
```java
// 统一封装订单状态变更
@Transactional(rollbackFor = Exception.class)
public void updateOrderStatus(String orderNo, String status) {
    // 1. 更新拼团订单
    groupServerMapper.updateGroupOrderStatus(orderNo, status);
    // 2. 同步更新通用订单(支付链路)
    oshOrderMapper.updateStatusByOrderNo(orderNo, mapToOshOrderStatus(status));
    // 3. 记录状态变更日志
    orderStatusLogMapper.insert(orderNo, status, "system");
}
```

**问题**：`server_expire_time` 字段同时存在于 `osh_group_work` 和 `osh_group_user_initiated`，且需要与 `osh_group_activity.server_end_time` 一致

### 3.4 activity_id 字段反查一致性【P0 - 已修复】

**历史问题**：`osh_group_user_initiated.activity_id` 字段缺失（已通过 `fix_group_table_structure.sql` 修复）

**当前状态**：

### 5.4 SQL 注入防护【P0 - 已基本解决】

**检查所有动态 SQL**：

### 5.5 日志脱敏【P2】

**当前日志**：`logger.info("用户 {} 参与用户发起的拼团，记录ID: {}", userId, activityId);`
- ✅ 用户ID脱敏（输出ID而非手机号）
- ❌ 订单号、服务器IP等敏感信息可能泄露

**优化方案**：
```java
// 统一日志脱敏工具
public class LogMaskUtil {
    public static String maskOrderNo(String orderNo) {
        if (orderNo == null || orderNo.length() < 8) return "***";
        return orderNo.substring(0, 4) + "****" + orderNo.substring(orderNo.length() - 4);
    }
    public static String maskIp(String ip) {
        if (ip == null) return null;
        String[] parts = ip.split("\\.");
        if (parts.length == 4) {
            return parts[0] + "." + parts[1] + ".***.***";
        }
        return "***";
    }
}
```
