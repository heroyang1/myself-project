# AI 治理组件落地 Playbook（可跨项目复用）

> 用途：把《Harness 工程方法论_学习笔记.md》里的理论，落成"照着提示语就能在任意项目复刻"的操作手册。
> 每个组件固定五段：**它解决什么 → 可复用提示语 → 实现过程（本次实际走的）→ 验收清单 → 换项目怎么改**。
> 配套：方法论见同目录学习笔记；本文只讲"怎么做"。

---

## 0. 三条贯穿全程的工作约定（先立规矩，再动手）

这三条不是某个组件的规则，是**所有落地动作的公共前提**，换任何项目都适用：

| 约定 | 做法 | 为什么 |
|---|---|---|
| **两段式写入** | 任何文件先只输出**草稿/大纲**，人确认后才落盘 | 防止 AI 一次性写歪、返工成本大 |
| **先取事实后出稿** | 写之前先 grep/实扫代码拿真实锚点（枚举值、接口路径、字段类型），不靠记忆 | AI 记忆有两个污染源：预训练通识 + 上个会话旧快照 |
| **落盘四查** | 写完立即查：①行数达标 ②每条红线有判据 ③索引路径逐个打开（无悬空）④命名口径一致 | 一条错指针（幽灵指针）比没有指针更坏 |

> 提示语里凡是"先只输出草稿，不要写入文件""结合真实代码""列出实际改动清单"这类句子，都是这三条约定的落地。

## 1. 组件总览与建设顺序

| 顺序 | 组件 | 路径 | 一句话作用 |
|---|---|---|---|
| ① | 项目宪法 | `CLAUDE.md` | 每轮常驻的红线 + 去哪找细则的索引 |
| ② | 任务路由表 | `.harness/ROUTING.md` | 动手前"该加载什么"的查表入口 |
| ③ | 暂存区规则 | `.harness/candidate/README.md` | 把"AI 发现"和"成为事实"隔开 |
| ④ | 五层知识库 | `.harness/wiki/*.md` | 项目知识按内容分层，按需装载 |
| ⑤ | 专项规范 | `.harness/<主题>规范.md` | 某类细则的单一事实源（示例：外部依赖） |
| ⑥ | SDD 契约 | `spec/<能力>.md` | 一个功能的可判定验收契约 |
| ⑦ | SDD 执行 | `spec/<能力>-impl/` | 按契约圈定范围生成的代码 + 测试 |

> 建议按 ①→⑤ 先建"治理底座"，⑥⑦ 是"用底座跑一个真实变更"的演练。

## 2. 组件① · 项目宪法 `CLAUDE.md`

**它解决什么**：给 AI 一份"每次都必须知道"的短宪法——身份、红线、去哪找细则。

**可复用提示语**：
```
基于本项目的 README、构建文件、目录结构，生成项目宪法 CLAUDE.md v1.0，要求：
- 五层结构齐全：①项目身份 ②核心约束(红线) ③规范索引 ④技能索引 ⑤沟通原则
- 红线层只放"可判定 + 有机器抓手(CI/工具能拦)"的 critical 项，每条挂一个抓手；无抓手的诚实标注"有红线无门禁"
- 索引层只写"内容 → 位置 → 装载方式"，不抄正文
- 所有引用路径必须先核验真实存在
- 全文 ≤100 行
先只输出草稿，不要写入文件。
```

**实现过程（本次）**：核验每个待引用路径存在性 → 出草稿 → 用户确认 → 写入 → `wc -l` 复验压到 ≤100 行。

**验收清单**：
- [ ] 行数 ≤100（超出先删/外置）；
- [ ] 每条红线有"可判定"表述 + 抓手（无抓手的写明缺口）；
- [ ] 索引指向的路径逐个打开都在；
- [ ] 命名口径与代码一致（grep 核对）。

**换项目怎么改**：替换技术栈基线、保护域清单（哪些文件改动必须走流程）、CI 抓手名称。没有 CI 的小项目，抓手可写"人工 review"，但要诚实标"无自动门禁"。

## 3. 组件② · 任务路由表 `.harness/ROUTING.md`

**它解决什么**：把"这次该加载哪些文档"从临场发挥收敛为动手前查表。

**可复用提示语**：
```
建立 .harness/ROUTING.md，含三张路由表：
- 表1 任务类型 → 该加载的文件
- 表2 文件 glob → 对应规则文件
- 表3 需求/变更类型 → 处理管道（无技能体系的项目可留骨架）
纪律：全文 ≤150 行；每行只允许"键→加载项"一个映射；只收经人确认的条目，AI 不得自行加行；
"一条规则只有一个家"——与宪法重叠的行改成指针（如"见 CLAUDE.md 第X层"），不复制正文。
内容可先留骨架，逐条填。
```

**实现过程**：先立三表头 → 逐讲/逐任务填 → 与宪法重叠处改指针 → 行数复验。

**验收清单**：
- [ ] 无与宪法双写同一规则的行（重叠即改指针）；
- [ ] 每条加载项路径真实存在；
- [ ] ≤150 行。

**换项目怎么改**：表2 的 glob→规则映射按本项目目录结构填；无自动装载通道的项目，装载方式一律如实标"手动·命中即读"，不伪装自动。

## 4. 组件③ · 暂存区规则 `.harness/candidate/README.md`

**它解决什么**：防止 AI 把自己"猜的"写进文档、下个会话当事实读，形成污染闭环。

**可复用提示语**：
```
生成 .harness/candidate/README.md 写清暂存区规则：
- 四步流水线：AI 发现 → 写进 candidate(标"未确认") → 人工确认 → 才进事实源
- 四类可进：合理推断/未入档事实/红线提案/违例记录；三类禁进：已验证事实/聊天噪音/密钥日志
- 每条四字段模板：来源·发现时间·置信度·状态；置信度分级(高=可复现实测/中=多处观察/低=单次印象，给不出证据只能填低)
- 晋升仅人可执行，AI 改状态字段=越权
- candidate 内容禁止当事实引用、禁止据此生成代码
```

**实现过程**：按模板写规则 → 本地化"晋升出口"（本项目事实源在哪，就写进哪，如 docs/宪法/openspec）→ 加"容量上限 + 定期清退"。

**验收清单**：
- [ ] 四步流水线、进出规则、置信度、晋升权、禁引用五块齐全；
- [ ] 晋升出口指向本项目真实存在的事实源。

**换项目怎么改**：把"晋升出口"替换成本项目的事实源位置；无 openspec 的项目，出口写"docs/ 或宪法红线区"。

## 5. 组件④ · 五层知识库 `.harness/wiki/`

**它解决什么**：项目知识按内容分层，让"该读哪一层"变成可精确判断的事。

**可复用提示语**：
```
参照五层知识库结构，为每个项目建 .harness/wiki/ 下五个文件：
业务模型.md / 接口协议.md / 数据模型.md / 领域术语.md / 事故复盘.md。
要求：
- 每个文件首行写"装载时机"，且写成触发事件（"修 bug、改并发时读"），不写话题标签（"相关"）
- 内容必须锚定实扫代码事实（枚举值/接口路径/字段类型），不复制既有文档正文，只做"摘要 + 指针"
- 领域术语层重点收"项目含义 ≠ 通用含义"的词，配四列对照(通用误解/项目真义/误读后果/代码证据)
- 事故复盘层每条带编号(A-01…)，指向案例全文的唯一住所
先出结构与大纲，确认后再落盘。
```

**实现过程（本次）**：先 grep/读代码取锚点（枚举值、控制器路径、字段类型）→ 按样例粒度出大纲 v2 → 用户确认 → 五文件落盘 → 立 change → ROUTING 表1 登记路由 → 宪法加索引行。

**验收清单**：
- [ ] 每文件首行"装载时机"是触发事件；
- [ ] 写进去的每条"事实"都有代码证据（可 grep 到）；
- [ ] 与既有文档无双源（只指针不复制）；
- [ ] 从宪法迁出的词条已确认目的地存在（"应该在那边"≠"在那边"）。

**换项目怎么改**：五层内容全按本项目代码重锚；没有独立"事故复盘"素材的项目，先建空壳 + 编号规范，随踩随填。

## 6. 组件⑤ · 专项规范 `.harness/<主题>规范.md`（示例：外部依赖）

**它解决什么**：把某一类反复用到的细则（线程池/超时/熔断等）收拢成单一事实源，宪法里只留一行索引。

**可复用提示语**：
```
把 <某主题> 的细则收拢成一份规范文档 .harness/<主题>规范.md：
- 分节，每节开头以"什么时候读这份规范"起手，写成触发形态（review 到 XxxYyy 时、new 某对象时）
- 只放结论与判据，示例要可 grep；参数给"标准值 + 为什么是这个值"
- 需要晋升为红线的句子只标"候选，待拍板"，不复制宪法正文（避免双事实源）
先在对话里出大纲 + 宪法索引行，未落盘。
```

**实现过程**：对话出大纲 → 确认 → 落盘（规范层不受 100 行限制，别把宪法预算套进来）→ 宪法第 3 层加一行索引（同时压缩等量冗余行抵"行数税"）→ 立 change。

**验收清单**：
- [ ] 每节有"什么时候读"；
- [ ] 无复制宪法正文；
- [ ] 宪法加索引后仍 ≤100 行。

**换项目怎么改**：主题随项目变（新项目可能是"日志规范""错误码规范""发布流程规范"）；套路一致：分节 + 触发式开头 + 判据可 grep。

## 7. 组件⑥ · SDD 契约 `spec/<能力>.md`（第①步·定规范）

**它解决什么**：动手写代码前，先把一个功能的规则、异常、改动范围写成可判定契约。

**可复用提示语**：
```
按 SDD 第①步"定规范"，为 <能力名> 写 spec/<能力>.md：
- 业务规则：每条后面跟"验收判据"——写成可判定断言（具体输入→具体输出/具体值），不许写"正确处理"这种许愿句
- 异常路径：单列一节，边界逐个列出（参数/权限/下游失败/并发/竞态）
- 允许改动的文件范围：明确"允许改 / 禁止改"两列清单
- 未写明的事项：列为"开放问题"交人拍板，不许按默认自行发明
只输出契约，不写任何代码。
```

**实现过程**：出契约草稿 → 人确认（含对开放问题拍板）→ 落盘。

**验收清单**：
- [ ] 每条规则有可判定断言；
- [ ] 异常路径逐条列（不是"等异常情况"一句带过）；
- [ ] 有"允许/禁止改动范围"；
- [ ] 未定义项进"开放问题"而非被实现。

**换项目怎么改**：路径前缀、错误码段位、鉴权方式按本项目替换；若项目正式契约有固定住所（如 `openspec/changes/*/specs/`），演练/沙盒契约要显式标注"非正式契约"，防未来误读。

## 8. 组件⑦ · SDD 执行 `spec/<能力>-impl/`（第②步·执行）

**它解决什么**：让 AI 严格按契约圈定的范围生成代码 + 测试，改完能跑。

**可复用提示语**：
```
按 spec/<能力>.md 执行，生成：
- <Service 方法> 实现
- <Controller> 接口
- 覆盖 spec 全部规则的单元测试
约束：
- 只能改 spec 里圈定的文件，不许动其他文件
- 不许做 spec 之外的"顺手优化"
- 测试必须覆盖"异常路径"那一节列出的每一条
改完后列出你实际改动的文件清单，以及测试通过情况。
```

**实现过程（本次）**：
1. 读契约（`spec/cart-add.md`）确认允许范围与规则；
2. 因本仓库无该域，产物圈在 `spec/<能力>-impl/` 沙盒，**不污染真实源码树、不破坏构建门禁**；
3. 核心逻辑设计成"只依赖接口、不 import 框架"，用内存假件让单测**能脱离 Spring/DB 真实跑**；框架适配层（Controller/Mapper/DDL）作为交付但不进单测编译；
4. 本地 `javac` 编译 + JUnit Platform Launcher 运行，**实跑 13/13 通过**；
5. 报告改动清单 + 测试结果 + 未定义项（Q1~Q3 未擅自实现）。

**验收清单**：
- [ ] 改动文件全在契约允许范围内（列清单自证）；
- [ ] 每条规则、每条异常路径都有对应测试；
- [ ] 测试是**真实跑过**的（贴通过数），不是"应该能过"；
- [ ] 未定义项没被擅自实现。

**换项目怎么改**：
- 有完整脚手架的项目，直接在真实模块里生成并 `mvn/gradle test`；
- 契约涉及不存在的域时，学本次"沙盒 + 端口接口 + 内存假件"的隔离法，别为演示破坏主构建；
- 运行方式随栈变（Maven/Gradle/npm test 等），关键是"改完必须真跑一遍"。

## 9. 通用工作流（横切所有组件）

1. **两段式**：先草稿/大纲 → 人确认 → 落盘 → 复验。
2. **先取事实**：涉及代码的产物，先 grep/实扫再写。
3. **落盘四查**：行数 / 判据 / 悬空指针 / 命名口径。
4. **单一事实源**：一条规则只有一个家，别处只放指针；迁出词条前验证目的地存在。
5. **诚实标注**：无门禁的红线写"有红线无门禁"、未设的超时写"未设置"（禁写"默认"）、沙盒契约写"非正式契约"。
6. **变更留痕**：正式项目里，影响行为/接口/数据/权限的改动走变更流程（如 OpenSpec change 四件套：proposal/design/tasks/spec）；纯文档小项目可降级为一条 PR 说明，但保留"为什么改"的记录。

## 10. 新项目第一天：最小起步提示语（复制即用）

按顺序跑，先把治理底座立起来：

```
1) 基于本项目 README/构建文件/目录结构，生成 ≤100 行的 CLAUDE.md 草稿（五层结构，红线只放可判定+有抓手的，索引不抄正文，路径先核验），只输出草稿。
2) 建立 .harness/ROUTING.md 三张路由表骨架（≤150 行，重叠项用指针），先留空后逐条填。
3) 生成 .harness/candidate/README.md 暂存区规则（四步流水线 + 进出规则 + 置信度 + 晋升仅人可执行）。
4) 结合真实代码，为 .harness/wiki/ 建五层知识库，每文件首行"装载时机"，内容锚定代码事实，先出大纲。
5) 选一个真实待做的小功能，按 SDD 第①步写 spec/<能力>.md（规则配可判定断言 + 异常路径单列 + 允许/禁止改动范围），只出契约不写码。
```

跑完 1~4 底座就位，第 5 条开始就能用"定规范 → 执行 → 人验 → 迭代"驱动日常变更。

## 附：本 Playbook 与学习笔记的关系

- **学习笔记**回答"是什么 / 为什么"（方法论、红线、金句、消歧）；
- **本 Playbook** 回答"怎么照着做"（提示语 + 步骤 + 验收）；
- 换项目落地时，先读 Playbook 第 0/9/10 节立规矩与起步，再按需查各组件段落。
