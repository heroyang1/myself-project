### 1.1 支付回调幂等闸门全模块覆盖盘点

- **背景与现状**：案例 2 证明"双通道（回调+主动查单）必须共用条件 UPDATE 幂等闸门"。记忆 `90cd20f0` 已沉淀标准范式（FOR UPDATE 行锁 + `ON DUPLICATE KEY` upsert 续期 + pay_status/grant_status 双状态分离），并已验证秒杀、会员中心、工具套餐、核销码、电子书五个模块。**盲区**：新接入支付的模块（信息差、实用网站、课程服务人员等）是否遵循范式未成体系化盘点；`PaymentSuccessConsumer` 的 Handler 注册表里每个 `XxxPaidHandler` 实现质量不一。
- **建议方案**：① 建立"资金链路幂等审计表"，逐 Handler 登记：是否行锁/是否条件 UPDATE/是否 upsert/是否双状态分离；② 新增 PaidHandler 必须通过 checklist 才能合入；③ 对未遵循的 Handler 补 `selectByOrderNoForUpdate` + upsert。
- **预期收益**：杜绝"支付消息重投/回调重试导致权益双发"这一资金类最高危事故。
- **优先级**：**P0**——资金链路，一次事故即资损。

### 1.2 Kafka 消费者退出路径 ack 全量审查

- **背景与现状**：`03228a94` 修复了支付成功消费者"提前 return 漏 ack → 重复消费"（该提交在 release/20260628，**尚未合入 master**，本身就是待办）。项目存在多个手动 ack 消费者（支付成功、公告刷新、ES 同步等），仅支付一个被审查过。**盲区**：其余消费者的每个 return 分支是否都明确了 ack 语义未知。
- **建议方案**：① 枚举所有 `AcknowledgingMessageListener` 消费者，逐条数"return 分支数 ≤ ack 调用覆盖"；② 统一语义：不可恢复脏数据 → ack 丢弃；可恢复异常 → 不 ack 重投；③ 封装 `AckHelper`（try/finally 或函数式包装）消除遗漏可能；④ 跟进 `03228a94` 合入。
- **预期收益**：避免权益重复发放与消息堆积两种极端；排查重复消费问题从小时级降到分钟级。
- **优先级**：**P0**——已有真实事故先例（支付消息重复发放），且修复未合入。

### 1.3 定时任务双调度器重叠治理

- **背景与现状**：项目历史上并存 Spring `@Scheduled`、Quartz、XXL-Job 三套调度；记忆 `d47c080f` 的审查技能明确指出存在功能重复（如 `PayStatusUpdateTask` vs `OrderCloseTask`）。重叠任务在多实例部署下可能并发执行同一批数据。规范（`631b351c`/`ca4a5fb0`）已定：统一 XXL-Job、阻塞策略 `DISCARD_LATER`、批量操作带 `WHERE id IN`、单条异常隔离。
- **建议方案**：按"定时任务横向普查"六步执行：全量枚举 → 重叠检测（合并或下线其一）→ 事务边界验证 → 多实例互斥检查 → 异常隔离评估 → 僵尸代码清理；输出一张任务清单表（类名/频率/职责/调度器/幂等方式）。
- **预期收益**：消除重复关单、重复退款、重复通知类一致性事故；多实例扩容时不再踩坑。
- **优先级**：**P0**——重叠 + 多实例 = 数据被处理两次，直接资损/客诉。

### 1.4 组合订单（Bundle）部分发放落地

- **背景与现状**：课程+电子书等套餐订单包含多个子资源，发放是循环遍历。技能记忆 `41cc1670` 已定义控制范式（逐项幂等 + 单项 try-catch + `bundle_grant_item` 明细表 + 只重试失败子项），**但落地程度未确认**——若无子项明细表，"一个子项因资源被删失败 → 整单回滚 → 无限重试"风险真实存在（坏苹果效应）。
- **建议方案**：① 落地 `bundle_grant_item` 表（order_no / resource_type / resource_id / grant_status / fail_reason / retry_count）；② 发放循环改为子项级事务隔离；③ 定时任务只重试失败子项；④ 不可重试异常（资源已删除）标记终态并告警人工。
- **预期收益**：套餐部分失败不再拖累整单；失败可定位到具体子项；重试风暴消除。
- **优先级**：**P0**——涉及已收款订单的权益交付，失败即客诉。

### 1.5 ES mapping 重建流程全索引覆盖

- **背景与现状**：`27520e7b` 为反馈索引补了 `rebuildIndex()` 三步走（删除→按最新 mapping 创建→全量回灌）。但项目有多个 ES 索引（课程、工具、首页卡片 a/b 双索引、反馈等），**其余索引是否具备同等重建能力未确认**；mapping JSON 是否版本化入仓也未统一。首页卡片用 a/b 双索引轮换，变更字段类型时若漏建别名切换，搜索直接失效。
- **建议方案**：① 为每个索引建立 `IndexRebuilder` 接口实现 + 管理端受保护的重建接口；② mapping JSON 统一放 resources 版本化；③ 首页卡片重建与别名切换联动演练一次并写进 runbook。
- **预期收益**：字段类型变更从"手动改集群的高危操作"变为可重复执行的标准流程，避免搜索静默错乱。
- **优先级**：**P0**（针对有字段变更计划的索引）——搜索是用户入口功能，失效感知极强。

### 1.6 权限注解安全红线制度化

- **背景与现状**：记忆 `0e5e6bd6` 明确红线：禁止为联调注释/删除权限注解。目前只靠 Code Review 人肉把关，无机器防线。项目双权限体系（B 端 `@PreAuthorize` / C 端 `@OshUserLevel`+认证 Filter）本身就高频出 403/越权类缺陷（案例 5）。
- **建议方案**：① CI 增加静态检查：接口方法权限注解被移除时告警（git diff 扫描注解删除）；② 调试需求一律走测试账号或 `@Profile("dev")` 白名单，从源头消灭"注释注解"动机；③ 安全扫描纳入每次 release 门禁。
- **预期收益**：杜绝"联调完忘恢复注解→接口裸奔上线"这一经典事故。
- **优先级**：**P0**——安全类缺陷，一次暴露即数据泄露风险。

### 2.1 统一日志占位符规范

- **背景与现状**：`a7366f06` 修复过"日志写 `seckillNo={}` 实传 orderNo"，排查时按订单号搜不到日志，误导方向。定时任务/消费者只能靠日志排查，错误的日志比没有日志更有害。目前无系统性约束。
- **建议方案**：① 规范：占位符名称必须与变量语义一致，业务主键统一格式 `[模块][动作] key={} value={}`；② 消费者/任务日志强制带业务主键（orderNo/seckillNo/userId 至少其一）；③ Review 检查项+示例进《案例集》。
- **预期收益**：线上问题按关键字即可定位，平均排查时间显著下降。
- **优先级**：**P1**——不直接引发事故，但决定事故恢复速度。

### 2.2 ES 搜索降级策略完善

- **背景与现状**：标准集成模式（`11c299e4`）要求"ES 查询失败自动降级 MySQL"，但**降级覆盖完整性与可观测性未验证**：哪些搜索接口实现了降级、降级后分页/排序行为差异、降级触发是否有告警，均不明确。
- **建议方案**：① 盘点全部 ES 查询入口，逐一确认降级实现；② 降级触发时打 WARN + 计数器（Micrometer），接入告警；③ 降级后的结果差异（如相关性排序缺失）在前端有明确预期。
- **预期收益**：ES 故障时搜索"可用但降级"可感知、可告警，而非静默劣化。
- **优先级**：**P1**——ES 是共享基础设施，故障影响面广。

### 2.3 数据关联匹配键语义一致性治理

- **背景与现状**：三模式陷阱（`98ff87c5`）——SQL 返回 Map key 与 Java 查找键不一致、远程调用入参维度与返回索引维度不一致、同步导入差集匹配条件不精确——均导致**静默数据丢失**。同步/导入场景已有精确匹配规则（`a11d6fca`：完整唯一键逐条查库 + 唯一索引兜底），但日常查询代码未治理。
- **建议方案**：① 用领域对象替代 `Map<key, value>` 传递，编译期暴露维度不匹配；② 聚合/批量关联处增加"查询数 == 匹配数"断言日志，不匹配 `log.warn`；③ 导入场景强制唯一索引兜底。
- **预期收益**：把最难发现的静默丢失变为显式告警。
- **优先级**：**P1**——静默错误累积成数据资产损耗。

### 2.4 Redis Key 生命周期管理

- **背景与现状**：秒杀模块已示范：`bought_cnt` 动态 TTL（`calcExpireSeconds` 与活动结束时间对齐）+ 所有释放路径（取消/超时/发送失败回滚）。但**全仓 Redis Key 无台账**：各业务 Key 的 TTL 策略、释放路径、清理责任散落各处；历史遗留的无 TTL Key 会持续膨胀。
- **建议方案**：① 建立 Redis Key 注册表（常量类集中定义 + 注释说明语义/ TTL/释放路径，参考 `SeckillCacheConstants`）；② 周期性审计任务扫描无 TTL 与超长 TTL Key 并告警；③ 计数器类 Key 必须列举全部增减路径（占位-释放配对检查）。
- **预期收益**：杜绝额度泄漏（用户永久被限购）与内存缓慢膨胀两类慢性问题。
- **优先级**：**P1**——慢性风险，但一旦发作表现为"用户莫名被限制"的疑难客诉。

### 2.5 Lombok 使用约束

- **背景与现状**：`d7a63c0b` 记录：`@AllArgsConstructor`/`@Builder` 与 Jackson 反序列化、MyBatis 反射映射冲突，曾导致"字段有值但 getter 返回 null"。禁用清单已明确（`@Value`、`@RequiredArgsConstructor` 慎用），但无机器防线。
- **建议方案**：ArchUnit/Checkstyle 规则：实体/VO/DTO 禁止 `@AllArgsConstructor`、`@Value`；`@Builder` 必须搭配 `@NoArgsConstructor + @AllArgsConstructor`；新代码默认只用 `@Data`。
- **预期收益**：消灭一类极难排查的字段赋值/反序列化问题。
- **优先级**：**P1**——偶发但排查成本高。

### 3.1 MyBatis XML 静态检查门禁

- **背景与现状**：案例 3/4 的静默失效（列名错位、JOIN 业务字段、缺 `@Param`、空 IN、INSERT 别名）全靠 Review 人肉。项目已用 MyBatisX 插件，但无强制。
- **建议方案**：① CI 集成 MyBatis Mapper 校验（如 mybatis-checker / 编译期注解处理器）检查 XML 列名与实体字段对齐；② Review checklist 固化三条（参数≥2 加 @Param / foreach 判空 / INSERT 无别名）；③ UPDATE 语句强制检查 affected rows 写入规范。
- **预期收益**：把"静默失效"家族在入口拦截。
- **优先级**：**P2**——有 Review 兜底，工具化为提效项。

### 3.2 OSS 签名统一入口 + 四环节检查清单

- **背景与现状**：OSS/R2 私有桶签名是**本项目最高频缺陷域**（记忆 `5f059ea7`），跨 4+ 分支反复出现：路径重复拼接、递归结构漏签、临时 URL 存库裂图、历史完整 URL 未重签。已沉淀标准方案（库只存 objectKey + 读取时动态签名 + 域名白名单提取 objectKey 重签）与四环节检查清单，但各模块实现分散。
- **建议方案**：① 统一 `AssetUrlResolver` 门面：所有对外资源 URL 只经此出口，内部自动判断 objectKey/完整 URL/白名单；② 递归结构（章节、富文本内嵌图）提供专用批量签名方法；③ 四环节清单进 Code Review 模板。
- **预期收益**：将复发率最高的缺陷域收敛到单一出口，"裂图/403"客诉清零。
- **优先级**：**P2**（但建议尽早做，投入产出比最高）。

### 3.3 新模块接入清单模板化

- **背景与现状**：五大集成点（支付/公告/ES/权限/OSS，`11c299e4`）已有检查清单；分支画像进一步证明缺陷可预测——新模块起步期必踩"字段债"（映射/自动填充/分页/判空，release/20260328 画像），集成验证期必踩"权限+校验+OSS"（qa/20260708 画像）。
- **建议方案**：把《案例集》第三层规范 + 五大集成点清单 + 分支预警合并为"新模块上线 Checklist"（起步阶段 8 项 / 集成阶段 7 项 / 上线前安全 4 项），新模块建 OpenSpec change 时强制引用。
- **预期收益**：新模块重演历史坑的概率大幅下降，缺陷前移到开发阶段。
- **优先级**：**P2**——预防性投资。

### 3.4 Outbox 事件表全覆盖

- **背景与现状**：异步链路标准为 Outbox → Kafka → Flink → ES（`11c299e4`），`OutboxEventPublishTask` 已有兜底投递。但部分模块仍用 Kafka 直发（可靠性中等，可能丢消息）；Outbox 表的 `retry_count/next_retry_time` 字段标准是否全表对齐未确认。
- **建议方案**：① 盘点所有"DB 写 + 发 MQ"点，凡核心链路一律改 Outbox；② 统一 Outbox 表字段规范；③ 兜底任务监控积压量。
- **预期收益**：状态与事件原子一致，消除"状态改了消息没发"的中间态。
- **优先级**：**P2**——渐进替换，非核心链路可接受最终一致。

### 3.5 分支画像预警前置

- **背景与现状**：经验地图（`0f049cd1`）显示：80% 未合入修复集中在 qa 可达路径；release→qa 是修复产出最高峰；统计需按提交哈希去重（否则虚高 5-6 倍）。这些元经验尚未流程化。
- **建议方案**：① 每个 release 分支合入前跑一次"修复提交画像"（按家族分类统计），对照《案例集》速查表确认同类问题未复发；② qa 阶段修复实时沉淀进记忆库（本次会话已示范）。
- **预期收益**：质量门禁从"事后修"转向"按画像提前设卡"。
- **优先级**：**P2**——流程改进项。
