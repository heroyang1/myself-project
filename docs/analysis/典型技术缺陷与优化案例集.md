## 第一层 · 概念先行：四大缺陷家族

项目中反复出现的缺陷可归纳为四个"家族"。先理解家族的共性，再看具体案例，举一反三。

| 家族 | 生活化比喻 | 共性特征 | 本集案例 |
|------|-----------|---------|---------|
| **A. 并发竞态** | 两人同时买最后一张票，"先查后改"必出事 | 检查与执行之间有时间窗口；副作用重复触发 | 案例 1、2 |
| **B. 静默失效** | 信寄出去没退信，你以为对方收到了，其实石沉大海 | 编译不报错、运行不报错，行为就是错的 | 案例 3、4、9、12 |
| **C. 体系边界混淆** | 拿 B 门禁卡刷 C 端的门；只看了一眼证件就放行 | 项目存在多套并行的体系（权限/数据源/渠道），跨边界误用 | 案例 5、6 |
| **D. 边界与双写失守** | 两本账只记一本；还库存不封顶还出"幽灵库存" | 关系表+计数、约束+触发、推进+副作用必须成对维护；数值增减必须带边界 | 案例 7、8、10、11 |

**通用心法（三条元规则）**：
1. 凡"先查后写"必有竞态窗口 → 改为条件 UPDATE / CAS / Lua 原子操作；
2. 凡静默失败必埋雷 → 让失败显式化：查 affected rows、判空、入口校验；
3. 凡跨体系/双写模型 → 先确认归属与配对，再动手。

## 第二层 · 案例详解（严格五步结构）

> 每案结构：**① 现象 → ② 根因 → ③ 修改前代码 ❌ → ④ 修改后代码 ✅ → ⑤ 教训与规范**，附提交哈希与记忆索引。

### 案例 1：拼团满员超卖 —— 从"先查后改"到 CAS 原子递增 【家族 A · 并发竞态】

- **关联提交**：`36ea8595`（拼团系统性优化 P0，`git show 36ea8595`）
- **记忆索引**：`4c600fb1-9178-4bbd-9f88-cbb6afdb6e3b`（拼团缓存一致性与并发安全缺陷记录）

**① 现象**：拼团支付回调高并发下，活动已参团人数 `current_num` 可能超过上限 `group_max_num`，出现超卖；对账定时任务还会把人数"改回退"。

**② 根因**：占位用"先 SELECT 判断 → 再 UPDATE +1"两步，两步之间并发窗口内多个回调都判断"还有位"；对账任务裸 `UPDATE current_num=N` 覆盖，与支付回调的递增互相踩踏。

**③ 修改前代码**
```java
// ❌ check-then-act：判断与写入分离，并发下多个请求同时通过判断
OshGroupActivity act = mapper.selectById(activityId);
if (act.getCurrentNum() < act.getGroupMaxNum()) {   // 两个并发回调都读到"还有位"
    act.setCurrentNum(act.getCurrentNum() + 1);
    mapper.updateById(act);                          // 双双 +1 → 超卖
}
```

**④ 修改后代码**（`OshGroupServerMapper.xml` L815-821，当前仓库已核实）
```xml
<!-- ✅ 判断下沉到 SQL 条件，数据库行锁保证原子：100 并发只有 1 个成功 -->
<update id="atomicIncrementCurrentNum">
    UPDATE osh_group_activity
    SET current_num = current_num + 1,
        update_time = NOW()
    WHERE id = #{id}
      AND current_num &lt; group_max_num
</update>
```
```java
// ✅ CAS 失败返回 false（WARN 日志），不抛异常不回滚事务，调用方走"已扣款终态"分支
boolean ok = mapper.atomicIncrementCurrentNum(activityId) > 0;
if (!ok) { log.warn("拼团满员, activityId={}", activityId); return false; }
```

**⑤ 教训与规范**：
- CAS： Compare and Swap 比较 交换（乐观锁）： 不加锁的情况下 保证并发安全
- 通过 synchronized 、ReentrantLock 关键字 实现对资源加锁 
- 一切"名额/库存/资金"递增用条件 CAS（`SET x=x+1 WHERE x<上限`），上限检查物理内置；
- CAS 失败属可预见业务场景：WARN + 返回 false，调用方必须检查返回值；
- 已扣款的失败分支必须有显式终态（退款/关单），禁止静默回滚；
- 对账任务覆盖计数字段必须持锁或改"仅当等于旧值才更新"的 CAS。

### 案例 2：支付双通道重复发放 —— 条件 UPDATE 行数做幂等闸门 【家族 A · 并发竞态】

- **关联提交**：`ce8abba0`（主动查单去重）、`03228a94`（消费确认机制）
- **记忆索引**：`9cfe1fed-ff70-4d12-968d-3844ab649eb4`（主动查单与回调并发需 CAS 结果做幂等闸门）、`a9a68a0d-932c-46c1-9a52-cfbddb76e202`（防重复发送方案）、`1158c438-d7fa-49a0-8134-e38e082fd34e`（幂等控制技能）

**① 现象**：支付成功后支付成功 Kafka 消息发了两次，权益重复发放。

**② 根因**：支付成功有两条天然并发的确认路径——支付平台回调 + 系统主动查单；主动查单路径无条件执行"更新流水 + 发权益消息"，两路各触发一遍副作用。

**③ 修改前代码**
```java
// ❌ 无条件推进 + 无条件发副作用，与回调并发时双份消息
paymentMapper.updateStatus(paymentNo, SUCCESS);
kafkaTemplate.send(PAYMENT_SUCCESS_TOPIC, msg);   // 回调路径也发了一次
```

**④ 修改后代码**（`OrderServiceImpl.java` L692-697 / L1074-1077，当前仓库已核实）
```java
// ✅ 条件 UPDATE（仅 pending→success）返回行数，作为唯一互斥闸门
boolean paymentUpdated = Boolean.TRUE.equals(executeInTransaction(() -> {
    int updated = paymentMapper.updatePendingToSuccess(payment.getPaymentNo(), platformTradeNo, paidTime, null);
    if (updated == 0) {
        return false;                 // 后到者：已被另一路处理，跳过全部副作用
    }
    return orderMapper.updatePendingToPaid(payment.getOrderNo(), paidTime) == 1;
}));
// 仅 paymentUpdated == true 的一方发送支付成功消息 / 发放权益
```

**⑤ 教训与规范**：
- 所有"状态推进 + 副作用"场景必须以**条件 UPDATE 的受影响行数**为幂等闸门，行数 0 即跳过；
- 同一状态的多条触发路径（回调/查单/定时兜底）必须共用同一闸门；
- MQ 消费端 ACK 必须在业务处理成功后提交（`03228a94` 同步修复）。

### 案例 3：MyBatis UPDATE 静默失败 —— 列名不匹配 + JOIN 关联错误 【家族 B · 静默失效】

- **关联提交**：`1f151d1d`
- **记忆索引**：`a41f52ff-a30c-4a7b-9d71-645c3e4d78d7`（MyBatis XML列名不匹配与JOIN条件关联错误）

**① 现象**：拼团订单状态更新后更新时间永远是旧值；参团列表关联查询结果错乱。全程无报错。

**② 根因**：① 表实际列名 `updated_time`，XML 写成 `update_time`，SET 子句静默失效；② JOIN 用业务字段 `group_activity_id` 关联而非主键，多 work 场景串行数据。

**③ 修改前代码**
```xml
<!-- ❌ 列名与 DDL 不一致，静默失败；JOIN 关联业务字段 -->
UPDATE osh_group_order SET status = #{status}, update_time = #{updateTime} WHERE id = #{id}

INNER JOIN osh_group_work gw ON go.group_work_id = gw.group_activity_id
```

**④ 修改后代码**（`OshGroupServerMapper.xml` L531-536 / L255，当前仓库已核实）
```xml
<!-- ✅ 列名对齐 DDL；JOIN 一律主键 -->
UPDATE osh_group_order SET status = #{status}, updated_time = #{updateTime} WHERE id = #{id}

INNER JOIN osh_group_work gw ON go.group_work_id = gw.id
```

**⑤ 教训与规范**：
- 列名必须与 DDL 严格一致，优先 MyBatisX 插件生成，减少手写；
- JOIN 一律主键关联，禁止业务字段；
- UPDATE 后检查 affected rows == 0 即显式抛错，把静默失败变显式失败。

### 案例 4：MyBatis XML 三大静默失效陷阱（@Param / 空 IN / INSERT 别名）【家族 B · 静默失效】

- **关联提交**：规则集，无单一提交（Code Review 检查项）
- **记忆索引**：`e56e34fc-9a7c-4e34-98d9-e6e06de571e6`（MyBatis XML 三大静默失效陷阱）

**① 现象**：三种"不报错但行为错误"：查询条件不生效返回全量数据；空集合查询报 1064 语法错误；带别名的 INSERT 在 MySQL 8.0 报错。

**② 根因**：① 多参数缺 `@Param`，`#{query.startDate}` 无法按名解析被忽略；② `<foreach>` 遇空集合生成 `IN ()`；③ INSERT 语法不支持表别名。

**③ 修改前代码**
```java
// ❌ 陷阱一：多参数无 @Param，XML 中 #{query.startDate} 条件静默失效
List<Record> selectByCondition(RecordQuery query, Integer status);
```
```xml
<!-- ❌ 陷阱二：ids 为空时生成 WHERE id IN () → MySQL 1064 -->
<foreach collection="ids" item="id" open="(" separator="," close=")">#{id}</foreach>
```
```sql
-- ❌ 陷阱三：INSERT 不支持 AS 别名
INSERT INTO osh_course AS t (id, title) VALUES (1,'x')
ON DUPLICATE KEY UPDATE t.title = VALUES(title);
```

**④ 修改后代码**
```java
// ✅ 参数 ≥2 必加 @Param，且与 XML #{xxx.field} 的 xxx 一致
List<Record> selectByCondition(@Param("query") RecordQuery query, @Param("status") Integer status);
```
```xml
<!-- ✅ if 判空包裹，空集合走 1=0 短路（或 Java 层前置 isEmpty 返回空列表） -->
<if test="ids != null and ids.size() > 0"> id IN <foreach .../> </if>
<if test="ids == null or ids.size() == 0"> 1 = 0 </if>
```
```sql
-- ✅ ON DUPLICATE KEY UPDATE 用 VALUES() 或完整表名
ON DUPLICATE KEY UPDATE title = VALUES(title);
```

**⑤ 教训与规范**：
- Mapper 参数 ≥2 必加 `@Param`；所有 `<foreach>` 必须有空集合保护；INSERT 禁用表别名；
- 三者共同点：编译期完全不拦——Code Review 时按此三条逐项扫 XML。

### 案例 5：接口全部 403 —— B 端注解误挂 C 端接口 【家族 C · 体系边界】

- **关联提交**：`81dd573a`（修正小班模块的访问权限）
- **记忆索引**：`9eb79e0e-9ee4-4a8b-bc07-ff9fcc573253`（C端/pc接口混用B端PreAuthorize导致403）；同源：`53871baa-c2f9-44bc-b68b-8e700f2bbdd9`（/pc 前缀被认证 Filter 拦截）

**① 现象**：内部会员管理模块接口全部返回 403，功能完全不可用。

**② 根因**：项目有两套并行权限体系——B 端（RuoYi Spring Security authority）与 C 端（自定义 Filter + osh_role）。Controller 走 `/pc/` C 端链路，却叠加了 B 端 `@PreAuthorize`，C 端登录态里没有这些 authority，全被拦。

**③ 修改前代码**
```java
// ❌ B 端注解挂在 C 端链路上：两套门禁互相打架
@PreAuthorize("hasAuthority('internal:member:*')")
@GetMapping("/page")
public TableDataInfo page(InternalMemberPageQueryDTO query) {
    ensureAdmin();   // 同属 B 端检查
    ...
}
```

**④ 修改后代码**（`InternalMemberAdminController.java`，当前仓库已核实）
```java
// ✅ 移除 B 端注解，权限收敛到 C 端单一机制（认证 Filter + osh_role_permission）
@RestController
@Validated
@RequestMapping("/pc/admin/internal-member")   // /pc/ = C 端链路
public class InternalMemberAdminController extends BaseController {
    @GetMapping("/page")
    public TableDataInfo page(InternalMemberPageQueryDTO query) { ... }
}
```

**⑤ 教训与规范**：
- 新增接口**先确认路径归属哪套认证链路**（`/pc/` = C 端），权限只在该链路机制内实现；
- `/pc/` 前缀接口禁止混用 B 端 `@PreAuthorize`；
- 同源陷阱：公开接口带 `/pc/` 前缀会被认证 Filter 拦 401（`e688778b`），公开接口走 `/public/`；
- 安全红线：禁止为联调注释/删除权限注解，调试用测试账号或 `@Profile("dev")` 白名单。

### 案例 6：VIP 用户被误拦 —— 多角色只查单角色 【家族 C · 体系边界】

- **关联提交**：`e663560d`（高等级用户可观看所有课程）
- **记忆索引**：`5a4a896d-9639-4c91-8cb0-1d25ef6020e4`（多角色用户权限判断只查单角色导致误拦）

**① 现象**：拥有 vip 等多个角色的用户访问付费课程被拦，只能试看。

**② 根因**：`getRoleCodeByUserId()` 只返回用户的**一个**角色；若恰好返回低权限的 `developer`，其余高权限角色全被忽略。

**③ 修改前代码**
```java
// ❌ 单角色查询：永远不能假设返回的是"最高权限"那个
String roleCode = oshRoleMapper.getRoleCodeByUserId(userId);
if ("vip".equals(roleCode)) { return "FULL"; }   // 恰不是 vip → 误拦
```

**④ 修改后代码**（`OshCourseServiceImpl.java` L212-235，当前仓库已核实）
```java
// ✅ 查全量角色 → 逐一比对 → 任一命中即放行
private boolean hasFullCourseAccessByRole(Long userId) {
    List<Integer> roleIds = oshRoleMapper.getRoleIdsByUserId(userId);      // 全部角色 ID
    if (roleIds == null || roleIds.isEmpty()) return false;
    List<OshRole> roles = oshRoleMapper.selectList(
        new LambdaQueryWrapper<OshRole>().in(OshRole::getId, roleIds)
            .eq(OshRole::getDeleteFlag, 0).eq(OshRole::getStatus, 1));
    for (OshRole role : roles) {
        if (role.getRoleCode() != null
            && FULL_ACCESS_ROLE_CODES.contains(role.getRoleCode().toLowerCase(Locale.ROOT))) {
            return true;                                                    // 任一命中
        }
    }
    return false;
}
```

**⑤ 教训与规范**：
- 多角色系统权限判断必须遍历**全部有效角色**，"任一命中即放行"；
- 封装通用 `hasAnyRole(userId, roleCodes)`；全量名单用常量集合集中维护（本例 `FULL_ACCESS_ROLE_CODES`）。

### 案例 7：秒杀库存还出"幽灵库存" —— Redis 归还无上限 【家族 D · 边界失守】

- **关联提交**：`14a0edb4`（库存归还上限 + Lua 原子归还）
- **记忆索引**：`c2803b7d-bcd9-4d68-9958-8c5c1acb58ce`（Redis库存归还超限需Lua脚本加边界）

**① 现象**：秒杀订单取消/超时回滚后，Redis 库存可能超过活动总库存，出现"幽灵库存"。

**② 根因**：归还用 `increment(stockKey, qty)` 直接加，无上限校验，并发归还突破 `totalStock`。

**③ 修改前代码**
```java
// ❌ 裸 increment：不加封顶，并发回滚可超过总库存
stringRedisTemplate.opsForValue().increment(stockKey, quantity);
```

**④ 修改后代码**（`SeckillOrderTimeoutTask.java` L60-73，当前仓库已核实）
```java
// ✅ Lua 原子"读→封顶→写回"，单线程执行无竞态；顺带保留原 TTL
private static final DefaultRedisScript<Long> RETURN_STOCK_SCRIPT = new DefaultRedisScript<>(
    "local cur = tonumber(redis.call('GET', KEYS[1])) or 0 " +
    "local total = tonumber(ARGV[2]) local qty = tonumber(ARGV[1]) " +
    "local ttl = redis.call('PTTL', KEYS[1]) " +
    "local newVal = math.min(cur + qty, total) " +        // 封顶
    "if ttl ~= nil and ttl > 0 then redis.call('PSETEX', KEYS[1], ttl, tostring(newVal)) " +
    "else redis.call('SET', KEYS[1], tostring(newVal)) end return newVal", Long.class);
```
DB 侧对称防护（`OshSeckillActivityItemMapper.incrStock`）：
```sql
-- ✅ LEAST 封顶库存 + GREATEST 防负销量
SET available_stock = LEAST(available_stock + #{quantity}, total_stock),
    sold_count      = GREATEST(sold_count - #{quantity}, 0)
```

**⑤ 教训与规范**：
- Redis INCR/DECR 不带边界，关键计数增减必须 Lua 原子化 + 边界（增封顶、减防负）；
- 归还永远加上限，上限值以 DB 实时值为准；Redis 与 DB 双侧回滚对称防护。

### 案例 8：限购只支持单件 —— Redis 数据结构选型错误 【家族 D · 边界失守】

- **关联提交**：`05e6d5c5`（支持限购数量配置，修复限购写死 1 件）
- **记忆索引**：`e92073e1-4d33-4065-92e0-ea27df4e6609`（Redis数据结构选型错误导致限购只支持单件）

**① 现象**：配置"每人限购 3 件"，但用户买过 1 件后再买就被拒。

**② 根因**：限购校验用 Redis Set（`SISMEMBER`），只能判断"买没买过"（有/无），无法记录"买了几件"（多少）。

**③ 修改前代码**
```lua
-- ❌ Set 只有"在不在集合里"的语义，多件限购无从谈起
if redis.call('SISMEMBER', boughtSetKey, userId) == 1 then return -2 end
redis.call('SADD', boughtSetKey, userId)
```

**④ 修改后代码**（`OshSeckillOrderServiceImpl.java` L195/L276/L408，当前仓库已核实）
```java
// ✅ String 计数器：KEYS[2]=seckill:bought_cnt:{activityId}:{itemId}:{userId}
// Lua 内 GET 已购数 → 判 bought+qty>limit → 通过后 INCRBY；取消/超时同步回滚：
stringRedisTemplate.opsForValue().increment(boughtCntKey, -qty);   // 释放额度
```
`SeckillCacheConstants` 注释同步标记旧 Set Key 废弃：`seckill:bought:`（已购用户 Set，保留兼容）。

**⑤ 教训与规范**：
- 限购/限额用计数器（String + INCRBY/DECRBY），Set 只适合"有/无"判断；
- 数据结构选型先问业务语义是"有无"还是"多少"；
- 计数器占位必须配套所有释放路径（取消/超时/发送失败回滚），否则额度泄漏。

### 案例 9：审核"通过"却变"下架" —— 状态硬编码映射错位 【家族 B · 静默失效】

- **关联提交**：`ff4d2eab`（修复信息差资源审核无法通过/拒绝）
- **记忆索引**：`5c0df4df-cc70-4a4c-b035-a6d157b826a7`（审核状态硬编码映射导致操作静默失效）

**① 现象**：管理员点"审核通过"，数据库状态却与预期不符，审核操作静默失效。

**② 根因**：业务代码里做了错误的数字翻译 `status==1 ? 4 : 6`，与审核中心状态机定义（DRAFT 0 / PENDING_AUDIT 2 / PUBLISHED 4 / OFF_SHELF 6）脱节。

**③ 修改前代码**
```java
// ❌ 裸数字三元映射：假设"1=通过其余皆拒绝"，是代码审查危险信号
int resourceStatus = Integer.valueOf(1).equals(status) ? 4 : 6;
```

**④ 修改后代码**（`ResourceAuditServiceImpl.java` L93-101，当前仓库已核实）
```java
// ✅ ① 入口枚举校验非法值直接拒绝 ② 合法值直接透传不二次加工 ③ 行数显式检查
if (!ResourceStatusEnum.isPublished(status) && !ResourceStatusEnum.isOffShelf(status)) {
    throw new IllegalArgumentException("审核状态错误");
}
int resourceStatus = status;
int rows = resourceAuditMapper.updateAuditStatus(..., resourceStatus, ...);
if (rows <= 0) { throw new ServiceException("待审核资源不存在或已处理"); }
```

**⑤ 教训与规范**：
- 状态流转由状态机/枚举单一定义源管理，禁止裸数字映射；
- 入口处校验 + 透传，不在中途"翻译"；影响行数为 0 必须显式抛错。

### 案例 10：收藏数永远不变 —— 关系表与主表计数脱节 【家族 D · 双写失守】

- **关联提交**：`6aa0f8bf`（解决收藏记录新增但收藏数不变化）
- **记忆索引**：`b8c664b6-f5b1-4e2e-8565-9c6e594c6224`（收藏操作未同步更新主表计数字段）

**① 现象**：收藏/取消收藏后，前端显示的收藏数纹丝不动。

**② 根因**：`toggleCollect()` 只写收藏关系表（明细账），没更新主表 `osh_info_gap.collect_count`（汇总账）。

**③ 修改前代码**
```java
// ❌ 只写明细账，三个状态分支都没碰主表计数
infoGapCollectMapper.insert(entity);
```

**④ 修改后代码**（`InfoGapCollectServiceImpl.java` L54-86，当前仓库已核实，三分支配对同步）
```java
// ✅ 分支1 新增收藏 / 分支3 重新收藏：+1
infoGapMapper.update(null, Wrappers.lambdaUpdate(OshInfoGap.class)
        .eq(OshInfoGap::getId, infoGapId)
        .setSql("collect_count = collect_count + 1"));
// ✅ 分支2 取消收藏：-1 且防负数
infoGapMapper.update(null, Wrappers.lambdaUpdate(OshInfoGap.class)
        .eq(OshInfoGap::getId, infoGapId)
        .setSql("collect_count = GREATEST(collect_count - 1, 0)"));
```

**⑤ 教训与规范**：
- "关系表 + 主表计数"双写模型，任何状态翻转必须**逐分支配对同步**两侧；
- 递减一律 `GREATEST(count-1, 0)` 防负；长期用定时对账视图校正漂移。

### 案例 11：参数校验形同虚设 —— 缺 @Validated 等于零校验 【家族 D · 双写失守】

- **关联提交**：`be7e5914`（修正业务逻辑，补全校验）
- **记忆索引**：`d62b90ce-6e53-4982-a11b-3367448e0248`（DTO校验注解缺@Validated触发等于零校验）

**① 现象**：就业档案接口可写入超长字符串、空必填项，脏数据入库。

**② 根因**：DTO 无约束注解；即使写了注解，Controller 没有 `@Validated` 也不会触发——"规则贴了，保安没到"。

**③ 修改前代码**
```java
// ❌ 裸字段 + 无触发注解 = 零校验
public class InternalMemberEmploymentProfileSaveDTO {
    private Integer jobStatus;    // 可传 null
    private String companyName;   // 可传 10000 字符
}
public R<Void> save(@RequestBody InternalMemberEmploymentProfileSaveDTO dto) { ... }
```

**④ 修改后代码**（`InternalMemberEmploymentProfileSaveDTO.java` L11-49 + Controller，当前仓库已核实）
```java
// ✅ 声明（DTO 约束）+ 触发（@Validated）双到位
public class InternalMemberEmploymentProfileSaveDTO {
    @NotNull(message = "求职状态不能为空")
    private Integer jobStatus;
    @Size(max = 128, message = "公司名称长度不能超过128")
    private String companyName;
}
@Validated                                    // 类上触发注解
public class InternalMemberAdminController extends BaseController {
    public R<Void> save(@Validated @RequestBody InternalMemberEmploymentProfileSaveDTO dto) { ... }
}
```

**⑤ 教训与规范**：
- `@Validated` 必须同时出现在 Controller 类/方法参数上才生效，只写 DTO 注解等于零校验；
- 所有写操作（POST/PUT）DTO 默认带必填与长度约束，错误消息用中文；
- Code Review：新增写接口 → 查 DTO 约束 + 查触发注解，缺一不可。

### 案例 12：审核通过后收不到通知 —— INSERT 遗漏 user_name 【家族 B · 静默失效】

- **关联提交**：`5e2f664a`（补充 user_name 修复小铃铛无法通知发布者）
- **记忆索引**：`78113389-ea46-4eae-b0fd-f167b7d400d8`（INSERT语句遗漏user_name导致通知流程失败）

**① 现象**：信息差审核通过后，发布者收不到小铃铛通知；上游发布、审核环节均无报错。

**② 根因**：`createInfoGap()` 只传 `userId`，INSERT 语句缺 `user_name` 列；下游通知环节需要 `user_name` 定位接收人，字段为空静默断链。

**③ 修改前代码**
```xml
<!-- ❌ INSERT 缺 user_name 列，下游通知找不到发布者 -->
INSERT INTO osh_info_gap (no, user_id, title, tag, content, status, create_time)
VALUES (#{no}, #{userId}, #{title}, #{tag}, #{content}, #{status}, NOW())
```

**④ 修改后代码**（`OshInfoGapMapper.xml` L90-93，当前仓库已核实）
```xml
<!-- ✅ 补列；配套链路：Controller 从 UserContextUtil 取 username → Service 加参 → XML 补列 -->
<insert id="insertInfoGap" useGeneratedKeys="true" keyProperty="id">
    INSERT INTO osh_info_gap (no, user_id, user_name, title, tag, content, status, create_time)
    VALUES (#{no}, #{userId}, #{userName}, #{title}, #{tag}, #{content}, #{status}, NOW())
</insert>
```

**⑤ 教训与规范**：
- 涉及通知/推送的业务，关联用户信息不能只存 `userId`，需冗余 `userName`（或通知时联查）；
- 新增实体字段后必须全局检查所有 INSERT 语句（"字段五处同步"：实体/VO/XML 查询列/INSERT/建表 SQL）；
- 下游依赖的字段，沿数据流反向确认上游是否真实写入。
