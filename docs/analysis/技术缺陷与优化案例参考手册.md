## 总览：缺陷四大家族

先建立一个整体认知。本手册的案例可以归为四大家族，理解了家族特征，遇到新问题时能快速对号入座：

| 家族 | 特征 | 生活化比喻 | 代表案例 |
|---|---|---|---|
| ① 并发竞态 | 两条路径同时推进同一状态，副作用重复执行 | 两个服务员同时给同一桌上菜 | 案例一、二 |
| ② 静默失效 | 代码不报错但行为错误，最危险 | 快递显示签收但东西没到手 | 案例三、六、八 |
| ③ 体系边界混淆 | 双权限体系/多角色体系中用错了"门" | 拿小区门禁卡刷公司大门 | 案例四、五 |
| ④ 生命周期缺失 | 会话/缓存 Key 只管生不管养 | 办了健身卡但没人管到期续卡 | 案例七 |

## 案例一：主动查单与支付回调并发，权益重复发放（并发竞态）

- **提交**：`ce8abba0`　**记忆索引**：`9cfe1fed`《主动查单与回调并发需CAS结果做幂等闸门》
- **涉及文件**：`backstage-system/.../service/order/impl/OrderServiceImpl.java`

### 1. 现象与根因

用户付款后，系统有两条路径同时推进订单状态：支付平台**回调** + 前端轮询触发的**主动查单**。
原代码主动查单路径无条件执行"更新流水 + 发权益消息"，与回调并发时两边都会触发，
导致**支付成功 Kafka 消息重复发送、会员权益重复发放**。

### 2. 修改前（错误代码）

```java
executeInTransaction(() -> {
    paymentMapper.updatePendingToSuccess(payment.getPaymentNo(), platformTradeNo, paidTime); // 不看结果
    orderMapper.updatePendingToPaid(payment.getOrderNo(), paidTime);
});
handleOrderProductPaid(payment.getOrderNo()); // ❌ 无条件发权益消息
```

### 3. 修改后（正确代码）

```java
boolean paymentUpdated = Boolean.TRUE.equals(executeInTransaction(() -> {
    int updated = paymentMapper.updatePendingToSuccess(payment.getPaymentNo(), platformTradeNo, paidTime);
    if (updated == 0) {
        return false; // CAS 失败：说明回调已抢先处理
    }
    orderMapper.updatePendingToPaid(payment.getOrderNo(), paidTime);
    return true;
}));
if (paymentUpdated) {
    handleOrderProductPaid(payment.getOrderNo()); // ✅ 只有本次推进成功者才触发副作用
} else {
    log.info("主动查询支付平台发现订单已被处理，跳过重复发放权益消息, paymentNo={}, orderNo={}",
            payment.getPaymentNo(), payment.getOrderNo());
}
```

配套为本地事务工具新增带返回值的重载，把事务内的 CAS 结果传出：

```java
private <T> T executeInTransaction(Supplier<T> operation) {
    return new TransactionTemplate(transactionManager).execute(status -> operation.get());
}
```

### 4. 修复逻辑与业务影响

用条件 UPDATE（`待支付→成功`）的 affected rows 作为**幂等闸门**：两条并发路径谁先
UPDATE 成功（updated == 1），谁才有资格发下游消息。业务影响：杜绝权益重复开通、
重复推送通知带来的资损与客诉。

### 5. 教训与可复用规范

- 所有"**状态推进 + 副作用**"场景，必须用条件 UPDATE 的 CAS 结果做幂等判断，
  只有推进成功者才允许触发副作用（消息 / 通知 / 发货）。
- 主动查单与回调是天然并发的两条路径，必须共用同一幂等闸门。

## 案例二：拼团回调 CAS 失败抛异常，已付款订单被回滚（并发竞态）

- **记忆索引**：`4467d2e8`《CAS失败处理规范（含拼团模块具体实现模式）》
- **涉及文件**：`OshGroupServerServiceImpl.java`、`OshGroupServerMapper.xml`、`OshGroupUserInitiatedMapper.xml`

### 1. 现象与根因

拼团高并发下多个支付回调同时到达同一活动。CAS 原子递增人数失败时若**直接抛
ServiceException**，外层 `@Transactional` 捕获异常整体回滚 → 订单"已支付"状态也被
回滚 → **用户已付款但本地显示待支付**，与支付平台状态不一致。

### 2. 修改前（错误模式）

```java
int result = mapper.atomicIncrement(activityId);
if (result <= 0) {
    throw new ServiceException("已满员"); // ❌ 触发事务整体回滚，订单状态一并丢失
}
```

### 3. 修改后（正确模式）

```xml
<!-- CAS SQL：UPDATE osh_group_activity SET current_num = current_num + 1
     WHERE id = #{id} AND current_num < group_max_num
     返回 0 表示已满员/被删 -->
```

```java
private boolean handlePayment(...) {
    int result = mapper.atomicIncrementCurrentNum(activityId);
    if (result <= 0) {
        logger.warn("CAS递增失败（已满员），activityId={}, orderNo={}", activityId, orderNo);
        return false;  // ✅ 关键：返回 false 而非 throw
    }
    // ...正常业务逻辑
    return true;
}

// 调用方检查返回值，差异化处理
boolean handlerResult = handlePayment(...);
if (!handlerResult) {
    throw new ServiceException("拼团权益处理失败"); // 由调用方决定是否升级
}
```

该模式同时覆盖双数据源：`atomicIncrementCurrentNum`（系统活动）与
`incrementCurrentNumAtomic`（用户发起拼团）。

### 4. 修复逻辑与业务影响

区分"核心状态写入"与"可预见业务失败"：满员 / 活动被删是正常业务分支，不应让整个
事务陪葬。业务影响：支付状态与本地订单最终一致，满员用户走退款兜底而非卡死在中间态。

### 5. 教训与可复用规范

- 事务内 CAS 失败 → **返回 false + WARN 日志**，不抛异常；调用方必须检查返回值兜底，
  否则 return false 会退化为静默失败。
- CAS 失败三大触发条件要提前预判：并发超卖 / 名额已被占满 / 记录被逻辑删除。
- 日志策略：可预见的业务失败用 WARN，系统异常才用 ERROR；日志带关键标识（ID + 脱敏订单号）。

## 案例三：MyBatis XML 列名不匹配 + JOIN 关联错误（静默失效）

- **提交**：`1f151d1d`　**记忆索引**：`a41f52ff`《MyBatis XML列名不匹配与JOIN条件关联错误》
- **涉及文件**：`backstage-system/src/main/resources/mapper/servicegroup/OshGroupServerMapper.xml`

### 1. 现象与根因

拼团订单状态更新后数据库没变化、且不报错。根因有二：
① `osh_group_order` 实际列名是 `updated_time`，XML 写成 `update_time`，UPDATE 静默失败；
② JOIN 条件用业务字段关联而非主键，查出错误的关联记录集。

### 2. 修改前（错误代码）

```xml
<update id="updateOrderStatus">
    UPDATE osh_group_order
    SET status = #{status},
        update_time = #{updateTime}   <!-- ❌ 表里没有这个列 -->
    WHERE id = #{id}
</update>

INNER JOIN osh_group_order go
    ON go.group_work_id = gw.group_activity_id  <!-- ❌ 业务字段关联，语义错位 -->
```

### 3. 修改后（正确代码）

```xml
<update id="updateOrderStatus">
    UPDATE osh_group_order
    SET status = #{status},
        updated_time = #{updateTime}   <!-- ✅ 与 DDL 严格一致 -->
    WHERE id = #{id}
</update>

INNER JOIN osh_group_order go
    ON go.group_work_id = gw.id  <!-- ✅ 用主键关联 -->
```

### 4. 修复逻辑与业务影响

列名与 DDL 对齐后 UPDATE 正常落库；JOIN 改用主键关联后参团名单查询结果正确。
业务影响：拼团订单状态流转恢复正常。

### 5. 教训与可复用规范

- XML 列名必须与 DDL 严格一致（建议用 MyBatisX 插件自动生成，减少手写）。
- JOIN 条件务必用**主键关联**，禁止拿业务字段凑。
- UPDATE 执行后检查 affected rows 是否为 0，主动暴露静默失败。
- DDL 与 XML 变更必须同批提交，避免"半新半旧"窗口期。

## 案例四：C 端接口混用 B 端 @PreAuthorize，全部 403（体系边界混淆）

- **提交**：`81dd573a`　**记忆索引**：`9eb79e0e`《C端/pc接口混用B端PreAuthorize导致403》
- **涉及文件**：`backstage-system/.../controller/internalmember/InternalMemberAdminController.java`

### 1. 现象与根因

内部会员（小班）模块接口全部返回 403。项目存在**双权限体系**：
- B 端：RuoYi Spring Security authority 体系
- C 端：自定义认证 Filter + 角色体系

`InternalMemberAdminController` 走 `/pc/` C 端链路，却叠加了 B 端 `@PreAuthorize` ——
C 端登录态里根本没有这些 authority，注解必然拦死所有请求。

### 2. 修改前（错误代码）

```java
@PreAuthorize("hasAuthority('internal:member:list')")  // ❌ B端注解用在C端链路
@GetMapping("/page")
public TableDataInfo page(InternalMemberPageQueryDTO query) {
    ensureAdmin();  // ❌ B端身份检查，C端上下文取不到
    startPage();
    ...
}
```

### 3. 修改后（正确代码）

```java
@GetMapping("/page")   // ✅ 移除 B端注解与 ensureAdmin()
public TableDataInfo page(InternalMemberPageQueryDTO query) {
    startPage();
    ...  // 访问控制交给 C端认证 Filter + 角色权限脚本（role_id = 6/7）
}
```

### 4. 修复逻辑与业务影响

删除错配的 40 行权限代码，访问控制回归该链路自己的机制。
业务影响：小班模块管理接口恢复可用，权限粒度由 C 端角色体系正确管控。

### 5. 教训与可复用规范

- 双权限体系项目中，新增接口**先确认路径归属哪个认证链路**，权限控制只在该链路
  对应的机制内实现。
- `/pc/` 前缀接口禁止混用 B 端 `@PreAuthorize`。
- C 端敏感权限通过角色权限脚本精细化控制（限定 role_id = 6/7）。

## 案例五：多角色用户只查单角色，高等级用户被误拦（体系边界混淆）

- **提交**：`e663560d`　**记忆索引**：`5a4a896d`《多角色用户权限判断只查单角色导致误拦》
- **涉及文件**：`backstage-system/.../service/impl/OshCourseServiceImpl.java`

### 1. 现象与根因

部分 VIP 用户无法观看全量课程。根因：`getRoleCodeByUserId(userId)` **只返回一个角色
code**，若 SQL 恰好返回低权限角色（如 `developer`），即使该用户同时持有 vip 等高权限
角色也会被拦截。

### 2. 修改前（错误代码）

```java
// 3. 查用户角色，高级角色直接全开放
String roleCode = oshRoleMapper.getRoleCodeByUserId(userId); // ❌ 只取一个角色，赌运气
if (roleCode != null && FULL_ACCESS_ROLE_CODES.contains(roleCode.toLowerCase())) {
    return "FULL";
}
```

### 3. 修改后（正确代码）

```java
// 3. VIP 及以上角色直接全开放（developer 除外）
if (hasFullCourseAccessByRole(userId)) {
    return "FULL";
}

/**
 * 遍历用户全部有效角色，任一 VIP 及以上角色即可全量访问课程。
 */
private boolean hasFullCourseAccessByRole(Long userId) {
    if (userId == null) {
        return false;
    }
    List<Integer> roleIds = oshRoleMapper.getRoleIdsByUserId(userId);
    if (roleIds == null || roleIds.isEmpty()) {
        return false;
    }
    LambdaQueryWrapper<OshRole> roleWrapper = new LambdaQueryWrapper<>();
    roleWrapper.in(OshRole::getId, roleIds)
            .eq(OshRole::getDeleteFlag, 0)   // ✅ 过滤已删除角色
            .eq(OshRole::getStatus, 1);      // ✅ 过滤停用角色
    List<OshRole> roles = oshRoleMapper.selectList(roleWrapper);
    for (OshRole role : roles) {
        String roleCode = role.getRoleCode();
        if (roleCode != null && FULL_ACCESS_ROLE_CODES.contains(roleCode.toLowerCase(Locale.ROOT))) {
            return true; // ✅ 任一命中即放行
        }
    }
    return false;
}
```

### 4. 修复逻辑与业务影响

从"取单角色赌运气"改为"全量角色 + 任一命中即放行"。
业务影响：高等级用户课程访问恢复正常，消除随机性误拦客诉。

### 5. 教训与可复用规范

- 多角色系统权限判断必须**遍历用户全部有效角色**，永不假设单角色查询返回的是
  最高权限角色。
- 建议封装通用 `hasAnyRole(userId, roleCodes)` 方法。
- 角色查询必须带 `delete_flag = 0 AND status = 1` 过滤。

## 案例六：DTO 缺 @Validated，校验注解等于零（静默失效）

- **提交**：`be7e5914`　**记忆索引**：`d62b90ce`《DTO校验注解缺@Validated触发等于零校验》
- **涉及文件**：`InternalMemberAdminController.java`、`InternalMemberEmploymentProfileSaveDTO.java`

### 1. 现象与根因

内部会员资料接口可写入超长字符串、空必填项。根因：DTO 字段无约束注解，
Controller 参数也无 `@Validated` —— 校验链路两环全缺，等于完全无校验。

### 2. 修改前（错误代码）

```java
// Controller：无触发注解
@PutMapping("/{userId}/employment-profile")
public R<Void> saveEmploymentProfile(@PathVariable("userId") Long userId,
        @RequestBody InternalMemberEmploymentProfileSaveDTO dto) { ... }

// DTO：裸字段，无任何约束
@ApiModelProperty("Company name")
private String companyName;
```

### 3. 修改后（正确代码）

```java
@RestController
@Validated  // ✅ 类级触发
@RequestMapping("/pc/admin/internal-member")
public class InternalMemberAdminController extends BaseController {

    @PutMapping("/{userId}/employment-profile")
    public R<Void> saveEmploymentProfile(@PathVariable("userId") Long userId,
            @Validated @RequestBody InternalMemberEmploymentProfileSaveDTO dto) { ... } // ✅ 参数级触发
}
```

```java
@ApiModelProperty("Company name")
@Size(max = 128, message = "公司名称长度不能超过128")  // ✅ 约束 + 中文提示
private String companyName;

@ApiModelProperty("Job status: 0-unemployed 1-looking 2-employed")
@NotNull(message = "求职状态不能为空")
private Integer jobStatus;
```

### 4. 修复逻辑与业务影响

补全"约束注解 + 触发注解"两环，校验才真正生效。
业务影响：杜绝脏数据（超长值、空必填）进入会员档案。

### 5. 教训与可复用规范

- `@Validated` 必须同时作用于 Controller 类 / 方法参数才生效；**只写 DTO 注解、
  不写触发注解 = 零校验**。
- 所有写操作（POST/PUT）DTO 默认带必填（`@NotNull`）与长度（`@Size`）约束，
  长度上限对齐数据库列宽，并附中文提示信息。

## 案例七：Redis 会话只写不续期，用户操作中途被踢出（生命周期缺失）

- **提交**：`3eb4e258`　**记忆索引**：`a329beaa`《Redis会话未滑动续期导致用户被踢出》
- **涉及文件**：`backstage-framework/.../security/filter/OshAuthenticationFilter.java`

### 1. 现象与根因

用户长时间编辑内容后突然要求重新登录。根因：`LoginUser:{userId}` 会话只在登录时
设置一次 500 分钟 TTL，**后续每次请求都不续期**，持续操作超过 TTL 后 Redis Key
过期，会话丢失。

### 2. 修改前（错误代码）

```java
Map<String, Object> userInfoMap = redisCache.getCacheObject(OshUserConstants.LOGIN_USER + userId);
if (userInfoMap != null) {
    // ❌ 只读不续期，TTL 从登录时刻开始单调递减
    ...
}
```

### 3. 修改后（正确代码）

```java
private static final int LOGIN_EXPIRE_MINUTES = 500;

String loginUserKey = OshUserConstants.LOGIN_USER + userId;
Map<String, Object> userInfoMap = redisCache.getCacheObject(loginUserKey);
if (userInfoMap != null) {
    // ✅ 前台站点登录态每次有效请求都顺延 TTL（滑动过期）
    redisCache.expire(loginUserKey, LOGIN_EXPIRE_MINUTES, TimeUnit.MINUTES);
    ThreadLocalUtil.set(OshUserConstants.USER_ID, userId);
    ...
}
```

### 4. 修复逻辑与业务影响

实现标准的**滑动过期**会话模式：只要用户持续活跃，会话就不会过期；只有真正闲置
超过阈值才失效。业务影响：活跃用户不再被误踢出。

### 5. 教训与可复用规范

- Redis 会话管理禁止"只写不管"，必须在每次有效请求时续期（滑动过期）。
- 或直接使用 Spring Session 的 `setMaxInactiveIntervalInSeconds` 自动处理。

## 案例八：审核状态硬编码数字映射，审核静默失效（静默失效）

- **提交**：`ff4d2eab`　**记忆索引**：`5c0df4df`《审核状态硬编码映射导致操作静默失效》
- **涉及文件**：`backstage-system/.../service/impl/audit/ResourceAuditServiceImpl.java`

### 1. 现象与根因

信息差资源审核时"通过/拒绝"操作后，数据库状态值与预期不符。根因：业务代码中做了
与表状态码定义不一致的硬编码数字映射。

### 2. 修改前（错误代码）

```java
int resourceStatus = Integer.valueOf(1).equals(status) ? 4 : 6; // ❌ 裸数字映射，与表定义脱节
```

### 3. 修改后（正确代码）

```java
int resourceStatus = status; // ✅ 直接透传，状态语义由统一审核状态机定义
```

### 4. 修复逻辑与业务影响

消除错误的中间翻译层，状态值以统一审核状态机为唯一事实来源。
业务影响：资源审核通过/拒绝恢复正常落库。

### 5. 教训与可复用规范

- 状态流转必须由状态机 / 枚举严格定义，**禁止业务代码中裸数字映射**。
- `status == 1 ? 4 : 6` 这类写法是 Code Review 危险信号，必须用
  `AuditStatusEnum.PASSED.getCode()` 代替裸数字。

## 附二：提炼出的通用开发规范清单

按优先级排列，可直接作为 Code Review 检查项：

### 并发与一致性（P0）
1. 状态推进 + 副作用场景，必须用条件 UPDATE 的 CAS 结果做幂等闸门。
2. 事务内 CAS 失败返回 false + WARN，不抛异常；调用方必须检查返回值兜底。
3. 主动查单与支付回调共用同一幂等闸门。

### 静默失效防护（P0）
4. MyBatis XML 列名与 DDL 严格一致；JOIN 用主键关联；UPDATE 后检查 affected rows。
5. `@Validated` 触发注解与 DTO 约束注解必须成对出现。
6. 状态流转用枚举/状态机，禁止裸数字映射。

### 权限与体系边界（P1）
7. 新增接口先确认认证链路归属，`/pc/` C 端接口禁用 B 端 `@PreAuthorize`。
8. 多角色权限判断遍历全部有效角色，"任一命中即放行"，带删除/停用过滤。

### 缓存与生命周期（P1）
9. Redis 会话每次有效请求滑动续期。
10. Redis 流程 Key 明确生命周期：支付成功/取消/超时等终态事件必须检查清理。

### 序列化与展示（P2）
11. `@JsonFormat` 一律显式指定 `timezone = "GMT+8"`。
