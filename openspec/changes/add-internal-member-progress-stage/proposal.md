# Proposal: add-internal-member-progress-stage

## 背景

当前 `InternalMemberAdminController` 已提供付费用户学习总览、就业结果列表、就业档案等接口，但“用户当前所处求职阶段”仍需要前端根据 `jobStatus`、简历投递数、面试状态、面试结果、入职时间等字段自行推断。  
这会带来三个问题：

- 前端阶段判断规则分散，容易和后台录入规则不一致。
- 现有 `jobStatus` 只有粗粒度三段状态，无法直接支撑付费用户模块的进度折线图。
- 若以后阶段规则调整，多端都要同步修改，维护成本高。

本次改造在不破坏原接口的前提下，给内部付费用户相关接口补充“标准化阶段枚举”字段，由后端统一计算当前阶段。

## 目标

- 为内部付费用户新增统一的阶段枚举定义，覆盖更细粒度的求职进度。
- 在现有接口返回中追加阶段字段，保持原路径、原字段、原查询参数兼容。
- 让前端可以直接根据接口返回的阶段字段绘制进度折线图，不再自行拼接复杂规则。

## 非目标

- 本次不修改已有接口路径和请求参数。
- 本次不删除或重命名现有 `jobStatus`、`jobStatusName` 等字段。
- 本次不新增数据库字段，阶段先基于已有就业档案数据推导。
- 本次不实现历史阶段轨迹明细，只提供“当前阶段”标准化输出。

## 用户影响

- 影响后台付费用户模块中的就业结果列表接口。
- 影响后台付费用户单用户就业档案详情接口。
- 现有调用方如果继续使用旧字段，不受影响。
- 新前端可直接使用新增阶段字段渲染阶段进度和图表。

## 风险

- 兼容性风险：低。仅追加返回字段，不移除旧字段。
- 数据风险：中。阶段基于已有字段推导，若历史数据录入不完整，阶段可能回退到较粗状态。
- 性能风险：低。阶段计算在服务层完成，不新增复杂联表。
- 安全风险：低。无权限模型变更。
- 回滚风险：低。回滚只需移除新增字段和计算逻辑。

## 验收标准

- [ ] `GET /pc/admin/internal-member/outcome/page` 返回统一阶段枚举字段，原字段保持不变。
- [ ] `GET /pc/admin/internal-member/{userId}/employment-profile` 返回统一阶段枚举字段，原字段保持不变。
- [ ] 阶段计算遵循统一规则，前后端无需各自维护不同映射。
- [ ] 增加对应测试，验证典型阶段映射和接口兼容性。
