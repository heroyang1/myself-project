# Proposal: add-gateway-service

## 背景

微服务拆分总纲（plan-microservice-split-roadmap）确立绞杀者模式：新服务逐步接管老单体流量，全程可灰度、可秒级回滚。这一策略的核心支点是统一入口网关——所有前端流量先经过网关，再由网关按路径决定转发到"老单体"还是"某个新微服务"。没有网关，就没有灰度切流与路由级回滚能力，绞杀模式无从落地。

当前系统前端直连 backstage-admin 单体，鉴权由单体内的 TokenFilter 承担，无独立入口层。本变更引入 Spring Cloud Gateway 作为 gateway-service，是所有后续 split-* change 的前置基建。

## 目标

- 新建 gateway-service（Spring Cloud Gateway），承接全部对外流量的统一入口。
- Phase 0 阶段网关行为等价于"透明反向代理"：所有请求原样转发回老单体 backstage-admin，前端零感知，风险最低。
- 将现有 TokenFilter 的鉴权粗校验能力上移到网关（JWT 有效性、登录态存在性），服务内保留 @PreAuthorize 细校验，形成双层鉴权。
- 内建按路径前缀路由 + 按用户 ID 尾号灰度分流能力，为后续 split-* 切流做准备（本 change 只建能力，不切实流量）。
- 内建全局限流（Sentinel/RequestRateLimiter）与统一异常/跨域处理。

## 非目标

- 本次不迁移任何业务域到新服务（那是 split-* change 的事）。
- 本次不改变前端调用的 URL/参数/响应结构。
- 本次不下线老单体的 TokenFilter（双跑期保留，网关与服务内双层校验）。
- 本次不引入服务内细粒度权限重构。

## 用户影响

- 对终端用户：Phase 0 无感知（网关透明转发）；域名/DNS 或负载均衡指向网关后，请求多一跳网关。
- 对前端：baseURL 可能需指向网关地址（或由现有 LB 层切换，前端代码不改）。
- 对运维：新增一个需部署、监控、扩缩容的服务；需配置网关路由规则（Nacos 动态路由）。
- 对鉴权：登录态校验点从单体内部前移到网关，需确保 JWT 解析、LoginUser 缓存 key 与单体完全一致（契约冻结）。

## 风险

- 兼容性风险：网关鉴权逻辑与单体 TokenFilter 若不一致，可能导致误拦（403）或漏放。缓解：复用同一套 JWT 工具与 LoginUser key，双跑期对比网关与单体的鉴权结果。
- 数据风险：无（网关不落库）。
- 性能风险：多一跳增加延迟；网关成为单点。缓解：网关无状态可水平扩展，压测 P99 增量控制在可接受范围。
- 安全风险：鉴权前移若配置错误可能绕过。缓解：服务内 @PreAuthorize 细校验保留作为兜底，双层防护。
- 回滚风险：低。缓解：Phase 0 网关纯转发，回滚即让前端/LB 重新直连单体，网关下线不影响业务。

## 验收标准

- [ ] gateway-service 独立启动并注册到 Nacos。
- [ ] Phase 0 透明转发：经网关访问的核心接口（登录、课程、下单、支付回调）响应与直连单体逐字段一致。
- [ ] 鉴权双层校验：无效/过期 JWT 在网关被拦截返回 401；有效 JWT 透传用户上下文，服务内 @PreAuthorize 正常鉴权。
- [ ] 灰度分流能力可用：按用户 ID 尾号配置能将指定比例流量路由到指定目标（用测试路由验证，不切实流量）。
- [ ] 全局限流生效：超过阈值的请求返回约定的限流响应。
- [ ] 统一跨域与异常处理：CORS 正常，网关层异常返回结构与单体 AjaxResult 兼容。
- [ ] 网关无状态，多实例水平扩展下会话/鉴权行为一致。
